# 비교 평가

- 초기에는 20–30개 안팎의 실제 작업 사례로 시작할 수 있다. 고정 숫자보다 주요 실패·정상 처리·스킬 불필요 요청을 포함하는 것이 중요하다.
- 당시 알 수 있었던 입력과 이후 밝혀진 정답·사용자 정정을 분리한다. 정답 누출 없이 baseline과 candidate에 동일 입력을 제공한다.
- 일부 사례는 수정에 사용하지 않은 검증용으로 남긴다. 평가가 불안정한 사례는 반복 결과를 기록한다.
- baseline/candidate의 skill release·bootstrap hash, dataset 버전, evaluator 버전, 모델·도구·저장소 환경을 기록한다. 평가 조건을 가능한 한 동일하게 유지한다.
- 스킬 선택은 검색·로드 경로로 평가하고 실제 코드·외부 도구 동작은 그 실행 경로에서 검증한다. 프롬프트 답변 비교를 전체 Codex 작업 검증으로 보고하지 않는다.
- 평가 실행은 허용된 비용·도구 범위를 따른다. 운영 이슈 수정·배포·메시지 발송을 그대로 재생하지 않고 격리된 저장소와 테스트 도구 결과를 사용한다. 이 환경이 없으면 실행 가능 평가와 미검증 범위를 구분한 계획을 만든다.
- 주지표는 사용자 결과 충족과 중요 오류다. 컨텍스트 토큰, 검색·로드 횟수, 재승인, 비용·지연을 함께 비교한다. 적게 읽었다는 이유만으로 좋은 후보로 판정하지 않는다.
- 지침 삭제·축약 후보도 비교한다. 환경 준비, 연결 복구, 요구 변경, compaction·인계 뒤의 상태 유지 사례를 변경 범위에 맞게 포함한다. 작은 사례집의 동등한 결과를 모든 작업에서의 무회귀 보장으로 표현하지 않는다.
- 전달 과정 개선이라면 구현 시간과 질문·검토·배포 대기를 구분한다. 기획부터 전달까지의 자체 지표와 commit부터 production까지의 DORA change lead time을 혼용하지 않는다.
- 코드로 확인 가능한 항목은 코드 평가기로, 설명·판단 품질은 근거 있는 검토로 평가한다. LLM judge를 사용하면 사용자·검토자 판단과의 일치도를 확인하고 버전을 기록한다.
- 평균 점수뿐 아니라 새로 실패한 중요 사례와 결과 누락을 확인한다. 채점 오류는 에이전트 실패와 분리하며 기준을 바꾸면 양쪽을 같은 기준으로 다시 평가한다.
- Langfuse experiment run과 source trace를 연결한다. 실험을 실행하지 않았다면 효과를 검증했다고 표현하지 않는다.
