# 환경과 업무 흐름

- 실패 지점 앞뒤에서 에이전트가 무엇을 알아야 했는지 확인한다. 긴 설명 대신 상태를 정확히 반환하는 도구나 재실행 가능한 스크립트로 해결할 수 있는지 검토한다.
- 프로젝트·계정·환경·포트·로그·테스트 데이터의 발견 경로를 확인한다. 도구가 정상 상태를 재사용하는지, 재개 후 연결을 확인하는지, 실패 원인을 구체적으로 반환하는지 본다.
- 스킬 절차는 gisul, 제품 요구·결정은 Linear, 코드와 실행·검증 구현은 repo, 관측·평가는 Langfuse에 둔다. 이미 원본이 있는 자료를 새 기억 파일에 복제하지 않고 링크와 버전으로 연결한다.
- 실행 호스트의 상태와 작업 기록에서 원본 이슈, 현재 commit·작업 경로, 로드한 skill digest, 검증 근거, 남은 작업을 재구성할 수 있는지 확인한다. compaction·인계만으로 외부 상태를 확정하지 않는다.
- 이벤트 재전송과 외부 쓰기 타임아웃 뒤의 조회·재시도 동작을 확인한다. trace 누락을 작업 미실행으로, agent_end·idle을 이슈 완료로 해석하지 않는다.
- 구현 시간과 환경 준비·질문·검토·배포 대기 시간을 구분한다. 성공한 결과당 총비용을 보고, commit·티켓 수를 성과로 대체하지 않는다. 부족한 데이터 수집을 위해 먼저 거대한 플랫폼을 만들지 않는다.
- 후보를 지침 수정, 지침 삭제·축약, 검색 개선, 환경 도구, 상태 보존, 검증 개선으로 나눈다. 중요한 변경 변수 하나를 중심으로 비교해 무엇이 효과를 냈는지 판단한다.
- 일상적인 작은 작업에 전체 preflight나 모든 회귀 검증을 강제하지 않는다. 현재 작업의 완료 조건과 실제 실패 위험에 필요한 경로를 사용한다.
- 원격 실행·병렬 작업을 제안할 때는 기존 호스트를 우선 활용한다. 작업 경계·쓰기 소유권·통합 책임·산출물 보존·정리 조건이 필요한지 확인한다. 분석 요청만으로 다른 에이전트를 생성하거나 운영 정책을 바꾸지 않는다.

근거: [Amp의 프로젝트 환경](https://ampcode.com/notes/putting-an-agent-in-an-orb), [Linear의 제품 맥락](https://linear.app/next), [DORA 지표](https://dora.dev/guides/dora-metrics/). 이 문서는 이를 현재 환경에 적용한 판단 절차이며 해당 제품의 기능을 자동으로 제공하지 않는다.
