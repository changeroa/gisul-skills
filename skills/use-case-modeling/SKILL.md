# 사용자 목표에서 검증 가능한 시나리오까지

사용자가 얻어야 하는 결과를 발견하고, 시스템의 외부 책임과 검증 기준으로 바꾼다.
문서 수나 그림의 완성도 대신 목표·경계·예외·보장의 일관성을 확인한다.

## 1. 작업 모드와 권한을 확인한다

- 기존 요구사항 검토, 요구사항 제안 작성, 승인된 변경 구현을 구별한다.
- 요구사항 작성 요청은 인터뷰 초대, 메시지 발송, 일정 생성이나 구현 권한이 아니다.
- 실제 workshop의 참석자 접촉, 녹음, 개인정보 수집과 외부 공유는 별도 권한을 확인한다.
- 승인 없는 workshop은 진행안과 질문 목록까지만 만들고 실제 참여나 합의를 꾸미지 않는다.
- 사용자의 기존 결정과 범위를 보존하고, 제안·가정·관찰된 구현을 확정 요구와 구별한다.
- 중요한 충돌은 결정권자에게 좁혀 묻고, 영향 없는 독립 항목은 계속 진행한다.

## 2. 목적과 시스템 경계를 먼저 적는다

1. 누구의 어떤 문제를 해결하며, 성공하면 무엇이 달라지는지 한두 문장으로 적는다.
2. 시스템 이름, 포함하는 책임, 제외하는 책임과 외부 서비스를 명시한다.
3. 소프트웨어만 다루는지, 장치·사람·조직까지 포함하는지 구별한다.
4. 경계가 달라지면 행위자와 목표도 다시 판단한다.
5. 기존 시스템이 하는 일과 새 시스템에 원하는 일을 별도로 적는다.

짧은 경계 설명이면 충분하다. 합의되지 않은 배포 구조나 내부 클래스를 먼저 고정하지 않는다.

## 3. 행위자와 목표를 발견한다

- 주 행위자: 시스템 서비스를 사용해 가치 있는 결과를 얻는 역할.
- 지원 행위자: 시스템에 필요한 외부 서비스나 정보를 제공하는 역할.
- 비참여 이해관계자: 직접 상호작용하지 않지만 결과에 이해관계가 있는 주체.
- 행위자는 사람뿐 아니라 외부 시스템·조직·장치일 수 있으며, 개인 이름보다 역할로 적는다.
- 시작·종료, 관리, 권한, 운영, 감시, 오류 통지와 외부 호출 주체도 확인한다.
- 시간에 따른 실행은 무조건 시간을 인물처럼 만들지 말고 실제 트리거와 책임 주체를 적는다.

행위자별로 `역할 → 목표 → 관찰 가능한 가치 → 관련 시나리오`를 만든다.
현재 화면의 작업 순서만 묻지 말고, 그 작업을 통해 무엇을 얻으려는지 묻는다.

## 4. 목표의 높이와 use case 범위를 조정한다

1. 이름은 수행하려는 목표를 드러내는 동사구로 쓴다.
2. 완료 결과가 의미 있는 업무 단위인지, 데이터를 일관된 상태로 끝내는지 확인한다.
3. 단일 클릭·입력은 보통 더 큰 목표의 단계로 합친다.
4. 여러 세션·부서에 걸친 거대한 목표는 업무 맥락과 시스템 목표를 나눈다.
5. 인증처럼 작은 목표라도 위험하거나 공통 처리가 복잡하면 별도 분석할 수 있다.
6. 생성·조회·수정·삭제는 독립 가치와 권한이 같을 때만 하나의 관리 목표로 묶는다.

사람 수, 장소, 단계 수, 페이지 수로 유효성을 기계적으로 판정하지 않는다.
기능 중심 제품이나 규칙 중심 문제는 억지로 이야기 형식에 넣지 말고 기능·규칙 계약을 사용한다.

## 5. 필요한 깊이만 선택한다

- 전체 범위는 목표 이름과 짧은 요약으로 넓게 살핀다.
- 가까운 구현 대상, 중요한 가치, 불확실성이나 구조 위험이 큰 목표부터 상세화한다.
- 낮은 위험의 단순 목표는 짧은 형식으로 유지한다.
- 목표 요약, 정상 흐름과 핵심 대안, 상세 단계와 보장 중 필요한 깊이를 선택한다.
- 모든 시나리오를 완성한 뒤 구현을 시작하는 선행 조건을 만들지 않는다.
- 미결정 사항은 빈칸 대신 질문·영향·확인 주체로 남긴다.

## 6. 주 성공 시나리오를 쓴다

1. 범위, 주 행위자, 목표, 트리거와 중요한 이해관계를 적는다.
2. 시작 전에 이미 성립한다고 가정하는 조건만 사전조건으로 적는다.
3. 시작 후 시스템이 검사해야 하는 조건은 단계와 실패 흐름에 적는다.
4. 행위자 의도, 시스템 응답, 검증과 관찰 가능한 상태 변화를 순서대로 쓴다.
5. 각 단계의 주체와 입출력이 분명하도록 번호를 붙인다.
6. 전형적인 성공 흐름은 읽기 쉽게 유지하고 중요한 조건 분기는 확장으로 뺀다.
7. 반복은 종료 조건을 밝히고, 성공으로 끝나는 지점을 명시한다.

시스템은 외부 책임을 가진 블랙박스로 다룬다. 저장 테이블, SQL, 클래스 호출은 설계와 섞지 않는다.
버튼·화면·위젯 이름 대신 의도와 책임을 쓴다. 실제로 확정된 UI·장치 제약은 별도 표시한다.
UI를 빼는 것은 오류 알림, 접근성이나 사용자가 확인할 결과를 빼라는 뜻이 아니다.

## 7. 확장 흐름과 종료 결과를 쓴다

- 각 중요한 단계에서 잘못된 입력, 거절, 취소, 권한 변화와 외부 실패를 살핀다.
- 관련성이 있으면 중복 요청, 응답 유실, 재시도, 중단·복구와 동시 변경도 살핀다.
- 조건은 가능한 한 행위자나 시스템이 탐지할 수 있는 사건으로 표현한다.
- `연결 단계 → 조건 → 처리 → 복귀 지점 또는 종료 상태`를 적는다.
- 대안적 성공과 실패 종료를 구별하고, 부분 성공을 전체 성공으로 표현하지 않는다.
- 어떤 단계에서나 발생하는 조건은 공통 확장으로 묶되 적용 범위를 명시한다.
- 복잡하거나 재사용되는 하위 흐름은 독립 문단으로 분리하되 원래 목표와 연결한다.

지원하지 않는 복구·취소·중복 방지 정책을 임의로 약속하지 않는다. 필요한 정책은 결정 사항으로 남긴다.

## 8. 보장을 이해관계와 맞춘다

1. 성공 종료 시 반드시 성립해야 하는 저장 결과, 외부 효과와 사용자 확인 결과를 적는다.
2. 관련된 경우 실패·취소 시에도 지켜야 하는 데이터·권한·금전 등의 최소 보장을 적는다.
3. 확장 흐름별로 해당 보장이 유지되거나, 어떤 다른 종료 계약을 갖는지 확인한다.
4. 지연 처리가 있다면 요청 접수와 최종 완료를 구별한다.
5. 외부 서비스가 완료한 것과 시스템이 확인·기록한 것을 구별한다.

보장과 장애 처리 사이에 충돌이 있으면 둘 중 하나를 조용히 지우지 말고 명시적인 결정을 구한다.

## 9. 시나리오 밖의 요구사항을 보완한다

- 사용성·접근성, 신뢰성·복구, 성능·용량, 운영·지원성과 변경 가능성을 점검한다.
- 보안·개인정보, 외부 인터페이스, 구현 제약, 법률·라이선스와 데이터 보존도 확인한다.
- 품질 요구는 조건·대상·측정 기준·허용 한계와 확인 방법으로 구체화한다.
- 수치가 합의되지 않았다면 목표치 제안이나 미결정으로 표시하며 확정 기준을 만들지 않는다.
- 여러 시나리오에 걸친 요구는 한 기준 위치에 두고 시나리오에서는 식별자로 연결한다.
- 도메인 규칙은 적용 범위, 권위 있는 근거, 소유자와 변경 가능성을 기록한다.
- 용어와 복합 데이터의 의미, 단위, 범위와 검증 규칙을 정의한다.
- 개요는 요약하고 상세는 연결한다. 문서 이름이나 분리된 파일 수를 강제하지 않는다.

## 10. 추적과 검증 기준을 연결한다

각 중요한 계약에 안정된 식별자를 주고 다음 연결을 유지한다.

`목표·이해관계 → 시나리오·확장 → 규칙·품질 요구 → 수용 기준 → 검증 증거`

- 수용 기준은 초기 조건, 사건 순서, 기대 결과와 허용되지 않는 효과를 포함한다.
- 정상 흐름뿐 아니라 위험한 확장과 보장을 검증할 기준을 남긴다.
- 어떤 조건을 검증할 수 있는지에 맞춰 검증 수단과 환경을 선택한다.
- 요구 검토, 정적 확인, 시뮬레이션, 실행 테스트와 실제 사용자 관찰을 구별한다.
- 실행 권한이나 환경이 없으면 검증 계획과 미검증 범위를 남기고 통과로 보고하지 않는다.
- 테스트 통과를 사용자 목표의 적합성이나 요구사항 완전성의 증명으로 확대하지 않는다.

## 11. 시나리오를 점진적으로 전달한다

1. 가치, 불확실성, 실패 영향과 중요한 경계의 검증 필요로 다음 시나리오를 고른다.
2. 같은 use case도 여러 전달 단위로 나눌 수 있다. 이번 포함·제외 흐름을 명시한다.
3. 각 단위는 시작부터 관찰 가능한 결과까지 연결하고, 필요한 초기화도 포함한다.
4. 합의한 피드백 시점까지 통합·검증 가능한 범위를 잡고, 초과하면 범위 조정을 제안한다.
5. 구현·테스트·사용자 평가에서 드러난 가정과 변경 근거를 요구 기록에 반영한다.
6. 다음 단위를 고를 때 위험과 우선순위를 다시 평가한다.

고정 주수, 상세화 비율, 특정 단계 이름이나 필수 문서 집합을 모든 프로젝트에 적용하지 않는다.
변경 수용은 무제한 범위 확장이 아니다. 약속과 권한을 바꾸는 변경은 결정권자의 승인을 확인한다.

## 12. 결과와 완료 범위를 보고한다

- 경계, 행위자 목표, 선택한 시나리오와 보장이 서로 일치하는가?
- 주 성공·확장 흐름에 주체 없는 단계나 도달 불가능한 복귀 지점이 없는가?
- 품질·규칙·데이터 계약과 승인된 변경의 근거가 추적되는가?
- 이번 전달 단위와 아직 지원하지 않는 흐름이 명확한가?
- 확인된 합의, 제안, 가정과 미결정 사항을 구별했는가?
- 검증한 시나리오, 증거, 미검증 범위와 다음 결정을 보고했는가?

필요한 경우 [시나리오와 workshop 양식](references/scenario-workshop.md), [품질·규칙·추적 양식](references/quality-traceability.md)을 사용한다.
UML 표기 상세는 같은 팩의 `uml-modeling` 소관이다. 이 절차는 그 스킬이나 다이어그램 없이도 수행한다.
