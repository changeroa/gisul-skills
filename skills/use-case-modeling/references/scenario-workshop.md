# 시나리오 발견과 검토

필요한 항목만 기존 요구 기록에 추가한다. 별도 양식이나 모든 칸의 작성을 의무화하지 않는다.

## 1. 목표·경계 기록

- 목적과 성공 변화:
- 시스템 범위 / 명시적 제외:
- 주 행위자와 가치:
- 지원 행위자와 제공 서비스:
- 비참여 이해관계자와 보호할 이해관계:
- 확인된 결정 / 제안 / 가정 / 미결정:

경계가 모호하면 같은 목표를 시스템 단독과 조직 전체 관점에서 각각 설명해 본다. 누가 서비스를 제공하고 누가 이용하는지 비교한 뒤 이번 범위를 선택한다. 조직 관점의 고객을 소프트웨어의 직접 사용자로 자동 치환하지 않는다.

## 2. 상세 시나리오 양식

- 식별자와 목표 이름:
- 범위 / 목표 수준 / 주 행위자:
- 중요한 이해관계:
- 트리거:
- 사전조건:
- 성공 보장:
- 필요한 실패·취소 시 최소 보장:
- 주 성공 단계:
  1. 행위자 의도 또는 외부 사건.
  2. 시스템의 관찰 가능한 응답과 상태 변화.
  3. 목표 완료와 결과 확인.
- 확장: 연결 단계 / 탐지 가능한 조건 / 처리 / 복귀 또는 종료.
- 관련 품질 요구·규칙·데이터 정의:
- 확정된 기술·입출력 제약과 허용 변형:
- 미결정 질문 / 결정권자 / 영향:
- 이번 전달 단위와 제외 범위:
- 수용 기준과 검증 상태:

빈칸은 곧 결함이 아니다. 가치 없는 자명한 사전조건은 생략한다. 중요한 불확실성은 생략하지 않는다.

## 3. 짧은 예시: 장비 예약 확정

다음은 표현 수준을 설명하기 위한 가상 예시이며 제품 정책이 아니다.

- 범위: 장비 예약 서비스. 장비 수리 업무는 제외.
- 주 행위자: 장비 사용자. 가치: 이용 가능한 시간과 예약 결과의 확실성.
- 사전조건: 사용자는 식별되어 있다. 대상 장비의 사용 권한은 예약 중 검사한다.
- 주 흐름: 사용자가 장비와 시간을 지정한다. 시스템이 권한과 이용 가능 여부를 확인한다. 사용자가 예약 내용을 확인한다. 시스템이 예약을 확정하고 확인 정보를 제공한다.
- 확장: 확정 직전 다른 예약으로 시간이 찬 경우, 충돌을 알리고 대체 시간 선택으로 돌아간다.
- 성공 보장: 승인된 시간에 대해 해당 사용자의 예약이 저장되고 결과를 확인할 수 있다.
- 미결정: 응답 유실 후 재시도 시 기존 예약을 어떻게 식별할지 결정이 필요하다.

이 예시의 재시도 정책은 합의 전 요구사항으로 승격하지 않는다. 화면·버튼 이름은 실제 상호작용 설계 단계에서 별도로 결정한다.

## 4. Workshop 준비와 진행

### 권한

요구사항 자료를 작성할 권한과 사람에게 연락할 권한을 구별한다. 참석자 초대, 일정 확정, 녹음, 내부 자료 외부 전송은 각각 승인 범위를 확인한다. 실제 회의가 없었다면 회의 결과나 이해관계자 동의를 만들어내지 않는다.

### 준비

1. 기존 합의, 문제 사례, 제약과 미결정 질문을 모은다.
2. 결정권자, 실제 사용자, 운영 담당자와 외부 경계 전문가 중 필요한 역할을 식별한다.
3. 목표 발견, 대표 흐름 구체화, 충돌 해결 등 이번 회의의 결정 단위를 정한다.
4. 회의 전에 민감 데이터 제거와 기록·공유 범위를 정한다.

### 진행

1. 문제와 시스템 경계를 짧게 맞춘다.
2. 역할별 목표와 이해관계를 적고 누락된 운영·지원 역할을 찾는다.
3. 중요한 목표의 전형적인 성공 이야기부터 함께 쓴다.
4. 각 단계에서 거절·실패·취소를 질문하고 보장과 모순되는 처리 방식을 찾는다.
5. 빠진 품질·규칙·데이터 요구와 결정이 필요한 부분을 분리한다.
6. 우선순위 의견과 확정 결정을 구별하고 다음 검증 단위를 정한다.

표결이나 다수 의견은 법적 근거, 보안 권한 또는 제품 결정권을 대신하지 않는다. 대리 사용자의 의견은 실제 사용자의 검증 결과와 구별한다.

### 종료

확정된 사항, 보류된 사항, 각 결정의 근거와 후속 확인 주체를 공유한다. 승인된 범위에서만 기록을 갱신하고 외부에 전달한다.

## 5. 검토 질문

- 이 목표를 끝내면 누구에게 무엇이 가치 있는가?
- 현재 절차가 아니라 근본 목적을 표현했는가?
- 시작 조건으로 숨겨 버린 검증 책임은 없는가?
- 시스템이 알 수 없는 내부 장애 원인을 조건으로 단정했는가?
- 실패 후 어느 단계로 돌아가며 어떤 상태가 남는가?
- 전체 목표와 이번 구현 범위를 혼동하지 않았는가?
- 공통 하위 흐름 분리가 이해를 돕는가, 탐색만 늘리는가?
- 이해관계자의 요구와 작성자의 추정을 구별할 수 있는가?
