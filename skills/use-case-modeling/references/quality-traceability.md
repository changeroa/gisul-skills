# 품질·규칙·추적과 점진 상세화

## 1. 시나리오가 놓치는 계약

아래 범주를 누락 탐지 질문으로 사용한다. 모든 범주에서 요구를 새로 만들 필요는 없다.

- 기능: 반복되는 공통 기능, 보고, 시스템 간 교환.
- 사용성·접근성: 실제 작업 환경, 입력·피드백 제약과 보조 기술.
- 신뢰성: 장애 탐지, 가용성, 복구와 데이터 손실 허용 범위.
- 성능: 응답·처리량, 부하, 정확도와 자원 한도.
- 운영·지원: 진단, 배포, 백업, 설정, 국제화와 변경 가능성.
- 보안·개인정보: 신원·권한, 최소 수집, 노출, 보존과 삭제.
- 외부 제약: 시스템 인터페이스, 장치, 실행 환경, 법률·계약·라이선스.

분류 이름이 겹쳐도 실제 계약을 중복 작성하지 않는다. 중요한 요구가 어디에 있는지 찾을 수 있으면 된다.

## 2. 측정 가능한 품질 요구 양식

`식별자 / 영향받는 목표 / 조건과 부하 / 관찰할 반응 / 허용 한계 / 측정 방법 / 결정 근거 / 상태`

예시 형태:

- 조건: 합의된 대표 부하와 데이터 규모에서 특정 요청을 수행한다.
- 반응: 사용자가 결과를 확인할 때까지의 시간을 측정한다.
- 한계: 합의한 백분위·시간·오류율을 만족한다.
- 상태: 수치 미합의라면 제안 또는 미결정으로 남긴다.

평균, 백분위, 최대값을 혼동하지 않는다. 측정 시작·종료 지점, 환경과 실패의 포함 여부를 밝혀야 검증할 수 있다. 서로 다른 기록의 수치를 임의로 더 엄격한 쪽으로 합치지 말고 적용 대상과 유효한 결정을 확인한다.

## 3. 규칙과 용어

도메인 규칙에는 다음 중 필요한 정보를 둔다.

- 식별자와 규칙 내용.
- 적용 대상·지역·제품·기간과 예외.
- 근거와 확인 주체, 유효 시점.
- 변경 가능성, 변경 시 영향을 받는 시나리오.

외부 법률·계약·정책은 실제 적용되는 근거를 확인한다. 오래된 예시나 업계 관행만으로 강제 정책을 만들지 않는다. 정식 해석이 필요한 사항은 적절한 결정권자에게 남긴다.

용어·데이터 정의에는 의미, 별칭, 단위, 값의 범위와 검증 규칙을 적는다. 복합 데이터도 구성과 필수 의미를 정의하되 전송 프로토콜이나 내부 저장 구조를 불필요하게 고정하지 않는다.

## 4. 추적 양식

| 목표·이해관계 | 시나리오·확장 | 규칙·품질·데이터 | 수용 기준 | 증거와 상태 |
|---|---|---|---|---|
| 실제 식별자 | 실제 단계 또는 흐름 | 기준 위치의 식별자 | 조건·행동·기대 결과 | 실행/관찰 범위와 미검증 |

링크는 상세 내용을 복제하지 않기 위한 수단이다. 같은 계약의 기준 위치를 하나로 정하고 개요나 시나리오에서는 연결한다. 작은 작업은 기존 이슈의 몇 줄로 충분할 수 있다.

## 5. 보장과 확장의 모순 찾기

다음은 검토 패턴이지 모든 제품에 강제할 요구가 아니다.

- 성공 보장은 외부 작업 완료를 요구하지만 장애 흐름은 접수만 하고 성공으로 끝난다.
- 사전조건은 인증 완료인데 정상 흐름은 인증 실패를 다시 처리한다.
- 취소는 변경이 없다고 약속하지만 이미 발생한 외부 효과의 처리 방식이 없다.
- 재시도를 허용하지만 중복 효과가 허용되는지 정해져 있지 않다.
- 품질 기준이 여러 문서에서 서로 다른 수치로 중복된다.
- 목표 범위는 전사 업무인데 단계는 한 화면의 클릭만 다룬다.

모순을 찾으면 관련 계약과 적용 조건을 함께 제시한다. 기존 약속을 약화하거나 새로운 보상을 임의로 확정하지 않는다.

## 6. 다음 전달 단위 선택

1. 사용자 가치, 불확실성과 실패 영향을 나란히 적는다.
2. 중요한 외부·데이터·권한 경계를 일찍 확인해야 하는지 판단한다.
3. 한 목표 전체보다 검증 가능한 시나리오 일부가 적절하면 포함·제외 흐름을 적는다.
4. 이번 단위의 끝에서 무엇을 관찰하면 위험이 줄었다고 말할 수 있는지 정한다.
5. 단순히 UI만 있거나 저장 기능만 있는 조각을 전체 목표 완료라고 부르지 않는다.
6. 피드백으로 바뀐 요구와 이전 결정을 구별하며 다음 우선순위를 다시 정한다.

학습을 위한 쉬운 예제의 순서를 실제 프로젝트의 위험 우선순위로 그대로 옮기지 않는다. 실험용 프로토타입, 검증된 부분 구현, 실제 배포와 운영 확인을 구별한다.

## 7. 완료 보고 양식

- 이번에 다룬 목표와 시스템 경계.
- 포함한 성공·확장 흐름과 아직 지원하지 않는 흐름.
- 보장·품질·규칙의 확인 상태와 중요한 미결정 사항.
- 실행한 검증의 환경, 대상 버전, 조건, 결과와 증거.
- 실행하지 못한 검증과 필요한 최소 다음 단계.
- 승인된 변경, 그 근거와 다음 피드백 지점.

`통과 / 실패 / 미검증 / 해당 없음`을 구별한다. 요구 문서 작성 완료, 구현 완료, 검증 완료와 배포 완료는 서로 다른 주장이다.
