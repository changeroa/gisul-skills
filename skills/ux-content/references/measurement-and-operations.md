# 측정과 운영

## 질문에서 방법을 고른다

- **무엇이라 부르는가:** 지원 문의·검색어·사용자 작성 내용을 분석하고 인터뷰에서 실제 표현을 수집한다.
- **뜻을 이해하는가:** 용어를 보고 예상되는 내용과 결과를 자기 말로 설명하게 한다.
- **중요 조건을 이해하는가:** 비용·데이터 사용·취소 가능성 등을 유도하지 않는 질문으로 확인한다.
- **찾고 행동할 수 있는가:** 목적만 제시한 과업 테스트로 선택과 완료를 관찰한다. 정답 라벨을 과업에 넣지 않는다.
- **무엇이 어렵고 반가운가:** 이해가 안 되는 표현과 도움이 되는 표현을 구분해 표시하게 하고 이유를 묻는다.
- **정보를 어떻게 묶는가:** 카드 분류와 공동 설계로 개념·순서·그룹 이름을 탐색한다.
- **어느 안이 행동을 바꾸는가:** 구현 여건과 충분한 표본이 있을 때 통제된 비교를 설계한다.
- **어디부터 고칠 것인가:** 과업 단위로 콘텐츠를 평가해 구체적인 근거와 수정 가설을 만든다.

참여자를 모집하거나 연락하기 전에는 작업 권한과 개인정보·연구 동의 절차를 확인한다.
편리한 동료만으로 대상 사용자의 다양성을 대표했다고 하지 않는다. 배제될 수 있는 역할·언어·보조기술 사용자를 고려한다.

## 측정 계획의 최소 필드

기존 이슈나 연구 계획에 다음을 필요한 만큼 남긴다.

1. 콘텐츠가 바꾸려는 사용자 행동과 조직에 대한 의미.
2. 현재 기준선, 계측 이벤트와 완료의 정의.
3. 대상 집단, 노출 조건, 기기·언어·역할과 비교 기간.
4. 비교할 문자열·화면 버전과 함께 바뀌는 비콘텐츠 요소.
5. 주요 지표, 오해·취소·지원 요청 등 부작용 지표.
6. 분석 담당자, 판단 기준과 다음 조치.

클릭 증가와 목표 완료를 구분한다. 긴급 경고의 클릭 감소가 실패이거나, 오래 쓰는 것이 언제나 성공인 것은 아니다.
온보딩 시간은 단순 가입이 아니라 첫 가치 행동까지의 시간을, 완료는 시작 대비 결과 도달을 정의해 측정한다.
지원 비용은 문의 수 외에 해결 시간과 재문의도 본다. 브랜드 인식과 신뢰는 행동 지표만으로 확정하지 않는다.

## 비교 실험의 한계

가능하면 비슷한 집단에 다른 안을 노출하고 기간·표본·최소 의미 있는 차이·중단 조건을 미리 정한다.
낮은 트래픽이나 초기 제품에서는 작은 차이를 구별하지 못할 수 있다. 결과 없음과 두 안이 같다는 결론은 다르다.
전후 비교에는 계절성, 유입 변화, 다른 기능 배포와 노출 차이가 섞일 수 있다.
통계 분석이 필요하면 적절한 담당자와 설계한다. 임의의 고정 표본 수·유의수준을 모든 과업에 강제하지 않는다.

## 휴리스틱 평가

같은 과업과 맥락에서 목적, 용어, 대화 순서, 패턴 적합성, 접근성·현지화와 voice를 평가한다.
현재 화면을 보존하고 관찰·추론·수정 가설을 분리한다. 잘된 부분도 남겨 불필요한 변경을 피한다.
점수가 유용하면 정의한 척도를 같은 제품 안의 우선순위에 사용한다. 적용하지 않는 항목은 분모에서 뺀다.
총점은 상대적인 전문가 판단이지 실제 사용자 성공률이나 접근성 인증이 아니다.
이미 일반 UI QA가 평가한 항목은 그대로 복제하지 말고 필요한 콘텐츠 결정과 문구에 연결한다.

## AI 생성 콘텐츠의 평가

- 도메인 전문가가 좋은·허용 가능한·허용 불가 결과의 특성을 정의하고 평가 예를 맞춘다.
- 형식 준수, 입력 사실 보존, 잘못된 약속·수치 추가, 편향과 해로운 표현을 별도로 확인한다.
- 이상적인 입력뿐 아니라 누락·모순·오타·긴 값·다양한 역할·언어와 악의적 입력을 포함한다.
- 같은 입력도 반복 평가하고 모델·프롬프트·검색 자료의 버전을 기록한다.
- 평가에 쓰는 정답과 사례가 학습·프롬프트 예시에 섞이지 않도록 관리한다.
- 자동 점수는 선별에 사용하되 유용성·사실성·안전을 대신하지 않게 한다.
- 사용자 수정·거부·신고를 학습 재료로 재사용하기 전에 권한, 품질과 비식별 처리를 확인한다.
- 재평가 주기, 실패 시 대체 경로, 위험한 결과의 보고와 운영 담당자를 정한다.

## 최소 운영 흐름

요청 → 브리프 → 화면 내 초안 → 의미·정책 검토 → 확정 → 구현·현지화 → 실제 환경 확인 → 측정·갱신.
각 단계의 책임자와 넘길 항목을 기존 팀 도구에 맞춘다. 모든 문구에 모든 부서의 검토를 요구하지 않는다.
위험에 따라 법률·개인정보·보안·브랜드 검토를 일찍 포함해 뒤늦은 문구 덧붙이기를 줄인다.
리뷰에는 화면과 편집 가능한 문자열, 변수 설명, 추천 이유와 필요한 판단을 같이 제공한다.
댓글 밖에서 받은 의견도 같은 기록에 합치고 해결·보류·기각의 이유를 남긴다.
규제·보존 요구가 있는 콘텐츠는 승인된 버전과 검토 기록을 관리하되 불필요한 개인정보를 쌓지 않는다.

## 콘텐츠 시스템에 남길 것

- **방향:** 대상 사용자, 사용자·조직 목표, 제품 원칙과 측정할 가치.
- **성격:** voice·tone 규칙과 대표 예·반례.
- **패턴:** UI 컴포넌트별 콘텐츠 틀, 용어, 변수·상태 계약과 접근 가능한 이름.
- **실무 규칙:** 표기·숫자·날짜·통화·단위, 현지화 전달, 검토·발행·갱신 책임.

가이드는 실제 컴포넌트와 작업 흐름에서 발견할 수 있어야 한다. 문서를 만들었다는 사실만으로 채택됐다고 하지 않는다.
새 팀에 도입할 때는 관계·현재 콘텐츠 파악, 긴급한 실제 작업, 최소 프로세스·기준선, 공동 확인된 시스템 순으로 확장한다.
정해진 날짜 수보다 실제 채택과 업무 흐름을 기준으로 전환한다. 모든 체계를 완성할 때까지 작은 도움을 미루지 않는다.
