# UX Content

문장을 꾸미기 전에 콘텐츠가 수행할 일을 설계한다. 결과물은 화면별 카피 묶음만이 아니라 목적, 대화 순서, 용어, 구현 가능한 문자열과 검증 방법이다.
기존 제품 정책과 디자인 시스템을 우선한다. 콘텐츠 작업이 기능·권한·데이터 보존 정책 변경을 허가하지는 않는다.

## 1. 콘텐츠 브리프를 만든다

1. 대상 과업을 사용자 역할, 진입 맥락, 원하는 결과, 사용 환경으로 정의한다.
2. 구매자·관리자·설정 담당자·실사용자가 다르면 각각의 정보 요구를 구분한다.
3. 사용자 목표와 조직 목표를 따로 적고, 이 콘텐츠가 돕는 행동을 하나씩 연결한다.
4. 목표가 충돌하면 숨기지 말고 손실, 동의, 비용, 개인정보와 사용자 통제에 미치는 영향을 드러낸다.
5. 법률·보안·브랜드·기술·기기·업데이트 주기·지원 언어의 제약과 확인 담당자를 적는다.
6. 성공 조건과 현재 근거를 정한다. 모르는 제품 동작을 매끄러운 문구로 단정하지 않는다.

브리프는 기존 명세나 이슈에 짧게 둔다. 작은 수정마다 새 전략 문서나 승인 절차를 만들지 않는다.
불명확한 정책이 문구의 의미를 바꾸면 그 부분만 미확정으로 남기고 독립적인 작성은 계속한다.

## 2. 콘텐츠 인벤토리와 우선순위를 잡는다

과업의 진입부터 완료·지원까지 현재 콘텐츠를 모은다. UI뿐 아니라 관련 알림, 이메일, 도움말, 정책 설명도 연결한다.
전체 감사를 요청받았다면 대표 화면만 보고 전체 인벤토리를 완료했다고 하지 않는다.

- 항목별로 위치 또는 문자열 ID, 사용 상태·조건, 대상 역할, 목적, 현재 문구와 관리 담당자를 기록한다.
- 정적 문구, 사용자 작성 내용, 시스템 데이터, AI 생성 내용을 구분한다.
- 동적 값의 자료형, 가능한 범위, 누락·지연·오류 때의 대체 표현을 확인한다.
- 중복, 서로 다른 의미로 쓰인 같은 용어, 오래된 정책, 빠진 지원 경로와 소유자 없는 항목을 찾는다.
- 각 항목에 유지·수정·통합·폐기 제안과 이유를 붙인다. 실제 삭제는 승인된 범위에서만 한다.
- 사용자 손실과 법적 위험, 진행 차단, 출시 의존성을 먼저 보고 긴급성과 중요도를 나눠 순서를 정한다.

인벤토리는 현재 사용 중인 도구에 유지한다. 자료를 모으는 일과 실제 제품에 반영한 일을 구분한다.

## 3. 용어와 voice·tone을 실행 규칙으로 만든다

먼저 검색어, 지원 문의, 기존 연구와 실제 사용자 발언에서 사람들이 쓰는 개념과 표현을 찾는다.
팀 내부의 약어가 사용자 언어라는 가정은 하지 않는다. 전문 용어가 필요한 업무에서는 뜻을 보존한다.

### 용어

- 개념마다 선호 용어, 정의, 품사, 사용 예, 피할 표현과 대안을 기록한다.
- 같은 개념에는 같은 용어를 쓰고 다른 개념을 비슷한 말로 합치지 않는다.
- 모든 일반 단어를 사전에 넣지 말고 제품에서 특별한 의미를 갖는 말에 집중한다.
- 새 이름은 사용자 이해, 기존 명칭과의 구별, 검색·지원·현지화 가능성으로 후보를 좁힌다.
- 이름의 법적 검토가 필요하면 담당자에게 넘긴다. 검색 결과만으로 사용 가능하다고 확정하지 않는다.

### Voice와 tone

Voice는 제품 전반에 유지할 특성이고 tone은 사용자의 상황과 감정에 맞춘 조절이다.
제품 원칙을 추상 형용사로 끝내지 말고 개념, 어휘, 길이, 문법, 구두점, 표기 규칙으로 바꾼다.
각 규칙에 허용 예와 반례를 붙이고, 오류·대기·성공·위험 고지에서 달라질 tone을 정한다.
브랜드의 장난스러움보다 손실 방지와 이해를 우선한다. 사용자가 곤란할 때 억지 유머를 쓰지 않는다.
이미 합의된 가이드를 재사용하고 충돌만 해결한다. 팀 취향 차이는 목표·근거·합의된 규칙으로 논의한다.
전사 규칙을 새로 만들었다면 적절한 결정권자의 확인과 실제 사용 팀의 이해를 얻는다.

## 4. 화면보다 먼저 대화를 설계한다

1. 시작 의도와 완료 결과를 양끝에 놓는다.
2. 제품이 묻고 설명할 말과 사용자가 답하거나 선택할 말을 번갈아 작성한다.
3. 필요한 정보와 질문의 순서를 바꾸며 목표를 더 적은 혼란으로 달성하는 흐름을 찾는다.
4. 새로운 개념은 필요한 시점에 소개하고, 이미 제공한 정보를 다시 요구하지 않는다.
5. 정상 경로뿐 아니라 취소, 수정, 조건 미충족, 실패와 재진입에서 이어질 대화를 확인한다.
6. 제품의 발화는 제목·안내·라벨로, 사용자의 응답은 버튼·선택지·입력으로 옮긴다.
7. 이 순서를 화면과 컴포넌트에 배치하고 문구·정보 계층·상호작용을 함께 다듬는다.

대화형이라는 이유로 모든 제품을 챗봇으로 만들지 않는다. 친근한 말투와 논리적인 대화 순서는 다르다.
역할극과 AI 시뮬레이션은 탐색 도구일 뿐 실제 사용자의 요구나 이해를 검증한 자료가 아니다.

## 5. UI 패턴으로 초안을 작성한다

[UI text patterns](references/ui-text-patterns.md)에서 해당 요소의 목적과 작성 틀을 읽는다.
패턴을 그대로 채우기보다 과업의 용어와 행동에 맞춘다. 제목·설명·버튼·접근 가능한 이름을 한 세트로 작성한다.

- 제목은 맥락을 알려야 하는지 단일 행동을 지시해야 하는지 먼저 결정한다.
- 버튼은 사용자가 하는 행동과 실제 결과를 이름 붙인다. 단순 이동과 결제·게시 같은 확정을 구분한다.
- 메뉴·라벨·컨트롤은 개별 단어가 아니라 함께 보이는 선택지 전체를 비교해 구별한다.
- 안내는 결정에 필요한 조건과 이익·비용을 적절한 시점에 제공한다. 중요한 제한을 각주에 숨기지 않는다.
- 입력은 지속되는 라벨과 필요한 형식·예시·조건을 제공한다. placeholder만으로 필드의 의미를 유지하지 않는다.
- 진행·성공·빈 상태·오류는 확인된 제품 상태에 맞춰 다른 문구를 쓴다.
- 알림은 사용자에게 지금 가치가 있는 정보와 다음 행동을 제공하고 빈도·민감정보 노출을 함께 설계한다.

단어 수나 글자 수를 맞추려고 핵심 조건을 버리지 않는다. 폭·줄 수·읽기 수준의 수치는 언어와 맥락별 참고값이다.

## 6. 네 번의 편집으로 후보를 좁힌다

1. **목적:** 필요한 행동, 조건, 위험, 기대 결과를 모두 담는다. 필요하면 초안은 길어져도 된다.
2. **간결함:** 중복과 불필요한 개념을 줄이고 핵심 정보의 순서를 바꿔본다.
3. **대화:** 제품의 설명과 사용자의 응답을 순서대로 읽고 어색한 단절과 불친절한 축약을 고친다.
4. **이해:** 용어, 수치, 지시, 책임 주체와 행동 결과가 실제 대상에게 같은 의미인지 확인한다.

편집은 실제 화면 또는 그 맥락을 보존한 시안에서 한다. 문자열 목록만 보고 최종 확정하지 않는다.
중요한 선택은 의미 있게 다른 소수의 후보를 만들고 각각의 장단점과 추천 이유를 남긴다.
표현만 바뀐 후보를 수량 맞추기 위해 늘리지 않는다. 이미 좋은 작은 수정은 한 안으로 충분하다.
최종 후보는 문법·맞춤법·표기 일관성까지 확인하되 교정이 콘텐츠 설계를 대신하지 않게 한다.

## 7. 접근성과 현지화를 함께 설계한다

- 화면에 보이지 않는 아이콘 이름, 이미지 설명, 반복 행동의 대상 구별, 오류와 상태 알림도 작성 범위에 넣는다.
- 접근 가능한 이름이 보이는 라벨을 포함하도록 협업하고 이름·역할·값·상태의 전달을 구현 담당자와 확인한다.
- 헤딩·링크는 단독으로 접해도 맥락과 목적을 알 수 있게 한다. 읽기 순서와 지시 순서를 맞춘다.
- 색·위치·시각적 모양만으로 지시하지 않는다. 필요한 의미를 텍스트로도 제공한다.
- 용어의 정확성을 유지하면서 문장 구조를 단순화한다. 영어 읽기 등급을 다른 언어의 합격선으로 옮기지 않는다.
- 번역에는 화면 맥락, 대상 역할, 상태, 변수의 뜻과 제한, 제품 용어를 함께 전달한다.
- 문장을 조각내 이어 붙이지 않는다. 복수형·성별·어순·날짜·시간대·통화·단위는 현지 형식에 맞춘다.
- 관용구와 비유는 평이한 뜻을 함께 남기고 현지 전문가가 자연스러운 표현을 고르게 한다.
- 긴 번역·긴 이름·큰 수·빈 값·RTL·확대 시 잘림과 의미 손실을 실제 레이아웃에서 점검한다.

번역 제공 여부와 업데이트 지연도 접근성에 영향을 준다. 화면 일부 검토를 접근성 인증으로 보고하지 않는다.

## 8. AI 초안과 생성 기능을 구분해 다룬다

AI를 작성 보조로 쓸 때는 브리프, 승인된 용어와 voice 규칙, 확인된 사실과 제약을 제공한다.
후보의 유창함은 정확성의 증거가 아니다. 정책, 가격, 기간, 수치, 자격, 약속과 기능 주장을 근거에 대조한다.
추론으로 채운 내용을 사실처럼 출고하지 않는다. 모르는 내용은 질문·미확정 표시·안전한 생략으로 처리한다.
개인정보·고객 데이터·내부 비밀은 승인된 환경과 허용된 목적 밖으로 보내지 않는다. 예시는 비식별·합성 데이터를 우선한다.

제품이 사용자에게 AI 생성 결과를 보여준다면 문구 검수만으로 끝내지 않는다.
- 생성할 콘텐츠의 목적, 허용·불허 기준, 필요한 사실 입력, 검토자와 수정·거부 경로를 정한다.
- 정적 안내로 생성 내용의 한계와 사용자의 검토 행동을 설명하되 면책 문구만으로 위험이 해결됐다고 보지 않는다.
- 좋은 입력뿐 아니라 누락·오입력·다양한 언어·편향·악의적 입력으로 반복 평가한다.
- 평가용 데이터를 학습·예시용과 분리하고 프롬프트·모델·자료 변경 후 관련 평가를 다시 실행한다.
- 실패 시 대체 경험, 문제 신고·사람 검토, 필요한 기록의 접근권한·보존·삭제 정책과 운영 책임자를 정한다.

AI와 자동 교정 결과에도 최종 콘텐츠 책임을 남긴다. 점수나 단어 유사도만으로 사실성·안전성·도움 여부를 판정하지 않는다.

## 9. 측정할 질문에 맞춰 테스트한다

[측정과 운영](references/measurement-and-operations.md)을 읽고 핵심 불확실성에 맞는 방법을 고른다.
사용자 목표와 연결된 행동 지표, 기준선, 대상 집단, 비교 조건과 부작용 지표를 작성 전에 정한다.
정량 지표는 무엇이 달라졌는지, 인터뷰·과업 테스트는 이해와 선택이 왜 어려운지 조사하는 데 쓴다.
용어는 기대 행동을 설명하게 하고 중요한 조건은 자기 말로 되짚게 한다. 취향 투표만으로 이해를 판정하지 않는다.
휴리스틱 검토는 실제 사용자 테스트와 구분한다. 관찰하지 않은 발언·성공률·전환 개선을 만들지 않는다.
작은 표본이나 전후 변화만으로 콘텐츠의 인과효과를 단정하지 않는다. 통계적 비교가 불가능하면 한계를 밝힌다.
이탈 감소·사용 증가만 최대화하지 말고 오해, 원치 않은 확정, 취소 난이도와 과도한 알림도 함께 본다.

## 10. 협업, 반영과 유지 책임을 닫는다

콘텐츠별 작성자, 의미 검토자, 정책·법률 승인자, 구현자와 유지 담당자를 필요한 범위에서 정한다.
추천안과 대안은 화면 맥락, 해결할 문제, 근거와 검토할 질문을 함께 전달한다.
피드백은 한곳에 모으고 의미·사실·정책 문제와 개인 취향을 구분한다. 해결 결과와 남은 쟁점을 기록한다.
민감한 고지와 필수 승인은 명시적으로 받는다. 사전 합의 없는 침묵을 승인으로 해석하지 않는다.
확정 문자열은 ID, 화면·상태, 변수·현지화 메모와 함께 전달하고 재입력으로 생기는 변형을 피한다.
실제 제품에서 문자열·동적 값·비노출 이름·오류가 승인된 의도와 일치하는지 확인한다.
출시 뒤 측정과 갱신 담당자, 재검토 계기와 만료 조건을 남긴다. 법률·지원·마케팅의 연결 콘텐츠도 조정한다.

## 결과물과 경계

작업 규모에 맞게 **브리프 → 용어·voice 결정 → 화면별 최종 문구 → 선택 이유 → 확인 결과·미확인 사항 → 담당자**를 전달한다.
인벤토리·리뷰 기록·테스트 계획은 기존 작업 공간을 재사용하고 요청받지 않은 대형 보고서를 만들지 않는다.
일반 화면 QA가 찾은 명확성 문제를 되풀이하는 대신 실제 콘텐츠와 작성·운영 결정을 제공한다.
상태의 판정·요청·전환 검증은 `ux-state-review`, 결정과 구현 인계의 연속성은 `preserve-decisions`에 연결한다.
이 스킬은 그 검증을 대체하거나 외부 게시·사용자 모집·연락·배포를 허가하지 않는다.
