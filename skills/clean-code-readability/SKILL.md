# Clean Code: Readability

코드의 의미와 관계가 처음 읽는 사람에게 드러나게 한다. 목표는 짧은 이름, 적은 주석, 작은 파일이 아니라 독자가 불필요한 추론과 왕복 탐색 없이 의도와 구조를 이해하는 것이다.

이 스킬은 이름, 주석, 파일 내부의 배치와 형식을 다룬다. 함수 책임과 제어 흐름은 `clean-code-functions`, 객체·클래스 경계는 `clean-code-objects`의 주 책임이다. 판본과 원칙의 적용 한계는 `skill://gisul/gisul/clean-code/references/sources-and-guardrails.md`에서 확인한다.

## 모드와 권한

리뷰 요청은 읽기 전용이다. 파일 수정은 사용자가 구현·리팩터링을 요청한 범위에서만 수행한다. 테스트·빌드 실행, commit·push·PR·배포와 외부 효과는 호스트와 저장소 정책 및 명시된 권한을 따른다. 사용자의 기존 변경을 덮어쓰거나 무관한 작업을 되돌리지 않는다.

## 1. 독자와 범위를 정한다

1. 대상 기호와 파일뿐 아니라 호출자, 테스트, 설정, 문서, 직렬화 이름, 공개 API 소비자를 찾는다.
2. 코드가 사용하는 문제 도메인 용어와 해법 도메인 용어를 구별한다. 예: 주문 상태는 문제 도메인, parser나 visitor는 해법 도메인이다.
3. repository formatter, lint, naming convention, generated-code 규칙을 확인한다. 팀 일관성이 개인 선호보다 우선한다.
4. 수정 요청이라면 rename이 외부 계약과 저장 데이터에 미치는 영향을 먼저 확인한다.

## 2. 이름의 체계를 점검한다

이름 하나보다 서로 연결된 이름의 체계를 본다.

- **의도:** 왜 존재하고 무엇을 하며 어떻게 쓰는지 드러나는가?
- **구분:** 다른 개념은 실제 의미 차이가 있는 이름을 쓰는가? `data`, `info`, `object`, 숫자 접미사만으로 구별하지 않는다.
- **정확성:** 실제 타입이나 동작과 충돌하는 단서를 주지 않는가? list가 아닌 값을 `...List`라 부르거나, 캐시가 아닌 값을 cache라 부르지 않는다.
- **검색과 발음:** 팀원이 말로 논의하고 저장소에서 찾을 수 있는가? 넓은 범위의 값과 magic literal에는 검색 가능한 이름을 준다.
- **범위:** 아주 좁고 익숙한 반복문의 `i`는 허용할 수 있다. 범위와 수명이 길수록 이름에 더 많은 의미를 담는다.
- **품사와 관례:** 타입은 대체로 명사, 동작은 동사, predicate는 언어 관례에 맞는 질문 형태를 사용한다.
- **단위와 상태:** 시간·거리·통화·원시값의 단위, optional 여부, lifecycle이 오해될 수 있으면 이름이나 타입에 드러낸다.
- **일관된 어휘:** 같은 개념에 `fetch`, `get`, `load`, `read`를 섞기 전에 실제 의미 차이가 있는지 확인한다. 다른 개념을 억지로 한 단어로 통합하지 않는다.
- **맥락:** 반복 prefix보다 클래스, namespace, 모듈, 함수처럼 구조적인 맥락을 우선한다. 구조가 더 복잡해지면 명시적 이름이 낫다.
- **명료성:** 농담, 속어, 문화적 암시, 내부자만 아는 약어를 피한다.

이름 길이에 고정 기준을 두지 않는다. 공용 추상화의 이름은 짧고 안정적일 수 있고, 좁은 private helper나 테스트 이름은 구체적이어서 길 수 있다. 극단적으로 긴 이름이 문장형 주석보다 낫다고 가정하지 말고, 이름과 정확한 설명 중 독자에게 더 적은 부담을 주는 쪽을 택한다.

### 이름 변경 절차

1. 정의와 모든 사용처를 언어 인식 검색으로 찾는다.
2. public API, reflection, dependency injection key, route, SQL·JSON field, template, string lookup처럼 정적 rename이 놓치는 사용을 찾는다.
3. 한 개념의 이름 묶음을 함께 바꾸되 무관한 대량 rename과 섞지 않는다.
4. IDE/LSP/AST rename을 우선하고 전역 문자열 치환을 피한다.
5. 호환성이 필요한 공개 이름은 alias, deprecation, migration 계획을 둔다. 단순 정리라는 이유로 소비자를 깨지 않는다.

## 3. 주석의 정보 가치를 점검한다

먼저 코드가 직접 말할 수 있는지 본다. 복잡한 조건의 의미가 well-named predicate나 지역 변수로 더 정확히 드러난다면 그렇게 바꾼다. 그러나 코드로 표현하기 어려운 정보까지 지우지 않는다.

유지하거나 추가할 가치가 있는 주석은 보통 다음 중 하나다.

- 선택한 해법의 **이유**, 버린 대안, 중요한 트레이드오프
- 외부 시스템·표준·법적 요구·성능 한계 때문에 생긴 **제약과 가정**
- 순서를 어기거나 바꾸면 생기는 **놀라운 결과와 경고**
- 코드만으로는 드러나지 않는 알고리즘이나 정규식의 목적
- 정확한 공개 API 계약과 사용 조건
- 추적 가능한 임시 우회책의 배경과 제거 조건

다음은 제거하거나 고쳐야 할 후보지만, 실제 정보 손실을 확인하고 처리한다.

- 코드 한 줄을 자연어로 다시 말하는 주석
- 현재 구현과 다른 오래된 설명
- “값을 증가시킨다”처럼 정보가 없는 noise
- 작성자 이름, 수정 이력, changelog 역할의 주석
- 실제 관련 코드에서 멀리 떨어진 nonlocal 정보
- 파일을 장식하거나 구획만 크게 나누는 banner
- version control에 이미 남는 주석 처리된 코드
- 모든 private symbol에 의무적으로 붙여 내용을 복제하는 문서 주석

TODO를 일률적으로 금지하지 않는다. 저장소가 issue ID, owner, 만료 조건 같은 형식을 정했다면 따른다. 추적 불가능하고 영구적으로 남은 TODO는 구현하거나 backlog로 옮기거나 제거한다.

### 주석 검증

- 주석이 설명하는 문장마다 현재 코드와 계약에서 확인 가능한지 본다.
- “항상”, “절대”, “thread-safe”, “O(1)” 같은 강한 표현은 실제 보장이 있을 때만 쓴다.
- 주석은 가능한 한 해당 코드 가까이에 두고 다른 모듈의 상태를 대신 설명하지 않는다.
- 코드 수정과 함께 주석, public docs, example도 갱신한다.
- 독자가 이미 알고리즘을 안다는 전제에서 쓴 이름과 주석은 실패하기 쉽다. 낯선 독자의 입장에서 다시 읽는다.

## 4. 형식으로 관계를 드러낸다

formatter가 지원하는 기본 형식을 우선하고 손으로 만든 정렬표를 유지하지 않는다. 형식은 장식보다 구조 전달에 사용한다.

- 서로 다른 개념 사이에는 빈 줄을 두고, 하나의 개념을 이루는 줄은 가깝게 둔다.
- 변수는 첫 사용과 가까운 곳에 두되 여러 함수가 공유하는 field는 팀이 정한 한 위치에 모은다.
- 호출자와 피호출자, 관련 함수와 테스트가 가까우면 읽기 순서가 좋아지는지 본다. 언어의 declaration 규칙이 다르면 그 관례를 따른다.
- high-level policy에서 세부 구현으로 자연스럽게 내려가게 배치한다. 독자가 가장 흔한 질문에 답하기 위해 파일 전체를 오갈 필요가 없게 한다.
- 들여쓰기로 scope를 명확히 하고, 짧다는 이유만으로 여러 scope를 한 줄에 접지 않는다.
- 긴 줄과 거대한 파일은 신호이지 자동 결함이 아니다. 가로 스크롤과 탐색이 실제로 독해를 방해하는지, 분리했을 때 관계가 더 선명해지는지 확인한다.
- 공백과 줄바꿈을 연산자 우선순위나 그룹 표현에 사용할 수 있지만 formatter와 충돌하는 개인 규칙은 강요하지 않는다.
- column alignment가 변경 때마다 흔들리거나 중요한 의미보다 타입·값 모양만 강조하면 제거한다.

무관한 전체 파일 포맷을 의미 변경 diff와 섞지 않는다. 자동 formatter 도입이나 대량 재포맷은 별도 변경으로 분리해 blame과 리뷰 가능성을 보존한다.

## 5. 검증과 결과

변경했다면 다음을 확인한다.

1. rename 후 이전 이름과 문자열 기반 참조를 다시 검색한다.
2. formatter와 lint를 실행하고, public surface나 build에 영향이 있으면 type check와 관련 테스트를 실행한다.
3. diff에서 의미 변경, 삭제된 제약 설명, 무관한 재포맷이 없는지 본다.
4. 파일을 처음부터 읽어 주요 개념과 다음 상세 단계가 자연스럽게 이어지는지 확인한다.

리뷰 결과에는 위치, 실제로 독자를 오도하거나 탐색시키는 단서, 구체적인 대안, 호환성 위험을 적는다. 스타일 선호만 있는 항목은 필수 수정으로 보고하지 않는다. 변경했다면 적용한 rename·주석·배치와 실행한 검사를 요약하고, 검증하지 못한 동적 사용처를 남긴다.
