# 개념 모델과 시스템 동작 계약

업무의 개념과 관계를 먼저 이해하고, 시스템 경계를 넘는 사건이 어떤 사실을 바꾸는지 명시한다.
개념 모델, 시스템 이벤트, 연산 계약, 시나리오 판정을 연결하되 구현 알고리즘을 미리 정하지 않는다.
이 절차는 단독 실행 가능하며 다른 팩의 스킬을 요구하지 않는다.
같은 팩의 `uml-modeling`은 정밀 UML 표기를 소유한다. 여기서는 의미 판단에 필요한 최소 표기만 사용한다.

## 1. 범위와 판단 근거를 고정한다

1. 이번에 해결할 사용자 목표, 대상 업무, 시스템 경계와 제외 범위를 적는다.
2. 대표 정상 시나리오와 빈번하거나 복잡한 대안·실패 시나리오를 고른다.
3. 요구사항, 실제 관찰, 전문가 설명, 구현에서 추정한 내용을 구별한다.
4. 현재 구현이나 DB 구조를 곧바로 업무 규칙의 정답으로 삼지 않는다.
5. 합격 기준을 바꾸는 모호함은 질문하거나 미확정으로 남긴다.
6. 작은 모델로 중요한 불확실성을 줄인다. 전체 업무를 완성한 뒤 구현하려 하지 않는다.

리뷰는 기본적으로 읽기 전용이다. 구현·실행·저장소 변경은 요청받은 범위에서만 한다.
권한, 개인정보와 외부 효과를 모델링 작업이라는 이유로 확대하지 않는다.

## 2. 개념 모델의 관점을 선언한다

- 개념 모델은 문제 영역의 의미 사전이다. DB 스키마나 소프트웨어 클래스 설계도가 아니다.
- 같은 이름의 개념과 코드 타입이 있어도 둘의 정체성·책임·수명이 동일하다고 가정하지 않는다.
- 개념에 메서드, repository, controller, ORM 필드나 외래키를 먼저 넣지 않는다.
- UI나 DB 자체가 문제 도메인인 경우에는 그 개념을 포함할 수 있다. 관점을 명시한다.
- 저장 요구가 없거나 속성이 없는 개념도 이해에 중요하면 포함할 수 있다.
- 모델에서 빠졌다는 사실만으로 구현 요소가 불필요하다고 결론내리지 않는다.

각 핵심 개념에 `이름 / 정의 / 포함되는 실례 / 제외되는 비실례 / 현재 범위에서 필요한 이유`를 적는다.
도메인에서 쓰는 말을 우선하며 동의어·동음이의어는 용어집에서 정리한다.
명사 추출은 후보 생성 수단이지 자동 클래스 생성 규칙이 아니다.

## 3. 개념·값·관계를 구별한다

1. 값이 같아도 별개로 구별해야 하는 대상을 독립 개념 후보로 둔다.
2. 고유 정체성보다 값 동등성이 중요한 정보는 속성 또는 값 타입으로 표현한다.
3. 독립 개념 사이의 의미 있는 연결은 연관으로 표현한다.
4. 관계를 연결하려고 상대의 ID를 속성으로 복제하지 않는다. 구현 키 선택은 이후 결정이다.
5. 복합 값은 부분 구조, 검증, 단위나 의미가 오용을 막을 때 별도 값 타입으로 드러낸다.
6. 모든 문자열과 숫자를 감싸거나 모든 속성을 별도 개념으로 만들지 않는다.

개념 모델의 속성 지침을 코드 필드의 허용 타입 제한으로 옮기지 않는다.
설명·정의가 실체보다 먼저 생기거나 실체 소멸 뒤에도 남아야 하면 설명과 실체를 분리한다.
반복 정보를 줄이는 효과는 유용하지만 정규화만으로 개념 모델의 옳고 그름을 정하지 않는다.
자세한 선택 기준은 [개념 결정](references/conceptual-decisions.md)을 사용한다.

## 4. 연관과 다중성의 의미를 검증한다

- 연관마다 어떤 관계를 왜 얼마 동안 기억해야 하는지 적는다.
- 순간적인 메시지 전달, 조회나 계산 의존성을 모두 연관으로 추가하지 않는다.
- 양 끝을 각각 읽는다. 한쪽 인스턴스 하나를 고정했을 때 반대쪽에 몇 개가 허용되는가?
- 다중성은 지정 시점·상태·범위의 제약이다. 평생 누적 이력 건수와 혼동하지 않는다.
- `*`는 0 이상, `1..*`는 1 이상이다. 0과 1의 차이를 초기·종료 상태에서도 확인한다.
- 현재 담당과 과거 담당처럼 뜻이 다른 관계는 이름과 시간 범위를 구분한다.
- 같은 두 개념 사이에도 서로 다른 역할의 연관이 여러 개 있을 수 있다.
- 연관 이름의 읽기 방향 표시를 코드 탐색 방향이나 호출 방향으로 해석하지 않는다.

관계 자체에 속성·기간·정체성이 있으면 명명된 관계 개념이나 연관 클래스를 고려한다.
다대다라는 이유만으로 중간 테이블을 만들거나 연관 클래스를 강제하지 않는다.
부분의 배타 소유와 수명 제약이 확실할 때만 합성을 표시한다. 애매하면 일반 연관으로 둔다.

## 5. 역할·시간·단위·분류를 다룬다

1. 동일 대상이 동시에 또는 순차적으로 맡는 역할을 식별한다.
2. 역할 이름만 필요하면 연관 끝으로, 고유 정보·기간·규칙이 있으면 별도 역할 개념으로 표현한다.
3. 역할 변화 때문에 대상의 정체성이 바뀌거나 이력이 사라지지 않는지 확인한다.
4. 바뀌는 값은 현재 값, 사건 당시 값, 특정 기간의 유효값 중 필요한 의미를 고른다.
5. 당시 값 복사와 유효기간 이력 중 조회·감사·미래 계획 요구에 맞는 방식을 선택한다.
6. 기간의 시작·끝 포함 여부, 겹침, 빈 구간, 시간대와 소급 수정 정책을 명시한다.
7. 수량에는 단위, 금액에는 통화와 필요한 반올림 규칙을 붙인다.
8. 파생값은 원천과 계산 기준 시점을 밝히고, 독립 사실처럼 중복 관리하지 않는다.

일반화는 하위 집합의 모든 실례가 상위 개념이며 상위 속성·연관 제약을 모두 만족할 때 성립한다.
추가 정보·관계·중요한 취급 차이가 현재 범위에 있을 때만 하위 개념을 만든다.
일시적 상태를 대상의 고정 하위 종류로 만들지 않는다. 상태·전이 또는 별도 상태 개념으로 표현한다.
개념적 분류를 코드 상속, 추상 클래스, 테이블 계층으로 자동 변환하지 않는다.
상위 개념을 무조건 추상화하거나 특정 접미사를 모든 이름에 강제하지 않는다.

## 6. 시나리오에서 시스템 이벤트를 도출한다

1. 시나리오 하나의 시작 상태와 직접 상호작용하는 외부 주체를 고른다.
2. 시스템을 블랙박스로 두고 경계를 넘는 입력 사건, 출력과 외부 시스템 협력을 나열한다.
3. 이벤트를 의도 수준의 동사로 이름 짓고 필요한 매개변수와 반환 의미를 적는다.
4. 장치 조작, UI 클릭명, 전송 프로토콜보다 수행하려는 업무 의도를 드러낸다.
5. SSD에서 시간 순서, 반복 조건과 중요한 대안 분기를 읽을 수 있게 한다.
6. 내부 객체 호출, 서비스 배치나 DB 접근을 SSD에 섞지 않는다.
7. 타이머·장애 사건이 범위에 있으면 인간 입력만으로 이벤트 목록을 끝내지 않는다.

입력 이벤트는 시스템 연산을 요청한다. 동일 연산이 여러 시나리오에 나타날 수 있다.
외부 시스템도 블랙박스다. 동기 화살표만으로 구체 프로토콜이나 원자성을 보장하지 않는다.
시나리오의 직접 입력 주체가 누구인지 확인하고 업무 참여자 전체를 입력 주체로 나열하지 않는다.

## 7. 필요한 연산에만 계약을 쓴다

복잡하거나 미묘한 상태 변화, 여러 개념의 연결, 실패 시 손실이 큰 연산을 우선한다.
단순하고 이미 명확한 동작에 형식 문서를 일괄 생성하지 않는다.
계약은 `연산·입력 / 관련 시나리오 / 사전조건 / 사후조건 / 불변식 / 실패·관찰 범위`로 쓴다.

- 사전조건: 실행 전에 참이라고 가정하는 중요한 상태다. 입력 검증이나 오류 처리의 대체물이 아니다.
- 사후조건: 완료 후 관찰되어야 하는 사실이다. 수행 절차나 호출 순서가 아니다.
- 불변식: 지정 관찰 지점에서 유지되어야 하는 술어다. 모든 값이 변하지 않는다는 뜻이 아니다.
- 실패 계약: 거절·중단·부분 완료·미확정 시 남는 상태와 허용되지 않는 효과를 구분한다.

전후 상태를 비교하여 아래 변화가 빠지지 않았는지 확인한다.
1. 인스턴스 생성·삭제 또는 업무상 존재 종료.
2. 속성 값 변경과 파생값에 영향을 주는 원천 변경.
3. 새 객체와 기존 객체 사이의 링크 형성.
4. 기존 링크 해제·교체와 역할·기간 변화.
5. 변하지 않아야 하는 관련 사실과 금지된 부작용.

새 인스턴스에는 짧은 별칭을 주고 후속 속성·연관 문장에서 같은 별칭을 쓴다.
연결되는 기존 대상은 일치 조건과 범위를 적어 동명이인·다른 계정·다른 시점의 연결을 막는다.
계약에서 발견한 새 개념·상태·관계는 모델과 용어집에 반영하거나 갱신이 불필요한 이유를 적는다.
템플릿과 판정 기준은 [연산 계약](references/operation-contracts.md)을 사용한다.

## 8. 시나리오 추적과 반례를 만든다

각 중요 시나리오에 `초기 상태 → 이벤트 → 적용 계약 → 기대 객체·링크 변화 → 관찰 증거`를 연결한다.
반환 성공, 내부 상태 변경, 영속화 완료와 외부 효과 완료가 같은 사건인지 확인한다.
시스템 밖 후속 결과는 통제 주체, 허용 지연, 완료 증거와 미확정 상태를 명시한다.
단일 계약을 적었다고 여러 시스템의 변경이 자동으로 원자적이라고 주장하지 않는다.

- 정상 사례와 규칙을 깨뜨릴 수 있는 최소 반례를 함께 적는다.
- 다중성의 0·1·상한, 잘못된 대상, 단위 불일치와 시간 경계를 검토한다.
- 상태 순서 역전, 중복 입력, 취소·재시도·부분 실패는 실제 요구와 위험이 있을 때 선택한다.
- 계약의 사후조건을 독립적인 판정 기준으로 삼고 구현 알고리즘으로 기대값을 다시 계산하지 않는다.
- 모델 검토, 소스 추적, 실제 실행과 미검증을 구별한다. 제안한 테스트를 실행했다고 쓰지 않는다.

공유 하위 흐름은 필요할 때 include로 분리한다. 선택 분기라는 이유만으로 extend를 강제하지 않는다.
extend를 쓰면 독립적으로 완결된 기본 흐름, 확장 지점과 발동 조건을 명시한다.
관계 그림을 정리하는 작업이 시나리오 본문과 실패 결과 작성을 대신하지 않게 한다.
자세한 질문은 [시나리오 검토](references/scenario-review.md)를 사용한다.

## 9. 결과와 갱신 범위를 보고한다

- 범위, 용어와 미확정 규칙.
- 개념·값·관계의 구분 및 역할·시간·단위·다중성의 근거.
- 선택 시나리오, 시스템 이벤트와 연산 계약의 연결.
- 생성·변경·해제되는 객체와 링크, 유지할 불변식.
- 정상·반례 판정, 확보한 증거와 미검증 외부 효과.
- 새로 발견한 사실, 변경한 산출물과 유지·폐기할 모델의 소비자.

모델과 계약은 이해와 검증을 위한 도구다. 그림의 완성도나 문서 수를 진척의 대리 지표로 쓰지 않는다.
