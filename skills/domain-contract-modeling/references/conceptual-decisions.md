# 개념 결정과 의미 제약

## 관점 분리

같은 이름도 서로 다른 관점일 수 있다.

- 개념: 업무 참여자가 구별하고 설명하는 대상·사건·약속.
- 값: 정체성보다 내용이 중요하며 동등한 값으로 교체할 수 있는 정보.
- 소프트웨어 타입: 행위·불변식·협력을 구현하는 설계 요소.
- 저장 표현: 인덱스·외래키·행·문서 등 지속성과 조회를 위한 선택.

관점 사이의 대응은 설계 결정이다. 클래스 상자 하나가 코드 타입 하나나 테이블 하나를 요구하지 않는다.

## 정체성과 값

1. 모든 속성이 같아도 서로 다른 두 대상을 구별해야 하는가?
2. 시간이 지나 속성이 바뀌어도 같은 대상으로 추적해야 하는가?
3. 단지 같은 내용을 가진 값으로 바꿔도 의미가 보존되는가?
4. 현재 범위에서 그 차이를 관찰하거나 업무 규칙에 사용해야 하는가?

식별자는 대상과 같지 않다. 식별자 자체에 형식·발급 범위·검증 규칙이 있으면 값 타입으로 다룰 수 있다.
개념 사이의 관계를 표현하려고 상대 식별자를 외래키처럼 쓰는 결정은 뒤로 미룬다.

## 설명과 실체

설명은 실체의 정의·분류·제공 조건을 기록하며, 실체와 다른 수명을 가질 수 있다.
실체가 하나도 없을 때도 설명을 조회·계획해야 하는지, 모든 실체가 사라지면 설명까지 잃어도 되는지 묻는다.
실체별 사실과 공유되는 정의를 구분하되 모든 반복 속성을 무조건 별도 개념으로 분해하지 않는다.

## 관계의 속성과 역할

가령 어떤 사람이 한 프로젝트에서는 조정자이고 다른 프로젝트에서는 참여자라면, 역할은 사람의 영구 종류가 아니다.
역할별 유효기간·권한 범위·배정 사유가 필요하면 역할 배정 자체를 개념으로 둘 수 있다.
이 예는 모델링 선택을 설명할 뿐 고정 클래스 목록을 요구하지 않는다.

관계 개념을 검토할 때 다음을 묻는다.

- 속성의 값이 어느 한 끝만으로 결정되는가, 두 끝의 조합으로 결정되는가?
- 같은 두 대상 사이에 시간·계약·목적이 다른 관계가 반복될 수 있는가?
- 현재 링크가 끝나도 감사·분쟁 처리를 위해 관계 기록을 남겨야 하는가?

관계 기록이 링크보다 오래 남아야 하면 단순한 링크 수명 종속으로 표현하지 않는다.
연관 클래스 표기나 명명된 개념 중 의미와 전달 목적에 맞는 것을 택한다.

## 다중성과 시간

다중성은 양 끝에서 따로 검증한다.
`한 A / 시점·상태·범위 / 허용 B 개수 / 근거 / 0개 사례 / 상한 사례`를 적는다.
초기 상태의 빈 관계와 완료 상태의 필수 관계가 다르면 적용 상태를 명시한다.
현재 배정과 누적 배정 이력에 같은 다중성을 강제하지 않는다.
한 값으로 합칠 수 없으면 상태별 제약이나 기간 있는 관계로 표현한다.

시간 값은 순간, 지역 달력 날짜, 지속시간과 유효기간을 구분한다.
변하는 정책값은 다음 중 필요한 것을 선택한다.

- 사건 당시 값을 보존하는 snapshot.
- 유효기간이 있는 값 이력.
- 현재 값만 필요하다는 명시적 요구.

기간 이력에는 시작·끝 포함, 겹침·공백, 동일 시점 우선순위, 시간대와 소급 변경의 의미가 필요하다.
현재 값을 바꾼 뒤 과거 사건을 다시 조회하는 반례로 역사적 사실 보존을 확인한다.

## 단위와 파생값

단위 없는 숫자는 다른 의미의 값과 잘못 결합될 수 있다.
측정 수량, 통화, 비율, 정밀도와 반올림 위치를 요구에 맞춰 명시한다.
숫자 표현을 정수·부동소수점·십진수 중 하나로 미리 강제하지 않는다.
파생값을 저장할지는 설계 선택이며, 개념 모델에서는 원천과 기준 시점을 우선 밝힌다.

## 일반화와 합성

일반화는 실례의 집합 포함과 상위 정의 준수를 둘 다 만족해야 한다.
공통 속성 이름만 같거나 코드 중복을 줄일 수 있다는 이유만으로 개념적 상하관계를 만들지 않는다.
상위 개념의 제약에 예외를 요구하는 하위 개념은 분류가 잘못됐는지 재검토한다.
일시적 승인·취소 상태는 대상의 종류보다 전이 가능한 상태로 표현하는 편이 적합할 수 있다.
소프트웨어 상속은 별도 설계 결정이며 함수·합성·합 타입 등 다른 표현도 가능하다.

합성은 부분의 수명과 배타 소유에 대한 강한 주장이다.
whole 인스턴스를 삭제할 때까지 부착된 object part도 삭제된다. 허용된 분리·이동을 삭제 전에 수행했다면 생존할 수 있다.
업무 상태 종료는 인스턴스 삭제와 다르다. 소유권 이전·분리 보존·감사 기록과 owner 다중성을 확인한 뒤 사용한다.
합성 표시를 DB cascade delete나 메모리 해제 지시로 자동 변환하지 않는다.
