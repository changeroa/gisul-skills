# 연산 계약 작성과 판정

## 템플릿

```text
연산과 입력:
관련 시나리오·이벤트:
모델 관점과 시스템 경계:
사전조건:
성공 사후조건:
거절·실패·중단 시 결과:
불변식과 적용 관찰 지점:
외부 후속 결과·허용 지연·완료 증거:
미확정 사항:
```

계약의 핵심은 구현 중간 순서가 아니라 의미 있는 관찰 지점의 전후 차이다.
알고리즘을 함수 호출명 대신 자연어로 바꿔 적었다고 계약이 되는 것은 아니다.

## 전후 차이 체크

각 변화에 대상 인스턴스와 일치 기준을 명시한다.

| 변화 | 확인할 질문 |
|---|---|
| 생성 | 무엇이 새로 존재하며 다른 기존 대상과 어떻게 구별되는가? |
| 속성 변경 | 어느 값이 어떤 입력·규칙을 기준으로 달라졌는가? |
| 링크 형성 | 새 대상이 누구에게 연결됐으며 다른 대상에 잘못 연결되지 않았는가? |
| 링크 해제·교체 | 이전 연결은 종료됐는가, 이력으로 남는가? |
| 삭제·존재 종료 | 업무상 종료, 기록 폐기, 소프트웨어 객체 제거 중 무엇인가? |
| 보존 | 영향받지 않아야 할 관련 상태와 금지된 부작용은 무엇인가? |

새 대상의 별칭을 후속 문장에서 재사용한다. 새로 만들었다는 사실만 적고 관계를 빠뜨리지 않는다.
모든 내부 field의 불변을 나열하지 말고 중요한 보존 조건과 영향 범위를 적는다.

## 사전조건과 실패를 혼동하지 않기

사전조건은 이 계약이 적용되는 상태의 가정이다.
시스템이 전제 위반 입력도 받을 수 있다면 거절·오류·무시·보정 중 실제 정책을 별도로 정한다.
전제를 적는 것만으로 모든 진입점이 그 조건을 검사한다고 주장하지 않는다.
입력 형식 검증과 업무 상태의 유효성도 구별한다.

예를 들어 업무 배정 요청에 이미 종료된 대상이 들어올 수 있다면, 정상 계약의 전제를 적는 것에 더해 그 요청의 실패 결과를 정의해야 한다.
이 예는 특정 오류 응답이나 저장 방식을 강제하지 않는다.

## 불변식의 적용 지점

불변식은 지정 범위의 모든 유효 상태에서 참이어야 할 술어다.
값 자체는 변할 수 있으며 관계를 포함한 술어가 유지돼야 한다.
관찰 지점은 연산 전후, commit 후, 공개 조회 시점 등 실제 보장에 맞춰 명시한다.
내부에서 잠시 나타나지만 외부에 보이지 않는 중간값을 곧바로 위반으로 판정하지 않는다.
반대로 외부에서 관찰 가능한 중간 상태를 내부 구현이라는 이유로 숨기지 않는다.

## 시스템 경계를 넘는 결과

외부 요청을 보냈다는 사실, 상대가 수락한 사실, 실제 효과가 완료된 사실은 다를 수 있다.
후속 결과마다 통제 주체·허용 지연·실패 처리·완료 증거를 정한다.
확인할 수 없는 결과는 미확정으로 남기며 응답 성공으로 대체하지 않는다.
다중 시스템 계약을 썼다는 이유로 원자성·한 번 실행·롤백을 가정하지 않는다.
중복·부분 실패 대응 방식은 실제 요구와 실행 모델을 조사한 뒤 설계한다.

## 계약과 설계의 경계

좋은 사후조건은 데이터 구조나 호출 순서가 달라져도 동일 의미를 검증할 수 있다.
특정 캐시·테이블·메서드 호출이 관찰 계약 자체인 경우에만 그 세부를 명시한다.
상태 변화가 모호하면 전후 개념 인스턴스와 링크를 간단히 적어 비교한다.
새 개념이 필요하면 모델을 개선한다. 기존 모델에 없는 사실이라는 이유로 요구를 버리지 않는다.

## 완료 체크

- 이벤트와 연산의 이름·입력 의미가 연결되는가?
- 객체 생성 뒤 필수 연결과 식별 범위가 빠지지 않았는가?
- 거절·실패 결과를 성공 계약과 혼합하지 않았는가?
- 불변식의 적용 시점과 통제 범위가 명확한가?
- 설계 선택을 필수 요구처럼 적지 않았는가?
- 판정 가능한 정상 사례와 반례가 있는가?
