# 상호작용 피드백 계약

작은 행동을 **트리거 → 규칙 → 피드백 → 반복·모드**의 시간적 계약으로 다룬다.
사용자가 무엇을 했고, 지금 무엇이 사실이며, 무엇을 할 수 있고, 언제 끝났는지 알게 한다.
피드백을 추가하는 것 자체가 목표는 아니다. 필요한 의미를 정직하고 접근 가능한 방식으로 전달한다.

## 작업 모드와 권한

- 설계 요청이면 제품 규칙과 제안·가정을 구분하여 계약과 검증 조건을 작성한다.
- 리뷰 요청이면 읽기와 허용된 관찰을 수행한다. 문제 제기를 코드 수정 허가로 해석하지 않는다.
- 구현 요청이면 승인된 기능·파일만 수정하고 영향을 받는 전환을 검증한다.
- 브라우저·테스트 도구는 작업 환경의 현재 지침을 따른다. 이 스킬은 도구 권한을 제공하지 않는다.
- 게시·결제·삭제·외부 전송·개인정보 수집은 기존에 허가된 범위에서만 수행한다.
- 운영 데이터로 실패를 주입하지 않는다. 안전한 재현 환경이 없으면 해당 검증을 보류한다.
- 규칙이 불명확하면 독립적인 검토는 계속하고, 판정을 바꾸는 미결정 사항만 분리한다.

## 책임과 비적용 경계

| 필요한 판단 | 담당 범위 |
| --- | --- |
| 언제 어떤 의미가 어떤 채널로 나타나고 끝나야 하는가 | 이 스킬 |
| 도달 가능한 제품 상태와 유효한 다음 행동은 무엇인가 | ux-state-review |
| 행동을 발견하고 라벨·화면을 이해할 수 있는가 | dont-make-me-think |
| 실제 화면·요청·저장 결과가 전환마다 맞는가 | browser-e2e-review |
| 요청 순서·이벤트·생명주기 때문에 잘못된 결과가 생기는가 | review-client-runtime |
| 재시도·멱등성·취소·보상의 실제 보장은 무엇인가 | review-failure-resilience |

기존 상태표·테스트·컴포넌트를 재사용한다. 전체 상태 분류나 네트워크 복원력 검사를 복제하지 않는다.
시간·채널 문제가 없는 단순 문구·색·간격 수정에는 전체 절차를 적용하지 않는다.
실행되지 않은 접근성 환경을 인증하거나, 에이전트의 관찰을 실제 사용자 연구로 보고하지 않는다.
같은 원인의 발견 사항을 모듈마다 중복 집계하지 않고 필요한 근거만 연결한다.

## 1. 목표와 완료 의미를 고정한다

요구사항과 현재 자료에서 사용자 목표, 대상, 시작 조건, 완료 근거를 한 문장씩 정한다.
목표는 버튼 누르기나 요청 보내기가 아니라 사용자가 얻으려는 결과다.
수신 확인, 로컬 반영, 서버 저장, 후속 처리, 외부 공개 중 어떤 사건이 완료인지 구분한다.
현재 구현을 자동으로 정답 삼지 않는다. 관찰한 사실과 합의된 동작, 제안하는 동작을 나눈다.

- 트리거: 수동 행동인가 자동 사건인가? 어떤 맥락에서 시작하며 무엇이 미리 보여야 하는가?
- 규칙: 행동이 무엇에 적용되고 언제 허용되며 진행 중 어떤 통제가 가능한가?
- 피드백: 사용자가 알아야 할 사실은 무엇이고, 아직 주장할 수 없는 것은 무엇인가?
- 반복: 갱신·알림·표시·장기 기억은 언제 다시 발생하고 언제 멈추는가?
- 모드: 같은 입력의 의미가 달라지는가? 현재 모드와 원래 작업으로 돌아가는 방법은 무엇인가?

진입 전에 필요한 대상·현재값·진행 정보를 기존 트리거에 표시할 수 있는지 검토한다.
중요한 행동이나 정보의 유일한 경로를 hover·숨은 제스처·소리로 만들지 않는다.
빈도가 낮더라도 위험한 취소·복구·권한 관련 행동의 발견성을 무조건 낮추지 않는다.

## 2. 상황에 따라 피드백을 결정한다

아래 표는 선택 규칙이다. 해당 작업에 존재하는 행만 계약에 포함한다.

| 상황·판단 근거 | 표시와 통제 결정 | 금지할 오해 |
| --- | --- | --- |
| 최초 진입, 아직 표시할 데이터 없음 | 필요한 영역의 로딩과 기다리는 대상을 알린다 | 조회 전을 빈 결과·미작성으로 단정 |
| 기존 데이터의 백그라운드 재검증 | 유효한 기존 내용을 유지하고 필요할 때 갱신 중·최신성 한계를 표시한다 | 매번 전체 화면을 지우거나 모든 갱신을 알림 |
| 사용자가 저장·생성·업로드 시작 | 즉시 수신을 확인하고 작업 대상·진행·가능한 중단을 표시한다 | 수신 확인을 저장·전체 완료로 표현 |
| 진행량을 신뢰할 수 있음 | 완료 단위·전체 범위를 일치시켜 진행량을 표시한다 | 파일 전송 완료를 후속 처리 완료로 표시 |
| 진행량·종료 시각을 모름 | 진행 중인 단계와 가능한 다음 행동을 설명한다 | 근거 없는 백분율·남은 시간 |
| 자동 갱신 실패, 기존 내용은 유효 | 기존 내용과 갱신 실패를 구분하고 필요한 조치를 붙인다 | 정상 데이터까지 사라짐·최신인 척함 |
| 서버가 해당 작업을 확정 | 확정된 범위의 완료를 알리고 이전 대기 표시를 끝낸다 | 아직 처리 중인 다른 작업까지 성공 주장 |
| 결과를 확인할 수 없음 | 미확정 상태와 결과 확인 경로를 제공한다 | timeout만으로 실패·미실행 확정 |
| 일부 대상만 성공 | 성공·실패·미확정 범위와 후속 행동을 구분한다 | 전체 성공 토스트·성공분까지 재실행 유도 |
| 사용자의 수정이 필요한 실패 | 수정 위치·보존된 입력·복구 행동을 연결한다 | 사라지는 토스트만 남기거나 원인 없는 재시도 |

구체적인 전환에는 다음 계약을 채운다. 작은 변경에 전 화면 문서를 강제하지 않는다.

| 사건·대상 | 확인된 사실·메시지 | 위치·채널 | 시작·지속·종료 조건 | 가능한 행동·다음 전환 |
| --- | --- | --- | --- | --- |
| 편집한 항목 저장 요청 시작 | 해당 변경을 저장 중 | 저장 제어 근처 상태와 필요한 상태 알림 | 수신 직후 시작, 확정·실패·미확정으로 교체 | 입력·이탈·취소는 제품 정책대로 |
| 해당 변경 저장 확정 | 확인된 변경이 저장됨 | 지속 상태, 필요할 때 짧은 확인 | 저장 근거 뒤 표시, 새 편집 시 이전 완료와 구분 | 후속 행동은 충족된 조건만 활성화 |

## 3. 성공·복구·취소의 의미를 보존한다

낙관적 UI는 확정 전의 예상 표시다. 빠르게 반영하더라도 확정된 저장과 혼동시키지 않는다.
거절이 확인되면 되돌릴 범위와 보존할 새 편집을 구분하여 실패·복구를 알린다.
결과 미확정이면 무조건 rollback하거나 성공 처리하지 말고 제품의 확인·조정 경로를 따른다.
다음 항목은 사용자에게 전달할 계약을 정하기 위한 질문이며 구현 검사 목록을 대신하지 않는다.

- 어떤 작업·대상·변경분에 대한 확인인가? 이전 작업 완료가 현재 편집까지 저장된 것처럼 보이는가?
- 낙관적 표시를 되돌릴 때 후속 편집·다른 성공 결과까지 지우는가? 보존 정책을 설명할 수 있는가?
- 일부 실패 후 사용자가 다시 할 범위와 이미 완료된 범위를 구별할 수 있는가?
- “취소”는 대기 화면 닫기인가, 아직 시작 전 철회인가, 실행 중 작업 중단 요청인가?
- 취소 요청의 수신과 실제 중단 완료를 구분하는가? 늦게 확정된 결과도 정직하게 알리는가?
- “되돌리기”는 실제 복원인가 별도 보상 작업인가? 대상·기한·권한·복구 불가 범위가 명확한가?
- 복구 행동 자체가 실패하거나 결과 미확정이면 원래 결과와 복구 상태를 구별하는가?

안전한 재시도나 실제 중단 보장을 알 수 없으면 관련 구현 계약의 확인이 필요하다고 남긴다.
재시도 횟수·멱등 키·abort 방식은 여기서 새로 강제하지 않는다. 버튼 비활성화는 보장의 증거가 아니다.
오류 안내에는 원인과 가능한 행동을 연결하되 사용자 비난·농담으로 심각성이나 해결법을 가리지 않는다.

## 4. 채널과 표시 수명을 정한다

각 피드백의 메시지를 먼저 정하고 위치·채널·강도·지속·반복·종료를 선택한다.
가능하면 기존 제어나 상태 영역을 활용한다. 모든 내부 사건을 토스트나 modal로 만들지 않는다.

- 수동 행동의 수신 확인은 입력 지점과 가깝게 둔다. 별도 위치라면 발견·인지 경로를 검증한다.
- 완료 토스트가 사라져도 중요한 저장·처리 결과를 다시 확인할 수 있게 한다.
- 오류·미확정·복구 수단을 읽거나 실행하기 전에 자동 소멸시키지 않는다.
- 소리·진동은 보지 않는 상황에서도 알려야 할 필요를 따져 사용하고 적절한 제어를 제공한다.
- 색·움직임·소리·진동 하나만으로 필수 상태를 전달하지 않는다. 텍스트·형태·의미 구조를 함께 쓴다.
- 보조기술의 상태 알림과 포커스 이동을 구분한다. 매 갱신마다 긴급 알림이나 포커스 강탈을 하지 않는다.
- 필수 정보는 키보드로 접근 가능하게 하고 제어의 이름·역할·현재값과 표시 의미를 맞춘다.
- 여러 작업의 알림이 경쟁하면 묶기·중요도·노출 위치를 조정하되 개별 실패를 숨기지 않는다.

## 5. 모션·반복·모드를 연결한다

모션마다 설명하는 관계·변화·위치를 적는다. 정보나 과업에 기여하지 않는 연출은 줄인다.
시각적 완료 연출이 데이터 완료를 결정하거나 다음 행동을 불필요하게 기다리게 하지 않는다.

- 빠른 연속 입력·취소·대상 전환에서 오래된 모션이 현재 상태를 거짓으로 설명하지 않는지 본다.
- reduced motion에서는 이동·반복·확대를 줄이거나 대체하고 동일한 의미와 행동을 유지한다.
- 모션을 없앴을 때 완료 이벤트·포커스·다음 행동이 누락되지 않게 한다.
- 기본 경로도 과도한 움직임·깜박임을 피한다. reduced motion 지원만으로 안전성을 단정하지 않는다.
- 화면 효과 반복, 작업 재확인, 알림 반복, 장기 기억을 다른 수명으로 취급한다.
- 각 반복의 시작·중지·다시 시작 조건과 이탈 후 표시 정책을 정한다. 실패를 무한 활동 표시로 숨기지 않는다.
- 장기 기억은 다음 과업에 필요한 정보만 대상으로 삼고 계정·공유 기기·보존·삭제 정책을 따른다.
- 사용 빈도만으로 숙련도를 단정하여 주요 라벨·복구 행동을 없애지 않는다. 오랜만의 복귀도 검토한다.

처리 중 상태와 모드를 혼동하지 않는다. 모드는 같은 입력의 의미를 바꾸는 규칙의 분기다.
모드가 필요하면 진입·현재 표시·종료·취소와 복귀할 대상·초안·선택·포커스를 정한다.
길게 누르기·제스처만으로 중요한 모드에 진입하게 하지 말고 가능한 동등 조작을 마련한다.
권한 부족을 편집 모드 종료나 저장 완료처럼 표현하지 않는다. 권한·기능 정책을 임의로 바꾸지 않는다.
인접 단계로 넘길 때 대상·완료 의미·문맥을 유지하고 중복 알림·모드 충돌을 확인한다.

## 6. 시간과 수치는 맥락에서 결정한다

지연 임계값, 노출 시간, ETA, 반복 간격, 되돌리기 기한에 보편적인 고정값을 적용하지 않는다.
과업 위험, 예상 지연과 변동, 사용자 읽기·조작 시간, 기기·입력 방식, 제품 정책을 근거로 정한다.
아주 짧은 작업의 불필요한 깜박임은 피하되, 수신 확인을 생략하여 중복 행동을 유도하지 않는다.
미관상 완료 표시를 빨리 지우거나, 연출을 위해 실제 완료를 늦추지 않는다.
수치가 미정이면 검증할 가정으로 기록한다. 추정 ETA에는 불확실성을 반영하고 신뢰할 수 없으면 다른 설명을 쓴다.

## 7. 전환을 검증하고 근거대로 보고한다

변경 위험에 맞는 시나리오만 고른다. 기존 상태·행동 테스트의 증거를 먼저 재사용한다.
정적 화면은 문구·배치의 증거이지 표시 시점·수명·저장·복구 성공의 증거가 아니다.

1. 시작 조건과 기대 메시지, 표시·종료 사건, 가능한 행동을 먼저 고정한다.
2. 필요한 경우 응답·시간을 통제하여 처리 중 표시를 관찰한다. 임의 대기로 상태를 추정하지 않는다.
3. 확정·거절·미확정·일부 실패 중 관련 경계를 확인하고 화면 주장과 실제 결과 근거를 연결한다.
4. 취소·복구·급속 반복·모드 복귀에서 이전 표시가 남거나 새 의미를 가리지 않는지 확인한다.
5. 모션 기본·reduced motion, 키보드·보조기술·소리 꺼짐 중 관련 조건을 실제 가능한 범위에서 확인한다.
6. 테스트용 보류·자원·데이터를 정리한다. 재시도 성공으로 최초 실패 증거를 지우지 않는다.

장기 기억의 시간 제어 검사는 전환 논리를 보여줄 뿐 실제 사용자의 장기 학습을 입증하지 않는다.
이해도·만족·알림 피로는 실제 사용자 관찰이 필요하다. 표본 수·클릭 수만으로 효과를 단정하지 않는다.

결과는 **전환·조건 → 기대 의미 → 관찰 근거 → 사용자 영향 → 최소 수정 → 검증 상태**로 전달한다.
검증 상태는 통과·실패·미검증·해당 없음으로 나누고, 미검증 이유와 필요한 다음 증거를 적는다.
제품 규칙의 미결정, 코드상 추론, 화면 관찰, 실제 사용자 결과를 서로 다른 근거로 표시한다.
구현·테스트·배포를 구분하며 실제 확인한 범위에서만 완료를 선언한다.
