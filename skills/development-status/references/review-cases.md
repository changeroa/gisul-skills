# 판단 사례

모두 가상의 사례다. 실제 프로젝트 성과로 인용하지 않는다. 애매한 상태를 해석하거나 스킬을 수정할 때 필요한 사례만 사용한다. 문구 일치보다 판단과 근거 범위가 맞는지 확인한다.

## 병합, 배포, 사용 가능성이 다를 때

자료: 저장 기능 PR 병합, 해당 커밋의 통합 테스트 성공, 스테이징 배포 성공. 운영 환경은 이전 버전.
판단: 구현·해당 통합 테스트·스테이징 반영은 확인됐다. 운영 사용 가능으로 보고하면 안 된다.
공유 예: “저장 기능 구현과 통합 검증을 마쳤고 스테이징에 반영했습니다. 운영 반영은 남아 있습니다.”

추가 자료: 운영 배포 성공, 기능 플래그는 내부 계정에만 활성화.
판단: 운영 배포와 내부 계정 이용 가능 범위를 구분한다. 전체 고객 출시로 확대하지 않는다.

## 할 일이 줄었지만 핵심 문제는 미해결일 때

자료: 작업 10개 중 8개 완료. 외부 결제 API의 중복 결제 방지 방식은 조사 중.
판단: 80%나 출시 임박을 주장하지 않는다. 해결된 기능과 핵심 불확실성을 구별한다.
공유 예: “기본 결제 화면은 구현했습니다. 중복 요청 처리 방식을 확인 중이며, 해결 후 남은 작업과 출시 전망을 갱신할 수 있습니다.”
추가 자료가 없으면 조사 담당·완료일을 만들지 않는다.

## 코드 변화 없이 불확실성이 줄었을 때

자료: 외부 API 실험 기록에서 필요한 기능이 지원되지 않음이 확인됨. 대체 방식은 아직 미결정.
판단: 중요한 제약을 확인한 진척과 새 결정을 함께 보고한다. 구현 완료나 정체로 분류하지 않는다.
결정 요청에는 대체 방식 검토가 필요한 이유와 영향을 연결한다.

## 기록이 충돌하거나 누락됐을 때

자료: 이슈는 완료, 최신 인수인계에는 저장 실패 시 입력이 사라지는 문제 미해결. 저장소 연결은 접근 실패.
판단: 이슈 완료를 기능 전체 완료로 확대하지 않는다. 인수인계의 미해결 범위와 확인 시점, 저장소 미확인을 명시한다.
저장소 접근 실패나 최근 커밋 부재만으로 미착수·중단·담당자 지연을 주장하지 않는다.

## 계획과 제안을 구분해야 할 때

자료: 댓글 “금요일까지 가능할 듯”, 이후 외부 승인 대기 기록. 승인 담당과 확정 기한은 없음.
판단: 금요일을 확정 약속으로 쓰거나 지연을 단정하지 않는다. 기존 추정과 현재 의존성, 일정 재판단 조건을 설명한다.
새로운 담당이나 의무적인 승인 단계를 만들지 않는다.

## 완료 후 회귀, 비교 기준, 공유 여부

자료: 지난 공유에 운영 배포 완료. 이후 배포는 롤백됐고 현재 이전 버전이 서비스 중.
판단: 현재 기능 이용 상태를 바로잡고 이전 공유 대비 변화를 설명한다. 과거 배포 사실만 반복하지 않는다.

자료: 이번 공유 초안은 작성했으나 전송 실패.
판단: 공유 완료로 처리하거나 마지막 성공 공유 기준점을 이동하지 않는다. 재전송 전 실제 게시 여부를 확인한다.

자료: 같은 기능을 다룬 세 PR 중 둘은 이전 공유에 포함됐고 하나만 새 변경.
판단: 새 변경을 중심으로 기능 단위로 묶는다. 세 기능 완료처럼 집계하지 않는다.
