# Development Status

개발자의 설명 부담을 줄이면서 팀이 다음 행동을 판단할 수 있는 현황을 만든다. **기능·사용자 변화 → 확인한 진척 → 남은 불확실성과 작업 → 영향 → 필요한 결정·다음 행동**으로 연결한다.

Ryan Singer의 《Shape Up》을 중심으로 Scott Berkun의 《Making Things Happen》에서 진척, 우선순위, 의존성에 관한 관점을 가져온다. 아래 상태 분류와 수집·공유 절차는 이 스킬의 적용 규칙이며 저자의 공식 보고 양식이 아니다. 출처와 적용 한계가 필요하면 [sources.md](references/sources.md)를 읽는다.

## 범위와 기준점

- 대상 프로젝트, 공유 대상, 기간, 현재 목표와 이전 공유를 대화와 기존 기록에서 찾는다. 이미 정해진 정책·범위·담당·일정을 보존한다.
- 기간이 없으면 확인 가능한 마지막 공유 이후를 우선한다. 이전 공유도 없으면 조회한 기간을 밝히고 현재 현황으로 작성한다. 과거 전체를 이번 기간의 성과로 집계하지 않는다.
- 대상 독자가 명시되지 않으면 함께 일하는 비개발 직군도 이해할 수 있는 팀 내부 초안으로 작성한다. 외부 고객용 문구나 출시 약속으로 바꾸지 않는다.
- 자료를 먼저 확인한다. 개발자에게 작업 목록을 다시 작성하게 하지 않는다. 결론을 바꾸는 미확인 사항만 짧게 묻고, 답이 없어도 확인된 범위의 초안은 작성한다.
- 대상 자체를 식별할 수 없거나 자료 접근이 전혀 없으면 필요한 프로젝트나 자료 위치만 요청한다. 접근 실패를 미착수·지연으로 해석하지 않는다.

## 1. 개발 흔적을 근거로 모은다

설정된 API와 연결을 우선하고, 작업 환경의 도구·스킬 지침을 따른다. 필요한 기간과 프로젝트로 한정하여 다음 중 관련 자료를 확인한다.

- 현재 요구사항·결정 기록과 이슈: 합의한 결과, 범위, 의존성, 일정과 담당.
- 작업·인수인계 기록, PR 설명과 토론, 변경 내역: 의도, 실제 변경, 남은 문제.
- 관련 테스트·검증 기록: 어떤 버전·조건·흐름을 확인했는지.
- 배포·릴리스·환경 기록: 어떤 변경이 어느 환경에 반영됐는지.
- 이전 공유와 이후 변경: 새 진척, 해결된 장애물, 재발·회귀, 변경된 계획.

자료마다 링크나 정확한 위치, 관련 시점, 브랜치·커밋·환경 등 결론에 필요한 식별자를 남긴다. 커밋 제목만으로 기능 완료를 판단하지 않는다. 제목으로 알 수 없는 중요한 부분만 상세 기록이나 소스를 추적한다. 현황 작성 때문에 전체 코드 감사, 빌드, E2E를 새로 수행하지 않는다.

로컬 미커밋 변경도 진행 근거가 될 수 있지만 저장·공유·배포된 변경과 구별한다. 다른 작업자의 파일, 브랜치, 이슈 상태를 현황 작성 목적으로 변경하지 않는다.

**주장에 맞는 근거를 선택한다.** 이슈의 완료 표시는 계획 관리 상태이고, 테스트는 해당 버전의 해당 조건에 대한 증거이며, 배포 기록은 환경 반영의 증거다. 최신 메시지 하나로 기존 합의나 다른 종류의 증거를 덮어쓰지 않는다. 기록이 충돌하면 내용과 시점을 비교하고 해결되지 않은 차이를 밝힌다.

## 2. 기능별로 진척과 불확실성을 해석한다

사용자에게 의미 있는 기능이나 독립적으로 완료 가능한 범위로 묶는다. 같은 기능의 여러 커밋·PR을 중복 집계하지 않는다. 너무 큰 묶음 안에서 상태가 다르면 나눈다.

각 범위에서 다음을 판단한다.

1. **해결된 것:** 어떤 문제의 해결 방법이나 결과를 근거로 확인했는가?
2. **아직 모르는 것:** 정책, 기술 가능성, 외부 의존성, 실제 동작 중 무엇이 미확정인가?
3. **남은 실행:** 방법은 정해졌지만 구현·검증·배포 등 어떤 작업이 남았는가?
4. **이전 대비 변화:** 불확실성이 줄었는가, 실제 사용 범위가 늘었는가, 새 문제가 생겼는가?

작업 개수, 코드량, 소요 시간으로 진척률을 만들지 않는다. 어려운 문제를 해결한 조사·실험도 진척일 수 있다. 반대로 코드가 많거나 테스트가 통과했다는 사실만으로 남은 불확실성이 없다고 단정하지 않는다. 작업자의 명시적 기록 없이 Hill Chart의 위치나 확신 정도를 수치화하지 않는다.

공유할 때는 필요한 상태만 사용한다. 아래 상태는 하나의 강제 순서가 아니며 같은 기능의 서로 다른 부분·환경에 함께 적용될 수 있다.

| 표현 | 필요한 근거와 제한 |
| --- | --- |
| 방향·조건 확인 중 | 해결 방법이나 정책 등 미확정 항목이 실제 기록에 있음 |
| 구현 중 | 관련 변경이나 작업 기록이 있으나 합의 범위 완료 근거는 부족함 |
| 구현 완료 | 해당 범위의 변경이 완료됐다는 근거가 있음. 병합·검증·배포 여부는 별도 표시 |
| 검증 완료 | 관련 버전과 조건에서 검증 결과가 있음. 확인하지 않은 흐름까지 확대하지 않음 |
| 배포 완료 | 대상 환경에 해당 변경이 반영됐다는 근거가 있음. 실제 사용 가능 여부는 권한·플래그·출시 조건도 확인 |
| 확인 필요 | 관련 근거에 접근하지 못했거나 기록이 충돌함 |

실패·롤백·회귀가 확인되면 현재 상태를 갱신한다. 과거 완료 기록만으로 현재도 사용 가능하다고 쓰지 않는다. 구현·검증·배포는 구별하고, 단독으로 “완료”라고 쓰려면 무엇의 완료인지 설명한다.

## 3. 팀이 알아야 할 영향과 행동을 연결한다

- **변화:** 내부 용어를 사용자의 행동이나 운영상 효과로 풀어쓴다. 확인하지 않은 성능 향상·사업 성과는 만들지 않는다. 내부 개선은 후속 개발, 안정성, 운영 등 관련 영향이 있을 때 설명한다.
- **장애물:** 실제로 멈춘 작업, 기다리는 조건, 영향을 받는 기능과 병행 가능한 작업을 구분한다. 잠재 위험을 현재 차단으로 쓰지 않는다. 기록이 없거나 한동안 커밋이 없다는 이유로 정체를 단정하지 않는다.
- **일정·범위:** 확정 일정과 추정·희망·후보를 구분한다. 지연은 기존 약속과 현재 근거가 있을 때만 판단한다. 영향 계산이 불가능하면 언제 또는 어떤 확인 후 판단할 수 있는지 쓴다.
- **결정 필요:** 무엇을 결정해야 하는지, 왜 지금 필요한지, 선택에 따른 영향을 적는다. 추천이 가능하면 근거와 함께 제시하되 확정 정책으로 쓰지 않는다.
- **다음 행동:** 기존 합의에서 확인한 행동과 새 제안을 구분한다. 담당·기한은 확인됐을 때만 명시하고 임의로 배정하거나 약속하지 않는다.

중요한 위험·결정은 성과 목록에 묻히지 않게 앞에 둔다. 동일한 장애물이 여러 기능에 영향을 주면 하나로 묶고 영향 범위를 적는다. 담당자를 평가하거나 작업 속도로 개인의 생산성을 평가하지 않는다.

## 4. 짧은 공유문과 추적 가능한 근거를 만든다

사용자의 언어와 기존 팀 형식을 우선한다. 기본은 한눈에 읽히는 짧은 본문이며, 상세 근거는 관련 항목의 링크나 별도 짧은 표로 연결한다. 작업이 작으면 한 문단으로 충분하다. 빈 섹션이나 모든 항목의 반복 필드를 강요하지 않는다.

```markdown
[프로젝트 · 대상 기간 · 기준 시점]

현재 판단: 가장 중요한 변화나 위험을 1~2문장으로 설명.

- [기능/사용자 변화] 확인된 진척과 사용 가능한 범위. 남은 작업·불확실성. [근거]
- [다른 기능] 이전 공유 이후 달라진 점. [근거]

결정·지원 필요: 필요한 결정, 영향, 확인된 담당·기한 또는 다음 확인 조건.
다음 작업: 합의된 다음 행동. 제안은 제안으로 표시.
확인 범위: 중요한 미확인 환경·자료·상태만 짧게 명시.
```

달라진 점이 없으면 확인한 범위에서 새 변화가 없다고 말한다. 지속되는 중요한 위험은 마지막 확인 시점과 함께 유지하되, 다시 조사하지 않은 항목을 최신 확인처럼 쓰지 않는다.

본문을 쓰기 전에 다음을 점검한다.

- 독자가 개발 배경 없이 무엇이 달라졌고 무엇을 해야 하는지 알 수 있는가?
- 구현, 검증, 배포, 사용자 이용 가능성을 혼동하지 않았는가?
- 핵심 주장과 일정·담당·결정이 근거에 연결되는가?
- 누락된 기록을 미진행으로, 추정을 확정으로 바꾸지 않았는가?
- 이전 공유의 단순 반복과 중복 집계를 줄였는가?

애매한 사례를 판단하거나 이 스킬을 수정·검증할 때 [review-cases.md](references/review-cases.md)를 읽는다.

## 5. 공유와 기록을 마무리한다

작성 요청이면 공유 가능한 초안을 제공한다. 외부 메시지 전송, 이슈 수정, 자동 알림 설정은 해당 행동에 대한 사용자 요청·기존 권한 범위에서만 수행한다. 이미 허가된 전송을 다시 승인받도록 강제하지 않는다.

실제 전송 시 대상·채널·공개 범위에 맞게 내부 정보와 상세 링크를 선별하고, 전송 결과를 확인한다. 응답이 불명확하면 전송 기록을 먼저 확인하여 중복 발송을 피한다. 초안 작성이나 실패한 전송을 “공유 완료”로 기록하지 않는다.

지속 공유가 요청된 경우 기존 기록 위치에 기준 시점, 사용한 주요 근거, 공유문 위치, 미결정 사항을 짧게 남겨 다음 비교에 사용한다. 새 문서 체계·반복 작업·모니터링을 자동으로 만들지 않는다.

## 관련 스킬의 사용 범위

`dont-make-me-think`와 `ux-state-review`의 기존 결과가 있으면 확인 범위에 맞는 증거로 사용한다. 실제 화면 이해나 상태별 완료 여부가 쟁점이고 추가 검토가 요청·필요한 경우에만 해당 스킬을 별도로 로드한다. 현황 공유만을 위해 자동으로 시각 QA나 전체 상태 테스트를 수행하지 않는다.
