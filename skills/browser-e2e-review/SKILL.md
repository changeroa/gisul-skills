# 브라우저 E2E 검증

작업을 끝냈다는 사실과 과정의 UI가 올바르다는 사실을 구분한다. 요구사항에서 정한 기대 상태, 실제 화면, 요청·저장 결과를 연결해 판정한다. 사용자에게 설명할 때는 익숙한 말로 원인과 필요한 조치를 풀어 쓰고, 전문 용어는 필요한 경우에만 뜻을 덧붙인다.

## 적용 범위와 도구

- 요청받은 흐름과 변경의 영향을 받는 상태를 우선한다. 작은 수정에 전체 서비스 검사를 강제하지 않는다.
- 브라우저 조작은 해당 환경의 지침과 사용자가 지정한 도구를 따른다. aside-browser 사용이 요구되면 그 스킬을 별도로 로드하고 현재 안내를 읽는다. 이 스킬 자체는 특정 브라우저 도구나 설치·실행 권한을 제공하지 않는다.
- 기존 테스트·응답 제어 장치·실행 기록을 먼저 재사용한다. 도구가 지원하지 않는 모바일 화면, 네트워크 제어, 화면 비교 등을 실행했다고 추정하지 않는다.
- 테스트 설계 요청에서는 기준과 시나리오를 작성한다. 실행 요청에서는 실제 증거를 수집한다. 보강 요청에서는 누락된 검사와 필요한 최소 재현 장치를 추가한다. 문서나 테스트 코드만 작성했으면 브라우저 검증 완료로 보고하지 않는다.

## 1. 실행 전에 정상 기준을 정한다

대상 행동마다 아래를 간결하게 기록한다.

| 항목 | 정할 내용 |
| --- | --- |
| 시작 조건 | 사용자 권한, 준비 데이터, 화면, 기존 저장값 |
| 행동과 사건 | 클릭·입력, 응답 도착, 실패, 재접속 |
| 처리 중 | 보여야 할 안내, 잠겨야 할 행동, 유지할 입력·선택 |
| 완료 후 | 성공·실패·결과 미확정별 표시와 다음 행동 |
| 제거할 상태 | 사라져야 할 이전 폼, 로딩, 오류, 완료 안내 |
| 결과 근거 | 저장값, 요청 수·대상, 화면과 이를 연결할 기록 |

기대값은 요구사항과 합의된 제품 동작에서 가져온다. 현재 구현이나 방금 찍은 화면을 그대로 정답으로 삼지 않는다. 제품 규칙이 불명확하면 그 부분은 판정을 보류하고, 독립적으로 확인 가능한 검사는 계속한다. 임의로 새 규칙을 정해 결함으로 확정하지 않는다.

서로 관련된 값의 일관성도 검사한다. 예를 들어 선택 수량, 병원별 수량, 생성 버튼 문구가 같은 개념을 나타내면 서로 맞아야 한다. 선택 수량과 현재 처리 가능한 수량이 다른 개념이면 이를 구분하는 문구를 검사한다. 특정 제품의 숫자나 표시 규칙을 다른 제품에 고정 적용하지 않는다.

## 2. 전환을 관찰한 뒤 다음 행동으로 진행한다

중요한 행동 뒤에는 현재 화면을 새로 읽는다. 이전 화면의 좌표·요소 참조가 계속 유효하다고 가정하지 않는다. 여러 행동을 묶더라도 검증해야 할 상태 경계를 건너뛰지 않는다.

처리 중 상태가 중요한 흐름에서는 다음 순서로 확인한다.

1. 대상 요청의 응답을 보류하도록 준비한다.
2. 실제 UI에서 행동한다.
3. 요청이 도착하고 해당 상태에 진입했는지 확인한다.
4. 처리 중 문구·잠금·입력 보존·수량·화면 배치를 검사한다.
5. 응답을 해제하고 다음 상태를 확인한다.

고정 시간 대기로 타이밍을 추측하지 않는다. 검사 대상 상태가 되었다는 조건으로 기다린다. 렌더링이 안정된 것과 저장·생성이 완료된 것을 구분한다. 응답 제어가 없다면 실제로 관찰한 범위만 판정하고 중간 상태는 미검증으로 남긴다.

실패·복구는 관련 위험에 맞춰 선택한다. 저장 전 거절, 저장 성공 후 응답 유실, 오래된 응답의 늦은 도착, 일부 대상만 실패한 경우를 구분한다. 응답 유실을 재현할 때는 저장 성공 근거도 확인한다. 성공 후 재조회·재접속이 중요한 흐름에서는 저장된 결과가 유지되는지 확인한다.

보류 요청을 해제하고 자신이 만든 테스트 서버·탭·데이터를 정리한다. 다른 작업의 자원을 종료하지 않는다.

## 3. 세 종류의 근거를 함께 확인한다

- **문구와 상태:** 제목, 수량, 선택값, 버튼 활성 여부, 입력 보존, 포커스, 이전 안내의 제거를 명시적으로 검사한다.
- **실제 화면:** 현재 viewport에서 가림·잘림·화면 밖 배치·팝오버·오류 후 다음 버튼을 확인한다. 페이지 전체 이미지나 DOM에 요소가 있다는 사실만으로 사용자가 볼 수 있다고 판정하지 않는다.
- **동작과 저장 결과:** 실제 다음 행동을 수행하고 요청 대상·횟수·저장값을 확인한다. 성공 안내만으로 저장 성공을 단정하지 않는다.

일반 클릭과 키보드 조작을 우선한다. 강제 클릭, 스크립트로 직접 발생시킨 이벤트, API 대체로 사용자 경로를 통과 처리하지 않는다. 진단용 우회가 필요하면 원래 경로의 결과와 분리해서 기록한다.

자동 반복 검사는 명시적 assertion(기대값을 확인하는 검사), 접근성 구조 비교, 화면 이미지 비교를 필요한 범위에 조합한다. 한 종류의 통과가 다른 종류의 검사를 대신하지 않는다. 도구의 visible 판정이 실제 시각적 노출을 보장하는지도 확인한다.

## 4. 화면 변화를 비교 가능한 상태로 남긴다

두 비교를 구분한다.

- 같은 실행의 행동 전·처리 중·행동 후 비교: 필요한 상태 전환이 일어났는지 확인한다.
- 이전에 정상으로 검토한 화면과 현재 실행의 같은 상태 비교: 코드 변경으로 의도하지 않은 표시·배치 변화가 생겼는지 확인한다.

이미지 비교에서는 브라우저·OS·폰트·viewport·화면 배율·언어·시간·테스트 데이터를 가능한 범위에서 일정하게 유지하고 차이가 나는 조건을 기록한다. 모바일과 키보드는 실제 실행한 조건만 결과에 포함한다. 모바일 크기 검사가 실제 기기의 키보드·터치 동작까지 증명하지는 않는다.

주요 화면 전체와 수량·CTA·팝오버 등 중요한 영역을 상황에 맞게 비교한다. 핵심 문구·버튼을 가리거나 허용 오차를 넓혀 결함을 숨기지 않는다. 변동 영역을 제외할 때는 이유를 남긴다.

기준 이미지가 없으면 먼저 기준 후보를 만든다. 그것만으로 회귀 검사가 통과했다고 보고하지 않는다. 예상하지 못한 차이를 없애려고 기준 이미지를 자동 갱신하지 않는다. 갱신은 의도한 변경과 diff를 검토한 뒤 프로젝트의 기존 승인 절차에 맞춰 수행한다. 스킬 자체로 매번 별도 사용자 승인을 추가하지 않는다.

## 5. 실패를 보존하고 근거로 판정한다

각 필수 확인 항목은 통과·실패·미검증·해당 없음 중 하나로 남긴다. 미검증에는 이유, 해당 없음에는 적용되지 않는 근거를 적는다.

- 통과에는 실제 관찰값과 증거가 필요하다.
- 필수 항목에 실패가 있으면 시나리오는 실패다.
- 실패가 없더라도 필수 항목이 미검증이면 전체 통과로 올리지 않는다.
- 자동 테스트 통과와 실제 브라우저 결과는 별도로 기록한다.
- 재시도 성공은 첫 실패를 지우지 않는다. 새로고침·재로그인·대체 경로로 복구했으면 각각의 결과를 남긴다.
- 예상하지 못한 UI 변화에 맞춰 locator나 기대값을 바꾸기 전에, 같은 대상·동작·결과인지 확인한다. 테스트를 녹색으로 만들기 위한 기준 완화를 하지 않는다.

시나리오·상태·viewport·소스 버전에 기대값, 관찰값, 이미지, 요청 기록을 연결한다. 기존 기록 형식을 사용하되 필수 근거 누락을 탐지할 수 있게 한다. 대화의 기억만으로 결과를 재구성하지 않는다. 민감한 값은 필요한 범위에서 제거한다.

최초 실패를 조사할 수 있도록 행동 전후 화면과 요청 기록을 보존한다. 재시도에서만 수집한 기록을 최초 실패의 증거로 제시하지 않는다. 최종 보고에는 확인한 범위, 발견한 문제, 미검증 범위와 이유를 구분한다.

## 6. 보강할 때는 검사가 결함을 잡는지도 확인한다

새 검사 체계를 만들거나 반복 누락을 보강할 때, 관련된 작은 결함을 격리된 테스트 환경에 의도적으로 넣어 검사가 실패하는지 확인한다. 매번 전체 E2E 실행에 강제하지 않는다.

예: 수량 불일치, 보이지 않는 버튼, 화면 밖 팝오버, 처리 중 중복 요청, 성공 후 남는 오류 안내, 늦은 응답에 의한 선택 덮어쓰기.

각 결함은 이를 잡아야 할 검사에서 올바른 이유로 실패해야 한다. 무관한 서버 오류나 시간 초과만으로 탐지 성공이라고 하지 않는다. 복구 후 정상 실행도 확인한다. 정상 실행·결함 실행·복구 실행의 결과를 구분하고 운영 시스템에 결함을 주입하지 않는다.
