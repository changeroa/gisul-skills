# Don't Make Me Think · UI QA

사용자가 화면을 이해하고 다음 행동을 선택하는 데 드는 불필요한 생각을 찾는다. 각 지적은 **화면의 단서 → 사용자가 해결해야 하는 의문 → 과업 영향 → 구체적인 수정 → 확인 조건**으로 연결한다.

Steve Krug의 책에서 다루는 명확성, 훑어보기, 선택, 문구, 내비게이션을 실무 점검에 적용한다. 아래 절차와 심각도는 이 스킬의 운영 기준이며 저자가 만든 공식 평가표가 아니다. 출처를 설명하거나 실제 사용자 테스트를 설계할 때 [근거와 사용자 테스트](references/sources-and-testing.md)를 읽는다.

## 범위와 입력

- 사용자 목표, 대상 화면, 사용자 유형, 기기를 대화에서 파악한다. 빠진 정보가 진행을 막지 않으면 가정을 한 줄 적고 진행한다. URL이나 화면 자료가 전혀 없으면 대상만 요청한다.
- 기본 단위는 사용자의 과업이다. 예: “기존 예약의 날짜를 바꾸고 결과를 확인한다.” 메뉴를 전부 열어보는 일을 과업으로 삼지 않는다. 범위가 넓으면 대표 과업부터 보되 요청된 화면이나 흐름은 누락하지 않는다.
- 리뷰 요청에는 발견 사항과 수정 제안을 제공한다. 구현까지 요청받았다면 승인된 범위에서 수정하고 같은 조건으로 재점검한다. 리뷰 자체를 코드 변경이나 외부 이슈 등록의 허가로 해석하지 않는다.
- 기존 제품의 사용자, 용어, 브랜드, 디자인 시스템을 존중한다. 전문 업무 도구에 필요한 밀도나 비교 정보를 단지 복잡해 보인다는 이유로 없애지 않는다.

| 입력 | 점검 범위 | 확인하지 못한 것으로 남길 것 |
| --- | --- | --- |
| 실제 URL 또는 실행 중인 앱 | 화면과 허용된 상호작용, 전후 상태 | 방문하지 않은 흐름·권한·기기 |
| 스크린샷 또는 정적 시안 | 보이는 문구, 배치, 계층, 시각적 상태 | 클릭 결과, 숨겨진 내용, 실제 포커스·저장 동작 |
| 코드만 있음 | 실행 가능한 화면 확보 또는 구현상 우려 제시 | 렌더링을 보기 전의 visual QA 통과 판정 |

## 화면과 흐름 관찰

브라우저 자동화와 웹 QA에는 **`aside-browser`의 현재 `SKILL.md`를 읽고 `aside guide`를 실행하여 그 지침을 따른다.** 목록에 없으면 로컬 스킬 경로를 검색한다. 설치·업데이트·로그인 문제는 해당 스킬의 절차로 처리한다. 접근이 막혀도 제공된 화면으로 가능한 점검은 계속하고 실행하지 못한 항목을 남긴다.

직접 스크린샷과 DOM을 조사해야 하는 작업이므로, Aside의 직접 검사 경로를 사용한다면 먼저 `aside guide repl`을 읽는다. 명령이나 API를 이 스킬에 고정해서 복제하지 않는다.

1. **처음 보이는 화면부터 본다.** 코드를 읽거나 숨겨진 DOM을 찾기 전에 화면을 보고 서비스/페이지의 목적, 현재 위치, 눈에 띄는 다음 행동을 기록한다. 개발자가 아는 기능을 사용자가 알아낼 수 있다고 가정하지 않는다.
2. **첫 선택을 기록한 뒤 조작한다.** 보이는 라벨과 시각적 단서로 예상한 결과를 적고 실제 결과와 비교한다. DOM에 존재하는 요소가 화면에서도 발견 가능하다는 결론을 내리지 않는다.
3. **과업을 따라간다.** 진입, 선택·입력, 완료 확인, 관련 오류·복구 상태를 본다. 검색·필터나 폼이 있으면 과업에 필요한 빈 결과·검증 오류 등을 포함한다. 실제로 재현하지 않은 상태는 추측으로 채우지 않는다.
4. **화면 조건을 남긴다.** URL/화면명, 역할, 데이터 상태, 뷰포트, 필요한 재현 순서를 기록한다. 반응형 웹이고 기기가 지정되지 않았다면 데스크톱과 좁은 모바일 폭을 대표값으로 확인한다. 예: 1440×900, 390×844 CSS px. 이 값은 책의 기준이나 모든 기기를 대표하는 인증값이 아니다.
5. **증거를 보관한다.** 발견 사항마다 실제로 본 스크린샷을 연결하고 위치를 설명한다. 첫 화면과 관련 부분을 구분하며 전체 페이지를 축소한 이미지 한 장만으로 글자 크기나 시인성을 판단하지 않는다. 기존 자료밖에 없으면 첨부 이미지 번호와 영역을 명시한다.

실서비스에서 게시·전송·결제·삭제처럼 외부 영향이 있는 조작은 기존에 허가된 범위까지만 수행한다. 안전한 테스트 데이터가 없으면 그 직전까지 관찰하고 완료 상태는 미검증으로 남긴다.

## 판단 기준

모든 기준을 억지로 문제로 만들지 않는다. 화면의 단서와 과업에 연결되는 항목만 보고한다.

| 관점 | 화면에서 확인할 것 | 수정 방향 |
| --- | --- | --- |
| 즉시 이해 | 제목·핵심 내용으로 무엇을 하는 곳인지, 어디서 시작하는지 알 수 있는가? | 구체적인 제목과 시작점을 드러내고 해독해야 하는 용어를 바꾼다. |
| 훑어보기 | 중요도와 시각적 강조가 맞는가? 제목, 그룹, 간격, 정렬로 관련 항목이 읽히는가? 장식이나 반복 강조가 과업을 가리는가? | 관련 정보를 묶고 읽는 순서를 정리한다. 주요 행동의 상대적 강조를 조정한다. |
| 조작 가능성 | 클릭할 수 있는 것과 정보가 구별되는가? 아이콘과 라벨로 행동을 예상할 수 있는가? | 익숙한 패턴과 명시적 라벨을 사용하고 동작 범위와 시각적 표현을 맞춘다. |
| 선택의 명확성 | 선택지의 차이와 결과를 구분할 수 있는가? 내부 조직·시스템 지식이 필요한가? | 사용자 목적에 맞는 이름과 짧은 구분 설명을 제공하고 관련 질문을 적절한 시점에 보여준다. |
| 문구의 부담 | 반복 설명이 핵심을 가리는가? 필요한 조건이 행동 가까이에 있는가? | 불필요한 말은 줄이되 결정에 필요한 비용·제약·오류 복구 정보는 유지한다. |
| 위치와 길 찾기 | 현재 페이지·상위 영역·선택된 항목을 알 수 있는가? 필요한 곳으로 이동하거나 돌아갈 단서가 있는가? | 제목, 현재 위치 표시, 일관된 메뉴·탭을 정리한다. 검색이나 경로 표시는 과업에 필요할 때 제안한다. |
| 첫 시작 | 새 사용자가 제품의 용도와 첫 유효 행동을 이해하는가? 빈 화면에서도 시작할 수 있는가? | 빈 상태에 상황 설명과 실제로 가능한 다음 행동을 제공한다. |
| 배려와 신뢰 | 결정 조건이 뒤늦게 나타나는가? 입력·실패·완료 상태가 모호하거나 이전 노력을 잃게 하는가? | 필요한 조건을 결정 전에 제시하고 상태, 복구 방법, 입력 보존을 명확히 한다. |

모바일·접근성은 과업을 막는지 함께 확인한다. 잘림, 겹침, 고정 요소의 가림, 좁은 조작 영역, 읽기 어려움, 색만으로 구별되는 상태를 살핀다. 실행 환경이 있으면 관련 흐름의 키보드 접근과 포커스도 확인한다. 스크린샷만으로 접근성 준수, 대비 비율, 실제 터치 영역을 단정하지 않는다. 정량 기준이나 인증을 요청받으면 해당 표준을 별도로 검증한다.

다음 오판을 피한다.

- **클릭 수를 절대 기준으로 삼지 않는다.** 선택의 불확실성, 반복 작업 부담, 실제 지연을 본다. 단계를 줄이면서 선택을 어렵게 만드는 수정은 피한다.
- 스크롤, 긴 페이지, 여러 버튼, 아이콘, 정보 밀도 자체는 결함이 아니다. 사용자 목표를 방해하는 구체적인 단서가 있어야 한다.
- 제품마다 동일한 글자 크기, 여백, 단 하나의 CTA를 강요하지 않는다. 기존 디자인 시스템의 관례를 우선한다.
- “직관적이지 않음”, “촌스러움”, “더 깔끔하게”로 끝내지 않는다. 어떤 사용자에게 어떤 의문이 생기는지 설명한다.
- 에이전트가 몇 초 안에 답했다는 사실을 사람의 이해 속도로 보고하지 않는다. 가상의 사용자 발언·성공률·전환율·시선 추적 결과를 만들지 않는다.

## 근거와 우선순위

**관찰**과 **해석**을 분리한다. 예: “두 버튼이 모두 ‘계속’이며 구분 설명이 없다”는 관찰이고, “사용자가 예약 확정과 임시 저장을 혼동할 가능성”은 해석이다. 실제 사용자 연구가 없다면 이를 휴리스틱 리뷰라고 명시한다.

각 발견 사항에는 근거 상태를 붙인다.

- **화면 관찰:** 특정 화면·조건에서 시각적 문제를 직접 확인했다.
- **동작 재현:** 조작과 결과까지 확인했다. 재현 순서를 기록한다.
- **검증 필요:** 우려는 있지만 관련 상태나 사용자 행동을 확인하지 못했다. 검증 방법을 제안하고 확정 결함과 구별한다.

심각도는 현재 과업에 대한 영향으로 정한다. 수정 난이도와 구분하며 불확실한 영향은 조건부로 적는다.

| 심각도 | 기준 |
| --- | --- |
| S1 · 차단 | 핵심 과업 진행이 막히거나, 되돌리기 어려운 잘못된 결과를 유발하는 문제가 확인됨 |
| S2 · 큰 마찰 | 주요 과업에서 잘못된 선택, 재입력, 우회나 큰 탐색 부담을 유발하는 근거가 있음 |
| S3 · 작은 마찰 | 국소적인 해석·탐색 부담이 있으나 과업은 계속할 수 있음 |

예쁜 정도에만 관한 선호는 심각도를 붙인 결함으로 집계하지 않는다. 같은 원인으로 여러 화면에서 반복되면 하나의 발견 사항에 발생 위치를 모은다. 영향이 큰 문제부터 제시하고 수정 규모는 별도로 설명한다. 근거 없는 총점이나 통과 기준을 만들지 않는다.

## 결과물과 재검증

사용자의 언어로 답한다. 먼저 과업 수행을 가장 방해하는 문제가 무엇인지 요약하고 관찰 범위와 중요한 가정을 짧게 적는다. 각 발견 사항은 아래 내용을 포함하되 작은 리뷰에 불필요하게 큰 보고서 형식을 강요하지 않는다.

```markdown
### F01 · [심각도] 구체적인 문제
- 위치·조건: 화면, 사용자 역할, 뷰포트, 관련 상태
- 근거 [화면 관찰/동작 재현/검증 필요]: 스크린샷 링크 또는 첨부 번호·영역, 필요한 재현 순서
- 관찰: 실제로 보였거나 재현된 사실
- 사용자 부담: 생길 수 있는 의문과 과업 영향; 관찰 사실과 구분
- 원칙: 관련 판단 기준
- 수정 제안: 바꿀 문구·배치·강조·상태를 구체적으로 명시
- 확인 조건: 같은 과업과 조건에서 무엇이 달라져야 하는지
```

예를 들어 “저장 버튼을 개선” 대신 “임시 저장과 외부 게시의 버튼명을 각각 구분하고 게시 범위를 실행 전에 표시”처럼 제안한다. 실제 동작을 모르면 문구를 확정하지 말고 필요한 확인을 함께 적는다.

마지막에는 우선 수정할 항목과 미검증 범위를 간단히 남긴다. 문제가 없으면 **관찰한 범위에서 근거 있는 문제를 찾지 못했다**고 말한다. 점검하지 않은 기기·상태까지 통과했다고 말하지 않는다.

수정을 수행한 경우 같은 과업, 역할, 데이터 조건과 뷰포트에서 다시 보고 원래 증거와 비교한다. 상태를 **해결 / 일부 해결 / 미해결 / 재검증 불가**로 갱신한다. 화면 단서의 개선은 시각적으로 확인할 수 있지만 사람이 더 잘 이해하는지는 실제 사용자 테스트로 확인한다. 수정 결과에 영향을 받는 인접 상태만 추가로 확인한다.
