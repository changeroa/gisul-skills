# Experience Mapping

지도는 공동 판단의 도구다. 그림을 완성하는 대신 **근거 → 경험 모델 → 공동 선택 → 담당 실행 → 결과 학습**을 연결한다.
작은 과업에는 짧은 문서로 시작한다. 모든 유형의 지도나 워크숍을 일괄 요구하지 않는다.

## 1. 바꾸려는 결정을 정한다

- 사용자가 해결하려는 문제, 결과를 사용할 사람, 결정권자, 영향을 받는 역할을 파악한다.
- 기존 정책·제품 계약·조사·운영 자료와 시간·자원 제약을 먼저 읽는다.
- “전체 여정을 그린다” 대신 “신청 후 대기에서 책임과 다음 행동을 결정한다”처럼 결정 질문을 적는다.
- 이미 알려진 사실, 내부 해석, 필요한 조사, 이번에 제외할 범위를 분리한다.
- 빠진 정보가 결정을 막지 않으면 가정을 명시하고 독립적으로 가능한 분석을 진행한다.
- 고객에게 중요한 결과와 조직이 원하는 결과가 충돌하는 지점도 남긴다.
- 매출·전환뿐 아니라 노력·안전·접근·신뢰·직원 부담 등 과업에 해당하는 가치를 고려한다.

최소 시작 기록:

> 결정 질문 / 사용자 목적 / 결정권자 / 참여 역할 / 기존 근거 / 범위·제약 / 미확인 사항

## 2. 관점·범위·입도를 고정한다

지도마다 다음을 명시한다. 고정된 템플릿보다 판단에 필요한 항목을 우선한다.

| 항목 | 정할 내용 |
|---|---|
| 관점 | 누구의 어떤 상황인가? 구매자·사용자·관리자·직원을 섞지 않는다. |
| 시작·끝 | 인간의 목적이 생긴 시점과 결과를 확인하는 시점. 조직의 첫·마지막 접점과 다를 수 있다. |
| 범위 | 포함할 채널·역할·서비스·선행 준비·사후 활동과 제외 이유 |
| 입도 | 생애주기·활동·과업·상호작용 중 주 수준과 상세 연결 방식 |
| 초점 | 행동·생각·감정·접점·전달 체계·관계 중 필요한 정보층 |
| 구조·용도 | 시간순·계층·네트워크 등 표현 구조와 이 지도로 내릴 결정 |

- 같은 수준의 단계에 “문제 해결”과 “버튼 클릭”을 섞지 않는다. 세부 흐름은 하위 모델로 연결한다.
- 다른 역할은 별도 지도나 lane으로 구별하고 공통 사건·접점으로 연결한다.
- 역할마다 목적이 다르면 하나의 평균 고객으로 합치지 않는다.
- 반복·병렬·순서 가변·채널 전환·중단·복귀를 직선 정상 경로로 숨기지 않는다.
- 범위 변경이 결론을 바꾸면 변경 이유와 영향받는 판단을 기록한다.

## 3. 질문에 맞는 지도 유형을 고른다

- 특정 서비스와의 관계·단절: **customer journey map**.
- 제품을 넘는 인간의 활동·목적·맥락: **experience map**.
- 제공 체계·보이지 않는 처리·책임 인계: **service blueprint**.
- 조사에서 드러난 사고·목적 구조와 지원 공백: **mental model diagram**.
- 여러 주체의 관계·정보·자원·가치 교환: **ecosystem diagram**.
- 해법과 독립적인 기능적 목적·수행 단계: **job map**.
- 합의된 경험의 구현·release 편성: **story map**. 사용자 필요 검증을 대신하지 않는다.

유형이 애매하거나 여러 지도를 연결해야 하면 [선택과 모델링](references/map-types.md)을 읽는다.
하나의 의사결정에 가장 작은 유효 모델을 택한다. 유형명을 맞추려고 중요한 사실을 버리지 않는다.

## 4. 자료를 조사 근거로 정리한다

1. 기존 인터뷰·지원 기록·운영 절차·분석 데이터에서 관련 자료를 찾는다.
2. 근거의 날짜·역할·맥락·수집 방법·관찰 범위와 중요한 제한을 기록한다.
3. 관찰 또는 자기보고, 그에 대한 해석, 경험상 함의를 분리한다.
4. 상반된 사례와 조사하지 못한 역할·채널·상황을 남긴다.
5. 추가 조사가 필요하면 가장 위험한 미확인 질문과 이를 확인할 방법을 제안한다.

제품을 직접 사용한 기록은 동작 근거다. 실제 고객의 생각·감정·선호를 관찰했다는 뜻은 아니다.
행동 로그는 발생·순서를 보여줄 수 있지만 이유·감정을 단독으로 입증하지 못한다.
내부 정책은 예정된 절차의 근거이지 고객이 실제로 그 경로를 따랐다는 근거가 아니다.
인터뷰에서는 최근의 구체적 사건·행동·우회·중단·결과를 묻고 원하는 답을 유도하지 않는다.
표본 수만으로 포괄성·대표성을 주장하지 않는다. 결론을 관찰된 역할·맥락에 한정한다.

### 권한과 개인정보

- 지도 작성 요청은 모집·연락·초대·녹음·외부 공유·운영 변경의 허가가 아니다.
- 기존 승인 범위 안에서만 행동한다. 외부 전송이 필요하면 내용을 준비하되 승인 없이 발송하지 않는다.
- 인터뷰·녹음·촬영의 목적, 참여 동의, 보관·공유 범위를 확인한다.
- 이름·연락처·계정·건강정보 등은 필요 최소한만 취급하고 공유본은 식별 정보를 제거한다.
- 원자료 접근권한과 재사용 제한을 보존한다. 비공개 자료를 승인 없이 외부 AI 도구에 올리지 않는다.
- 조사할 수 없으면 가설지도와 조사 계획을 만든다. 가상 참여자·발언·조사 결과를 만들지 않는다.

## 5. 증거 상태와 시간 상태를 따로 표시한다

각 주요 주장에는 두 축을 적용한다.

- **증거 축:** 관찰·자기보고·내부 자료·로그·해석·가설·미확인.
- **시간 축:** 현재 경험 / 미래 제안. 실험 결과와 실제 배포·운영 상태는 별도 기록한다.

현재 지도도 가설을 포함할 수 있다. 미래 제안이 실험에서 지지돼도 전체 여정이 구현된 것은 아니다.
관찰한 사실 옆의 해석을 같은 근거 수준으로 보이게 하지 않는다. 근거 위치를 역추적할 수 있게 한다.
자동 생성·LLM 출력은 독립적인 사용자 근거가 아니다. 새로 생성한 주장과 빈칸 보완은 가설로 표시한다.
원자료 요약은 원자료와 대조한 범위만 사용한다. AI가 제시한 발언·감정·인과를 원자료 확인 없이 채택하지 않는다.

## 6. 경험과 제공 활동을 연결한다

- 주 관점의 언어로 단계와 행동을 적는다. 내부 조직명·기능 목록을 인간의 목적 대신 쓰지 않는다.
- 행동, 질문·생각, 감정을 구별하고 각각 어떤 관찰·자기보고·해석에 기대는지 표시한다.
- 근거 없는 감정 곡선·만족 점수는 만들지 않는다. 정성적 해석을 측정값처럼 표현하지 않는다.
- 동시에 존재하는 긍정·부정 감정과 맥락 차이를 평균선 하나로 지우지 않는다.
- 접점은 채널 이름만이 아니라 목적·상황·상호작용·기대 결과로 기록한다.
- 대기·재입력·우회·복구가 누구에게 어떤 부담을 주는지 드러낸다.

Service blueprint에서는 다음을 연결한다.

1. 고객 행동과 고객에게 보이는 접점·결과.
2. **Frontstage:** 고객이 직접 경험하는 직원·디지털 서비스의 행동.
3. **Backstage:** 그 결과를 만드는 고객에게 보이지 않는 처리.
4. **Support:** 이를 지원하는 조직·시스템·정책·파트너.
5. 고객/제공자와 가시/비가시 경계, 단계 사이의 의존성과 인계.

중요한 handoff에는 **보내는 주체 → 받는 주체 → 전달 정보·대상 → 접수/완료 신호 → 대기·실패·복구 책임**을 남긴다.
알 수 없는 담당자나 약속 시간을 만들어 넣지 않는다. 책임 공백은 미결정으로 표시한다.
내부 처리의 효율이 고객 재입력이나 직원의 숨은 수작업으로 전가되지 않는지 양쪽을 본다.

## 7. 지도를 함께 읽고 판단을 정렬한다

지도 배포만으로 합의를 선언하지 않는다. 필요한 직무·결정권자가 실제로 검토한 범위를 기록한다.

1. 목적·관점·범위·라벨을 설명하고 대표 사건을 따라 지도를 함께 읽는다.
2. 각자가 수정·불확실성·지원 부족·평가를 먼저 적게 한다.
3. 평가가 갈린 부분의 근거·정책·목표·용어 차이를 논의한다.
4. 문제 정의와 해결안을 분리하고, 모르는 사실은 조사 질문으로 남긴다.
5. 가능성을 발산한 뒤 사용자 영향·목표 기여·근거·비용·의존성으로 선택한다.
6. 선택·보류·이견과 결정권자·이유를 기존 결정 기록에 남긴다.

투표는 선호를 모을 수 있지만 사실을 검증하지 못한다. 결석자나 응답하지 않은 역할의 동의를 추정하지 않는다.
실제 협업이 불가능하면 비동기 검토안과 열린 질문을 만들고 “정렬 완료”가 아닌 “검토 대기”로 보고한다.
워크숍 설계나 실험 인계가 필요하면 [정렬과 활성화](references/workshop-activation.md)를 읽는다.

## 8. 선택을 실행과 검증으로 바꾼다

각 우선 과제에 다음을 연결한다.

> 문제·근거 / 영향받는 단계·역할 / 선택·이유 / owner / 기대 결과 / 측정 방법 / 검증 시점·사건 / 다음 결정

- 기존 backlog·제품 계약·운영 과제에 연결한다. 지도 때문에 중복 장부를 만들지 않는다.
- 담당·수락·검증 조건이 정해지지 않은 과제는 배정 대기다. 활성화 완료로 세지 않는다.
- 불확실한 해법은 가장 위험한 가정부터 작게 실험한다.
- 대상·조건·개입·관찰 지표·성공/중단 기준을 실행 전에 정한다.
- 측정되지 않은 baseline·전환율·효과를 만들지 않는다. 결과를 본 뒤 합격선을 바꾸지 않는다.
- 결과로 구현·수정·재시험·중단 중 무엇을 할지 결정한다. prototype 반응을 운영 성과로 확대하지 않는다.
- 고객의 노력 감소와 직원 부담·오류·안전 등 관련 부작용을 함께 본다.
- 실험·테스트·배포·외부 부작용은 별도 승인 범위와 안전한 환경을 따른다.

## 9. 여정을 지속 관리한다

- 반복 사용하는 지도에는 map owner, 버전, 검토 날짜, 검토 사건을 둔다.
- 역할·단계·접점·이벤트 명칭과 ID를 안정적으로 유지해 여러 자료가 같은 경험을 가리키게 한다.
- 정책·역할·채널·파트너·주요 지표·새 연구가 바뀌면 영향을 받는 부분을 갱신한다.
- 현재 관찰, 과거 결정, 미래 제안을 구분하고 대체된 버전을 현재 근거처럼 유통하지 않는다.
- 새 근거가 기존 결정을 반박하면 이유와 재검토 owner를 기록한다.
- 지속 관리 인력·데이터 접근·지표가 없으면 작은 유지 절차부터 시작한다.
- 실시간 orchestration은 고객 식별·이벤트 정의·권한·중복·최신성·실패 복구가 준비된 경우에만 별도 검토한다.
- 플랫폼 구매·자동 갱신을 공동 이해나 의사결정의 대체물로 제시하지 않는다.

## 10. 인계와 완료 판정

- 결정의 보존은 기존 결정 관리에, 선정한 화면의 명확성은 UI QA에 연결한다.
- 상태·요청·복구는 상태 검토와 동작 테스트로 인계한다. 지도만으로 기능·사용성 통과를 주장하지 않는다.
- 시각 제작 도구는 합의된 의미를 표현한다. 렌더링 성공을 조사 근거나 이해관계자 합의로 쓰지 않는다.
- 최종 결과에는 결정 질문·관점·범위, 선택한 지도와 이유, 근거·가설·미확인, 주요 발견을 담는다.
- 선택·이견·보류, owner·측정·실험, 갱신 책임과 남은 검증을 함께 전달한다.
- 근거 없는 포괄적 완료 대신 **모델 작성 / 검토 대기 / 합의됨 / 실행 배정 / 실험·구현·운영 확인**을 구분한다.

완료 전 질문:

1. 주요 주장과 생각·감정의 근거, 현재/미래를 구별할 수 있는가?
2. 역할·입도·예외·인계 책임이 숨겨지지 않았는가?
