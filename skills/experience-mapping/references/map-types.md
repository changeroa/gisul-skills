# 지도 선택과 모델링

유형명부터 정하지 않는다. 결정 질문, 인간의 목적, 조직이 영향 줄 수 있는 범위와 필요한 해상도로 고른다.

## 선택 기준

| 유형 | 답하려는 질문 | 필요한 정보 | 자주 생기는 오용 |
|---|---|---|---|
| Customer journey | 특정 서비스와의 관계에서 어디가 끊기는가? | 역할·상황, 단계, 행동, 접점, 기대·감정의 근거 | 구매 funnel이나 화면 목록만 그리기 |
| Experience map | 특정 제품을 넘어서 목적을 어떻게 달성하는가? | 활동·대안·선행 준비·사후 활동·맥락 | 우리 제품 순서를 인간 경험 전체로 간주 |
| Service blueprint | 누가 어떻게 경험을 제공하고 인계하는가? | 고객 행동, frontstage/backstage/support, 경계·의존성 | 내부 업무도에 고객 lane만 덧붙이기 |
| Mental model | 사람의 사고·목적 구조와 지원 기능이 맞는가? | 조사 기반 생각·목적 묶음, 기능·콘텐츠 대응과 공백 | 제품 IA·개발자 가정을 사용자 사고로 표시 |
| Ecosystem | 여러 주체가 어떤 가치·자원을 교환하는가? | actor, 관계 방향·교환물, 영향·통제, 누락된 연결 | 관계의 의미 없이 로고·선만 배치 |
| Job map | 해법과 독립적으로 어떤 일을 수행하는가? | performer, focus job, 단계, 별도 성공 기준 | 기능·클릭 경로를 job으로 부르기 |
| Story map | 합의된 경험을 어떤 단위로 구현할 것인가? | 활동 backbone, stories, 의미 있는 release | 기능 목록 편성을 사용자 근거로 승격 |
| Workflow/state | 상세 분기와 전환이 맞는가? | 이벤트·조건·대기·실패·복구 | 상태 정합성으로 경험 가치까지 검증했다고 주장 |

## 해상도와 여러 지도 연결

- 생태계의 모든 관계를 한 장의 journey에 넣지 않는다. 주 관점과 대표 상황을 선택한다.
- 구매자·실사용자·관리자의 목적이 다르면 별도 lane 또는 지도에 두고 공통 사건으로 연결한다.
- 여러 지도의 같은 actor·stage·handoff에는 같은 식별자나 명확한 대응을 둔다.
- 넓은 모델에서 중요 접점을 찾은 뒤 상세 blueprint·workflow로 내려갈 수 있다.
- 다른 입도의 지도를 이어도 같은 수준의 사실처럼 합치지 않는다.
- 조직의 영향 밖 관계도 경험에 중요하면 표시하되 통제할 수 있다고 주장하지 않는다.
- 특정 제품에 가까운 모델은 구현에 유용하지만 변경 시 더 자주 재검토해야 한다.

## Journey·experience map

1. 역할·상황·목적·시작/끝을 적는다.
2. 사용자 언어로 같은 수준의 활동 단계를 만든다.
3. 행동을 배치하고 채널·접점·대기·전환·복귀를 연결한다.
4. 생각·질문·감정에는 각각 자기보고·해석 등 근거 상태를 붙인다.
5. 기대 결과와 실제 지원의 차이, 접근·시간·돈·숙련·노력의 장벽을 찾는다.
6. 중요한 분기는 연결 문서로 분리할 수 있지만 정상 경로만으로 전체성을 주장하지 않는다.

## Service blueprint

- 고객 lane이 기준이다. 내부 부서의 업무 순서를 먼저 만들고 고객을 끼워 맞추지 않는다.
- Frontstage는 사람이 하는 일만이 아니다. 고객이 직접 경험하는 디지털 응답도 포함한다.
- Backstage는 그 응답을 가능하게 하는 비가시적 처리다. Support는 이를 떠받치는 시스템·정책·파트너다.
- 가시성 경계와 고객/제공자 상호작용 경계를 구별한다. 같은 주체도 활동에 따라 다른 층에 나타날 수 있다.
- 고객에게 보이는 성공 신호와 실제 처리 완료 시점이 다르면 둘 다 표시한다.

중요 인계의 최소 기록:

> 발생 사건 / 보내는 주체 / 받는 주체 / 전달할 대상·정보 / 접수 신호 / 완료 조건 / 대기 안내 / 실패·복구 owner

정해지지 않은 정책·담당·시간은 미결정이다. 보기 좋은 흐름을 위해 자동 승인·재시도·보상 정책을 발명하지 않는다.
역할 변경·채널 전환·대상 식별·부분 완료가 맥락이나 데이터를 잃는 지점을 먼저 본다.
직원 수작업·재입력·예외 처리도 포함해 고객에게 보이지 않는 비용을 드러낸다.

## Mental model·job map

- 조사에 나온 표현·목적을 묶고 분류 이유를 설명한다. 조직의 기능 카테고리를 그대로 씌우지 않는다.
- Mental model은 목적·생각 구조와 지원을 비교한다. 검증되지 않은 분류는 가설 모델이다.
- Job은 해법·브랜드·기술 이름을 제거한 기능적 목적으로 표현한다.
- 너무 큰 열망과 너무 작은 조작을 focus job에 섞지 않는다.
- 수행 단계와 빠름·정확성·비용 같은 성공 기준을 분리한다.
- 감정·사회적 맥락이 중요하면 경험층을 추가한다. 기능적 job 모델이 이를 다 담는다고 주장하지 않는다.

## Ecosystem

- actor마다 목적·기여·얻는 가치와 주요 제약을 적는다.
- 관계에 방향과 교환물을 붙인다. 정보·돈·물리 자원·신뢰·책임을 무차별적으로 한 종류의 선으로 표현하지 않는다.
- 갈등·비대칭·의존성·누락된 연결·비용 전가를 찾는다.
- 고객뿐 아니라 직원·파트너·취약 집단·수리/종료 단계의 영향도 범위에 맞게 검토한다.
- 연결이 많다는 이유로 중요하다고 단정하지 않는다. 목적과 변화 가능성이 있는 관계를 선택한다.

## 정보 표현 QA

현재/미래와 근거/가설은 색상만이 아니라 라벨로도 구별한다.
범례·단계 이름·행동 문법을 통일하고 중요한 내용을 줄이기보다 상세를 분리한다.
감정 곡선은 측정 근거가 없으면 수치처럼 그리지 않는다. 동시에 존재하는 감정을 지우지 않는다.
시각적 명확성 검토는 사실 검증·사용자 연구·조직 합의와 별개의 결과로 기록한다.
