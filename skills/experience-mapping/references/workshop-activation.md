# 공동 정렬과 실행 활성화

워크숍은 선택지다. 작은 팀·과업에서는 비동기 검토나 짧은 회의로 동일한 판단을 만들 수 있다.
참석·발언·투표 수보다 공동 문제 정의와 실행 책임을 확인한다.

## 준비

- 목표는 “지도 리뷰”가 아니라 이번에 선택할 문제·책임·우선순위로 적는다.
- 결정권자, 영향을 받는 직무, 현장 정보를 아는 사람과 진행자를 구별한다.
- 결석한 역할의 영향과 사후 검토 경로를 남긴다. 대리 참석이 동의를 뜻하지 않는다.
- 사전 자료에는 범위·라벨·대표 사건·중요 근거·미확인 질문을 포함한다.
- 원격·비동기 참여자도 개별 의견을 남길 수 있게 한다.
- 고객 참여·초대·녹음·외부 공유는 별도 승인과 동의 범위 안에서만 진행한다.

## 1. 이해하기

1. 특정 역할의 대표 사건을 지도에서 따라간다.
2. 관찰·자기보고·추론·가설과 현재/미래를 구별한다.
3. 참가자가 사실 수정·빠진 상황·다른 해석을 먼저 개별 기록한다.
4. 지원 수준을 평가한다면 평가 기준을 맞추고 각자의 근거를 남긴다.
5. 평균보다 평가 차이가 큰 부분을 논의한다.

자료의 충돌은 관찰 조건·시점·역할 차이인지 확인한다.
권한자의 기억이나 다수의 선호로 외부 사실을 확정하지 않는다.
해결되지 않은 사실은 조사 질문, 가치 선택은 결정 사안으로 분리한다.

## 2. 가능성 찾기

- 합의한 문제를 사용자 목적·상황·장벽으로 적는다.
- 특정 기술이나 화면을 이미 정답으로 넣은 질문은 더 상위 문제로 다시 쓴다.
- 개별 발상 후 모아 발언량과 직급이 선택지를 지배하지 않게 한다.
- 발산 중 평가를 섞지 않는다. 이후 중복을 묶고 차이를 보존한다.
- 사용자 영향·목표 기여·근거 강도·비용·의존성으로 비교한다.
- 내부 처리 감소가 고객 재입력이나 직원 부담으로 이동하는 대안은 그 비용을 함께 표시한다.
- 미래 제안이 현재와 비슷하면 별도 layer를, 구조가 달라지면 별도 지도를 쓴다.

## 3. 선택하고 표현하기

선택에는 문제·대안·이유·결정권자·반대 의견·보류 조건을 남긴다.
투표는 선호를 파악하는 수단이다. 조사 결과나 제품 정책을 대신하지 않는다.
구체적 시나리오·storyboard·작은 prototype으로 각자가 같은 해결안을 상상하는지 확인한다.
동료의 빠른 피드백을 대상 사용자의 검증이나 시장 성과로 부르지 않는다.
실제 참가자 검토 없이 만든 결과는 제안 또는 검토 대기로 표시한다.

## 4. 실행 계약

각 선택된 기회에 다음을 연결한다.

| 필드 | 기록할 내용 |
|---|---|
| 문제·근거 | 어느 역할·단계의 어떤 부담이며 무엇을 보고 판단했는가 |
| 기대 결과 | 사람과 조직에게 무엇이 달라져야 하는가 |
| Owner | 실행을 맡은 사람·팀과 수락 여부 |
| 의존성 | 다른 직무·정책·데이터·파트너가 먼저 결정할 것 |
| 측정 | 지표·관찰 방법·대상·조건·기간과 알려진 baseline |
| 검증 | 언제 또는 어떤 사건에서 결과를 판단할 것인가 |
| 결정 | 구현·수정·재시험·중단을 나누는 조건 |

기존 backlog·계약·결정 기록에 연결하고 별도 장부를 중복 생성하지 않는다.
Owner를 임의로 배정하거나 수락했다고 쓰지 않는다. 미배정·미수락은 열린 과제다.
검토·실험·구현·배포·효과를 서로 다른 상태로 기록한다.

## 5. 가정부터 실험하기

1. 해결안의 성공을 좌우하는 가장 위험한 가정을 고른다.
2. 그 가정을 반박할 수 있는 최소한의 안전한 개입을 설계한다.
3. 대상·상황·개입·예상 변화·관찰 방법을 적는다.
4. 결과를 보기 전에 성공·실패·중단 기준을 정한다.
5. 접근성·오류·직원 수고·안전 등 관련 부작용도 확인한다.
6. 결과·제한·반증을 기록하고 다음 결정을 내린다.

baseline을 모르면 먼저 측정하거나 비교의 한계를 적는다. 가상의 전환율이나 만족 점수를 만들지 않는다.
의도한 행동의 자기보고, prototype에서의 과업 수행, 실제 운영 성과를 구분한다.
외부 전송·결제·권한 변경·배포가 포함된 실험은 별도 승인·격리 환경을 따른다.
작은 표본이나 제한된 환경의 결과를 전체 고객·채널로 일반화하지 않는다.

## 6. 지속 운영으로 넘기기

- 지도·주요 과제·측정의 owner가 같아야 할 필요는 없다. 각 책임과 연결을 명시한다.
- 정책·역할·파트너·채널·고객 연구·지표 변화 중 어떤 사건이 재검토를 촉발할지 정한다.
- 안정된 단계·actor·event 명칭으로 운영 데이터와 연구를 연결한다.
- 데이터 출처·갱신 시점·중복·식별·권한이 불명확하면 수치를 지도의 사실로 확정하지 않는다.
- 동기식 협업은 새로운 의미·이견·방향을 다루고 비동기식 검토는 유지·추적을 확장한다.
- 실시간 자동화는 별도 기술·운영 과제다. mapping이나 지속 관리의 기본 완료 조건으로 요구하지 않는다.

## 종료 판정

지도를 만들었지만 검토하지 않았다면 모델 작성이다.
선택은 했지만 owner·측정·실험이 없으면 활성화 대기다.
구현했지만 운영 결과를 확인하지 않았다면 효과 미확인이다.
남은 이견·담당 공백·근거 공백을 숨기지 않는 것이 정확한 인계다.
