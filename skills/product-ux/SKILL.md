# Product UX

사용자가 실제 업무를 이해하고, 수행하고, 결과를 확인하며, 실패에서 회복할 수 있게 설계한다. 화면 수나 보기 좋은 시안 수가 아니라 **과업의 완결성, 예측 가능한 행동, 정직한 상태, 검증 가능한 결정**을 기준으로 삼는다.

이 스킬은 진입점이다. 전문 스킬 하나가 요청을 충분히 다루면 다시 전체 절차를 강요하지 않는다. 필요한 스킬은 현재 카탈로그에서 찾아 읽는다. 이름만 알거나 검색 결과만 본 것을 로드했다고 말하지 않는다.

## 1. 작업 모드와 경계를 고정한다

- **분석·리뷰:** 자료를 읽고 발견과 대안을 제시한다. 수정이나 사용자 접촉을 허가받은 것으로 해석하지 않는다.
- **설계·시안:** 대안을 실제로 비교할 수 있게 만든다. 정적 화면, 모의 동작, 실제 연결 범위를 구분한다.
- **구현:** 승인된 범위와 기존 동작을 보존한다. 디자인 선택을 정책·권한·기능 삭제의 승인으로 확대하지 않는다.
- **연구:** 질문, 모집, 동의, 자료 취급과 분석 계획을 정한다. 실제 참여자 없이 사용자 연구를 수행했다고 말하지 않는다.

외부 초대·모집·연락, 게시·결제·삭제, 운영 데이터 변경, commit·push·배포는 호스트 정책과 해당 작업의 허가를 따른다. 이 스킬과 팩 자체는 추가 권한을 주지 않는다.

기존 제품의 역할, 용어, 승인 시안, 디자인 시스템, 코드 변경과 출시 조건을 먼저 확인한다. 일반 UX 권고로 실제 사업 정책을 새로 만들지 않는다. 자료가 충분하면 먼저 조사하고, 의미나 권한이 갈리는 결정만 질문한다.

## 2. 화면이 아니라 과업을 작업 단위로 삼는다

다음 다섯 가지를 간단히 적는다.

1. **누구:** 역할, 숙련도, 접근 요구와 사용 환경.
2. **왜:** 사용자가 얻으려는 결과와 조직이 해결하려는 문제.
3. **어디서 시작:** 진입점, 선행조건, 기존 데이터와 권한.
4. **어떻게 완료를 앎:** 사용자에게 보이는 확인과 실제 업무 결과.
5. **무엇을 유지:** 바꾸지 않을 흐름·레이아웃·문구·정책과 승인 기준.

실제 서비스 화면, 정적 시안, 소스 코드, 분석 수치, 인터뷰와 가정을 구분한다. 코드를 읽었다고 렌더링을 검증한 것이 아니며, 화면을 보았다고 실제 저장이나 사용자의 이해를 확인한 것도 아니다.

## 3. 문제에 맞는 전문 절차만 선택한다

| 주된 결정 문제 | 전문 스킬 | 독립적으로 확인할 산출물 |
| --- | --- | --- |
| 메뉴, 정보 분류, 화면 유형, 상세·탭·단계 흐름과 길 찾기 | `interface-architecture` | 과업·정보 관계, 경로, 선택 이유와 복귀 문맥 |
| 위계, 그룹, 타이포그래피, 밀도, 그리드와 작은 화면 재배치 | `interface-layout` | 콘텐츠 우선순위와 상태·폭별 레이아웃 계약 |
| 목록·테이블, 검색·필터, 선택 범위, 대시보드와 데이터 탐색 | `collection-data-design` | 목록의 목적, 비교·선택·탐색 계약과 데이터 의미 |
| 입력, 선택 컨트롤, 검증, 저장·실행·취소·되돌리기 | `form-command-design` | 입력·명령의 범위, 결과, 보존·복구 계약 |
| 로딩, 저장, 갱신, 알림, 모션, 반복과 임시 모드 | `interaction-feedback` | 트리거부터 종료까지 시간·채널·피드백 수명 |
| 여러 역할·채널·운영 조직 사이에서 끊기는 경험 | `experience-mapping` | 근거가 연결된 현재 경험과 실행 책임·실험 |
| 패턴 선택·조합, 토큰·컴포넌트 일관성과 시스템 운영 | `ui-pattern-systems` | 패턴의 맥락, 조합 계약, 소유자와 변경 정책 |
| 버튼·라벨·상태·오류 문구, 용어·voice/tone와 콘텐츠 운영 | `ux-content` | 문구의 목적·사실성·어조·검증·소유권 |
| 사용자를 알아야 내릴 수 있는 결정, 실제 관찰과 검증 | `ux-research` | 질문→증거→해석→결정의 연구 연결 |

예: 로딩 전환 효과만 요청받았다면 `interaction-feedback`를 우선한다. 메뉴와 화면 형태를 다시 설계하지 않는다. 로딩 중 잘림이 확인될 때만 `interface-layout`을 추가한다.

온보딩 순서가 문제라면 `interface-architecture`부터 시작한다. 권한과 선행조건의 실제 상태가 충돌하면 기존 `ux-state-review`를 연결한다. 사용자·운영자의 책임 자체가 불명확할 때에만 `experience-mapping`으로 범위를 넓힌다.

## 4. 기존 검토·검증 스킬과 책임을 나눈다

사용 가능한 경우 아래 절차를 선택적으로 조합한다. 사용할 수 없으면 그 검증을 완료했다고 쓰지 않는다.

- `dont-make-me-think`: 실제 화면의 이해, 발견 가능성, 탐색과 선택 부담을 휴리스틱으로 리뷰한다. 새 설계의 정답이나 실제 사용자 연구를 대신하지 않는다.
- `ux-state-review`: 도메인 상태·권한·선행조건과 화면·다음 행동·요청의 일관성을 검토한다.
- `browser-e2e-review`: 실제 브라우저의 처리 중·완료·실패·복귀와 시각적 변화를 증거로 검증한다.
- `exploratory-ux-qa`: 허용된 사용자 여정을 탐색하고 화면·네트워크 근거를 수집한다.
- `preserve-decisions`: 큰 구현이나 인계에서 유효한 결정·승인 기준과 증거를 보존한다.

같은 결함을 여러 스킬 이름으로 중복 보고하지 않는다. 하나의 발견에 여러 관점을 연결한다. 새 설계·휴리스틱 평가·기능 회귀·시각 회귀·접근성 검증·인간 사용성 연구를 서로 다른 증거로 취급한다.

## 5. 대안을 결정과 검증으로 연결한다

1. 현재 문제와 보존할 계약을 고정한다.
2. 같은 역할·과업·데이터·상태에서 실질적으로 다른 대안을 비교한다.
3. 각 대안이 줄이는 부담과 새로 만드는 비용을 적는다. 시안 수를 채우기 위해 변형을 만들지 않는다.
4. 되돌리기 쉬운 국소 개선과 정책·정보구조 변경을 구분한다.
5. 선택한 변형·버전·추가 메모와 관찰 가능한 수용 조건을 기존 기록에 남긴다.
6. 구현·데이터 연결 뒤에도 선택한 기준을 유지하고, 의도된 이탈은 이유를 기록한다.

사용자가 상태 피드백만 바꾸라고 했는데 새 대시보드를 제안하는 것은 개선이 아니라 범위 이탈이다. 반대로 업무 완료가 불가능한 문제를 색상과 여백만으로 해결했다고 판단하지 않는다.

## 6. 완료 전에 증거 수준을 확인한다

- 대상 역할, 정상·오류·빈 결과·부분 결과·복귀 중 요청과 위험에 해당하는 상태를 보았는가?
- 데스크톱 축소가 아닌 콘텐츠 우선순위에 맞는 좁은 화면 동작을 확인했는가?
- 실제 데이터·요청·완료 결과와 문구가 같은 의미인가?
- 키보드, 포커스, 텍스트 확대, 비색상 단서와 모션 축소 중 관련 요구를 확인했는가?
- 실행하지 못한 도구·참여자·환경·상태를 미검증으로 남겼는가?

정적 체크리스트 통과는 실제 사람의 이해, 전환율 향상, 표준 접근성 준수나 운영 준비 완료의 증명이 아니다. 근거 없는 점수, 사용자 발언, 실험 수치와 심리 상태를 만들지 않는다.

## 결과

작업 크기에 맞춰 **대상 과업 → 확인한 문제 → 선택한 변경과 유지 항목 → 검증과 미검증 → 남은 결정**을 보고한다. 작은 수정마다 대형 문서를 만들지 않는다. 리뷰만 했으면 구현했다고, 로컬 구현만 했으면 배포했다고 말하지 않는다.
