# Clean Code Skill Pack

읽는 사람이 현재 동작과 변경 지점을 빠르게 이해하고, 다음 변경을 안전하게 수행할 수 있도록 코드를 개선한다. 깨끗함은 줄 수, 함수 수, 패턴 수가 아니라 **의도가 드러나는 정도, 변경 영향의 국소성, 반복 가능한 동작 증거**로 판단한다.

이 스킬은 팩의 진입점이다. 전체 책을 하나의 거대한 체크리스트로 적용하지 말고 현재 요청에 필요한 전문 스킬만 선택한다. 판본, 장별 반영 범위, 원칙의 한계가 필요하면 [출처와 장별 적용 지도](references/sources-and-guardrails.md)를 먼저 읽는다.

## 전문 스킬 선택

같은 카탈로그 릴리스에서 필요한 스킬만 찾아 정확한 URI로 불러온다. 직접 호출된 전문 스킬이 요청을 충분히 다루면 이 진입 절차를 다시 강요하지 않는다. 사용할 수 없는 스킬을 실행했다고 말하지 않는다.

| 문제 또는 요청 | 전문 스킬 |
| --- | --- |
| 이름, 주석, 파일 내 배치, 형식, 읽기 흐름 | `clean-code-readability` |
| 함수 크기와 책임, 인수, 제어 흐름, 오류, 부수 효과, 중복 | `clean-code-functions` |
| 객체와 데이터 구조, 클래스 응집도, 공개 표면, 객체 협력 | `clean-code-objects` |
| 테스트 규율, 단위 테스트 표현, 수용 테스트, 회귀 증거 | `clean-code-tests` |
| LLM·코딩 에이전트가 만든 코드의 사용과 검증 | `clean-code-ai` |
| 단순 설계, YAGNI, SOLID, 컴포넌트, 지속적 설계 | `clean-code-design` |
| 스레드, 태스크, 공유 상태, 종료, 동시성 테스트 | `clean-code-concurrency` |
| 정책과 세부사항, 사용 사례 독립성, 시스템 경계와 의존성 규칙 | `clean-code-architecture` |
| 작은 주기, 지속적 개선, 팀 협업, 추정과 직업적 책임 | `clean-code-craft` |

하나의 함수 정리는 보통 `clean-code-functions`만으로 충분하다. 이름과 테스트까지 실제로 문제가 될 때만 다른 스킬을 더한다. 저장소 전체 요청이라도 모든 전문 스킬을 자동 실행하지 말고, 먼저 변경 경로와 위험을 좁힌다.

## 작업 모드와 권한

요청에서 모드를 확정한다.

- **리뷰:** 기본은 읽기 전용이다. 근거 있는 문제와 최소 수정 방향을 제시하되 파일을 바꾸지 않는다.
- **리팩터링:** 사용자가 변경을 요청한 범위에서 관찰 가능한 동작을 보존하며 수정한다.
- **기능 구현:** 새 요구 동작과 구조 개선을 구별한다. 가능하면 동작 변경과 순수 정리를 별도 단계나 별도 커밋으로 나눈다.
- **설명·교육:** 코드나 저장소 변경 없이 사례와 트레이드오프를 설명한다.

리뷰 요청을 수정, 커밋, 푸시, PR, 배포 허가로 확대하지 않는다. 실행과 외부 전송은 호스트와 저장소의 권한 정책을 따른다. 생성 파일, vendored code, minified code는 원본 생성 경로나 공급자를 먼저 찾고 직접 손대지 않는다.

## 1. 범위와 기준선을 고정한다

1. 대상 저장소, 파일 또는 변경, 사용자의 목적, 명시된 비목표를 확인한다. 정보가 저장소에서 확인 가능하면 먼저 조사하고 불필요한 질문을 하지 않는다.
2. 현재 revision과 작업 트리 상태를 기록한다. 사용자의 기존 변경을 덮어쓰거나 무관한 변경을 정리하지 않는다.
3. 저장소의 언어·프레임워크 관례, formatter, lint, type check, test 명령, 공개 API 정책을 찾는다. 개인 취향보다 이미 합의된 일관성을 우선한다.
4. 호출자, 피호출자, 관련 타입과 설정, 테스트를 읽는다. 한 파일만 보고 시스템 동작을 추측하지 않는다.
5. 요청한 경로를 한 번 끝까지 추적한다. 입력과 검증, 핵심 규칙, 상태 변경, 외부 효과, 결과와 오류가 어디에서 결정되는지 적는다.

리뷰 중 발견한 오래된 문제는 현재 변경이 만든 문제와 구별한다. 범위 밖 대규모 재설계를 작은 정리의 완료 조건으로 만들지 않는다.

## 2. 보존하거나 바꿀 계약을 구별한다

리팩터링 전에 무엇이 같은 채로 남아야 하는지 적는다. 반환값만 비교하지 말고 해당되는 항목을 본다.

- 공개 함수·API·파일 형식과 소비자 호환성
- 예외·오류 종류, 메시지나 상태 코드가 계약인 경우의 값
- 저장, 네트워크, 로그, 이벤트 같은 부수 효과와 발생 순서
- 정렬, 직렬화, 반올림, 시간대, 로케일, 경계값
- 트랜잭션, 재시도, 취소, 자원 해제와 종료 시점
- 성능이나 메모리 특성이 요구사항인 경로
- 동시성의 원자성, 순서, 중복 실행 가능성

명세, 승인 기준, 공개 계약, 실제 소비자, 기존 테스트, 현재 구현은 서로 다른 증거다. 기존 동작과 테스트가 있다는 사실만으로 그 동작이 올바른 요구사항이라고 단정하지 않는다. 알려진 버그를 고치는 작업이라면 의도된 동작 변경을 명시하고 나머지 계약만 보존한다.

## 3. 반복 가능한 증거를 확보한다

1. 관련 테스트와 정적 검사를 변경 전에 실행할 수 있으면 기준선을 남긴다. 전체 스위트가 비싸면 가장 가까운 테스트부터 시작하고 최종 단계에서 필요한 범위로 넓힌다.
2. 중요한 동작에 증거가 없고 테스트 추가가 범위에 포함되면, 구현 내부가 아니라 관찰 가능한 계약을 고정하는 작은 특성 테스트를 먼저 만든다.
3. 테스트를 실행할 수 없다면 코드 추적 결과와 미검증 항목을 분리한다. 실행하지 않은 절차를 통과했다고 말하지 않는다.
4. 실패가 이미 존재하면 변경 전후를 비교해 새 실패와 기존 실패를 구별한다. 원인을 모르면 추측하지 않는다.

테스트를 통과시키기 위해 assertion을 약하게 만들거나 snapshot을 무비판적으로 갱신하지 않는다. 테스트 자체의 품질은 `clean-code-tests`로 점검한다.

## 4. 문제를 독자의 질문으로 진단한다

체크리스트 항목 수가 아니라 다음 질문에 답하기 어렵게 만드는 원인을 찾는다.

- 이 코드는 무엇을 하며 왜 존재하는가?
- 정상 경로와 실패 경로는 어디인가?
- 어떤 상태를 읽고 바꾸며, 외부에 어떤 효과를 남기는가?
- 이 요구 하나를 바꾸면 어디를 함께 수정해야 하는가?
- 어떤 불변식과 순서 제약을 지켜야 하는가?
- 같은 정책이 여러 표현으로 흩어졌는가?
- 새 추상화가 현재의 실제 변화를 단순화하는가, 미래를 추측해 층만 늘리는가?

문제마다 구체적인 읽기 비용, 변경 비용, 오용 경로 또는 검증 어려움을 설명한다. “SRP 위반”, “함수가 김”, “깔끔하지 않음”만으로 발견 사항을 만들지 않는다.

## 5. 가장 작은 의미 단위로 개선한다

한 번에 하나의 가설을 적용한다. 예: “이 이름이 단위를 드러내면 호출자가 변환 규칙을 다시 추론하지 않아도 된다.”

안전한 순서는 대체로 다음과 같다.

1. 자동 포맷과 동작을 바꾸지 않는 코드 이동을 의미 변경과 분리한다.
2. 이름을 명확히 하고 지역 변수와 표현을 정리한다.
3. 응집된 단위를 추출하거나, 잘못 쪼개진 단위를 다시 합친다.
4. 중첩과 숨은 부수 효과를 줄여 정상 경로와 오류 경로를 드러낸다.
5. 함께 바뀌는 규칙은 모으고 다른 이유로 바뀌는 규칙은 분리한다.
6. 실제 확장점과 경계에만 추상화를 둔다.
7. 죽은 코드와 틀린 주석을 제거하되, 사용 여부를 검색과 실행 경로로 확인한다.

각 의미 단위 뒤에 가능한 가장 가까운 검사를 실행한다. 실패하면 더 많은 수정을 쌓기 전에 원인을 확인하거나 그 단위를 되돌린다. 전역 이름 변경, 대량 이동, 공용 API 변경은 언어 인식 도구와 소비자 조사를 사용하고 작은 텍스트 치환으로 밀어붙이지 않는다.

## 6. 규칙을 절대화하지 않는다

- 함수와 파일에 고정 줄 수를 강제하지 않는다. 더 작게 나눴을 때 이름과 국소 추론이 좋아지는지, 아니면 탐색과 인수 전달만 늘어나는지 비교한다.
- 주석을 전부 코드로 바꾸거나 전부 삭제하지 않는다. 코드가 말할 수 있는 것은 코드로 드러내되, 이유·제약·공개 계약·놀라운 결과는 정확한 주석이 더 낫다.
- TDD만 허용하지 않는다. 테스트 우선, 짧은 번들, 다른 규율 중 무엇을 쓰든 설계 사고, 빠른 피드백, 회귀 증거, 정리 단계를 빠뜨리지 않는다.
- SOLID, DRY, 패턴, 함수 추출을 결함 판정기로 쓰지 않는다. 현재의 변경 압력과 실제 소비자가 이득을 얻는지 확인한다.
- 비슷하게 생긴 코드를 무조건 합치지 않는다. 같은 지식이고 함께 바뀌는 중복만 통합한다. 서로 다른 이유로 변하는 우연한 유사성은 분리해 둔다.
- 단순성을 코드량 최소화로 착각하지 않는다. 의도, 경계, 실패가 드러나는 데 필요한 구조는 남긴다.
- 성능이 중요한 경로에서 명료성을 이유로 비용을 추측해 바꾸지 않는다. 측정과 요구 한계를 확인한다.
- 팀 관례와 언어 관용구에 맞는 여러 해법을 인정한다. 개인 선호를 필수 수정으로 보고하지 않는다.

## 7. 최종 검증

변경 후 다음을 확인한다.

1. 대상 테스트, 새 회귀 테스트, formatter, lint, type check, build 중 실제 프로젝트에 해당하는 검사를 실행한다.
2. 기준선과 같은 조건에서 결과, 오류, 부수 효과, 순서와 경계값을 비교한다.
3. 최종 diff를 처음부터 읽어 기능 변경, 무관한 포맷, 임시 로그, 주석 처리된 코드, 사용되지 않는 추상화, 약해진 테스트가 섞이지 않았는지 본다.
4. 공개 이름이나 경계를 바꿨다면 모든 소비자, 문서, 예제, migration 경로를 확인한다.
5. 처음보다 코드 이동 경로와 변경 지점이 실제로 짧아졌는지 냉정하게 다시 읽는다. 개선이 불명확하면 선호성 변경은 하지 않는다.

## 결과물

작업 크기에 맞춰 간결하게 보고하되 다음을 구별한다.

```markdown
## 범위와 계약
- 대상 revision/파일/경로
- 보존한 동작과 의도적으로 바꾼 동작

## 발견 또는 변경
### [위치] 구체적인 문제 또는 개선
- 근거: 실제 코드와 실행 경로
- 비용: 이해·변경·검증에 미치는 영향
- 조치: 적용한 최소 변경 또는 제안
- 트레이드오프: 유지한 복잡성이나 선택하지 않은 큰 대안

## 검증
- 실행한 명령과 결과
- 실행하지 못한 검사와 이유
- 남은 위험 또는 범위 밖 항목
```

리뷰에서 확인된 결함, 유지보수 개선, 선택적 취향을 섞지 않는다. 변경했다면 파일과 검증 결과를 명시한다. 문제가 없으면 검토 범위에서 근거 있는 개선점을 찾지 못했다고 말하고, 보지 않은 경로까지 깨끗하다고 일반화하지 않는다.
