# UX State Review

사용자가 목표를 달성하는 흐름을 기준으로 검토한다. 버튼 하나가 올바르게 비활성화되어도 주변 화면과 요청이 이전 상태를 전제하면 완료가 아니다. 구현 요청이면 아래 검토를 변경과 검증에 반영하고, 리뷰 요청이면 근거 있는 발견 사항을 전달한다.

## 1. 변경할 흐름과 실제 상태부터 파악한다

요구사항과 소스, 제공된 화면에서 **누가 → 무엇을 하려고 → 어떤 조건으로 진입하여 → 무엇을 보면 완료를 아는지** 정리한다. 이미 결정된 제품 정책을 우선한다. 접근권한, 관계 확인, 이용 자격, 제작 준비 여부를 확인 없이 합치거나 별도 승인 단계로 늘리지 않는다. 소스나 화면을 볼 수 없다면 확인한 사실과 가정을 구분한다.

상태를 결정하는 근거를 찾는다. 서버에 저장된 값과 작성 중인 초안, 조회 전과 조회 실패, 데이터 없음과 조회 권한 없음은 다를 수 있다. HTTP 상태 코드만으로 원인을 추정하지 말고 도메인 응답과 실제 호출 조건을 확인한다.

변경 범위에서 도달 가능한 주요 상태와 위험한 조합만 아래 표로 정리한다. 모든 상태의 조합을 기계적으로 나열하지 않는다.

| 상태와 판단 근거 | 사용자에게 보일 설명 | 가능한 다음 행동 | 필요한 조회·변경 요청 | 나타나거나 실행되면 안 되는 것 | 다음 상태와 확인 방법 |
|---|---|---|---|---|---|

특히 처음 진입, 부분 입력, 저장 중·실패·완료, 승인 대기, 준비 완료지만 결과 없음, 기존 결과 있음, 실제 통신 실패 중 관련 상태를 포함한다.

## 2. 원인에 맞는 화면과 행동을 정한다

- **선행조건 미충족:** 무엇을 준비해야 하는지와 그 위치를 안내한다. 같은 요청을 반복해도 해결되지 않는다면 재시도를 해결책으로 제시하지 않는다.
- **외부 처리 대기:** 누가 처리하는지, 사용자가 지금 할 일이 있는지 설명한다. 사용자가 할 수 없는 승인을 요구하는 버튼을 만들지 않는다.
- **정상적인 빈 결과:** 처음 이용, 검색 결과 없음, 작업 완료로 인한 비어 있음의 다음 행동은 서로 다르다.
- **입력 검증 실패:** 수정할 항목과 이유를 연결하고 이미 작성한 값을 보존한다.
- **실제 조회·저장 실패:** 실패를 숨기지 않는다. 재시도가 유효하면 제공하고, 기존 데이터나 입력을 유지할 수 있는지 확인한다.
- **아직 모르는 상태:** 확인 중이거나 확인에 실패한 것을 미작성·권한 없음·결과 없음으로 단정하지 않는다.

주요 행동이 실제 원인을 해결하는지 확인한다. 현재 상태 설명, 행동 이름, 이동한 화면의 제목과 위치가 연결되어야 한다. 사용자가 내부 권한 모델이나 API 용어를 해석해야 하는 문구는 사용자 과업 언어로 바꾼다.

## 3. 화면 전체와 요청을 같은 상태에 맞춘다

안내문뿐 아니라 제목, 배너, 탭, 버튼, 빈 표의 헤더·페이지 이동, 수치, 로딩, 토스트, 캐시된 오류를 함께 확인한다. 의미 없는 표 구조는 빈 상태로 대체하되 유효한 검색·필터·기존 결과 탐색까지 없애지 않는다. 여러 영역에 동일한 안내와 주요 버튼이 중복되는지도 본다.

구현 시 상태의 근거 → 요청 조건 → 응답 처리 → 캐시 → 렌더링까지 추적한다.

- 선행조건이 필요한 작업과 독립적인 읽기 작업을 구별한다. 새 생성이 불가능해도 기존 결과 조회·다운로드가 허용될 수 있다. 페이지나 병원 전체의 요청을 일괄 차단하지 않는다.
- 조건 미충족이 확정된 작업에 불필요한 조회·자동 재시도·폴링을 실행하지 않는다. 단, 준비 여부 확인과 유효한 기존 데이터 요청은 유지한다.
- 저장 성공이나 권한 변경 뒤 어떤 이벤트로 재확인하고 화면이 전환되는지 정한다. 탭 이동·포커스·구독·폴링 중 기존 요구와 비용에 맞게 선택하며 고정 주기를 강제하지 않는다.
- 대상 전환과 늦게 도착한 응답 때문에 다른 병원·계정의 결과나 과거 오류가 남지 않는지 확인한다. 여러 대상이 섞이면 대상별로 판단한다.
- 비활성화는 서버 검증을 대신하지 않는다. 중복 제출이나 이미 처리된 신청은 실제 결과에 따라 기존 상태 확인·이어하기 등 적절한 경로로 연결한다. 충돌 응답을 무조건 성공으로 바꾸지 않는다.

## 4. 처음 쓰는 사람의 과업을 따라간다

변경된 흐름을 한 단계씩 진행하며 다음을 묻는다.

1. 지금 무엇을 해야 하는지 알 수 있는가?
2. 그 행동을 실행할 곳을 발견할 수 있는가?
3. 이름과 설명으로 원하는 결과가 나올지 예상할 수 있는가?
4. 실행 후 진전했는지, 실패했는지 알 수 있는가?

어느 단계든 아니라면 화면·코드·관찰 근거를 붙여 수정한다. 키보드로 주요 행동에 도달 가능한지, 오류가 해당 입력과 연결되는지, 동적 상태 변화와 이동 후 위치를 인지할 수 있는지도 변경 범위에서 확인한다. 브라우저 검증은 작업 환경이 지정한 도구와 스킬을 따른다.

이 검토를 실제 사용자 테스트로 부르지 않는다. 용어 이해나 탐색의 성공 여부가 불확실하면 실제 대상 사용자가 수행할 중립적인 과업을 제안한다. 정답 버튼이나 경로를 과업 문구에 넣지 않는다. 사용자 모집이나 연락은 별도 요청 없이 수행하지 않는다.

## 5. 보이는 것과 없어야 하는 것을 함께 검증한다

테스트는 변경 위험에 맞게 선택한다. 주요 상태의 렌더링과 요청 여부, 중요한 전환은 컴포넌트·통합 테스트로, 화면 전체의 모순과 과업 완료는 가능한 실제 화면으로 확인한다. 스냅샷이나 문구 일치만으로 끝내지 않는다.

- 정상 안내와 다음 행동이 **나타나는지**, 부적절한 오류·재시도·요청은 **없는지** 함께 확인한다.
- 선행조건을 채우는 중, 저장 실패, 저장 성공 이후가 구별되는지 확인한다.
- 조건이 바뀐 뒤 새로고침·직접 진입·다른 대상으로 이동해도 정책이 유지되는지 확인한다.
- 기존 결과, 일부만 준비된 여러 대상, 실제 장애가 변경 때문에 잘못 차단되거나 은폐되지 않는지 확인한다.

시나리오 선택이나 회귀 검증에는 [review-cases.md](references/review-cases.md)를 읽는다. 고정된 전체 체크리스트로 사용하지 않는다.

결과는 **상태 → 근거 → 사용자 영향 → 수정 → 검증 결과**로 간결하게 전달한다. 미확인 항목은 확인했다고 쓰지 않는다. 구현·테스트·배포를 구분하며 이 스킬 자체가 배포나 외부 메시지 전송을 허가하지는 않는다.

근거의 적용 범위를 설명하거나 기준이 충돌할 때 [sources.md](references/sources.md)를 읽는다. 문헌의 원칙과 이 스킬의 엔지니어링 적용을 구분한다.

## 작업 계약과 연결

하네스의 작업 계약이 이미 있는 경우, 선정한 주요 시나리오를 해당 요구사항의 verification에 연결한다. 시작 상태 → 사용자 행동 → 화면·요청 결과 → 재진입 결과와 증거를 남긴다. 기존 객체를 편집하는 흐름에서는 조회·편집·저장 대상 ID의 연속성을 확인한다. 스킬 때문에 별도 계약이나 전체 E2E를 새로 강제하지 않는다. 단순 테스트 개수와 배포 자산 일치만으로 과업 성공을 판정하지 않는다.
