# 교차 관점 검사

## 검사 절차

1. 동일한 시나리오와 지위를 기준으로 모델 헤더를 대조한다.
2. 정체성 ledger로 같은 요소와 다른 요소를 구별한다.
3. 시나리오를 처음부터 끝까지 추적하며 각 경계의 의무를 적는다.
4. 정상·실패·복구의 중요한 경로에서 계약과 소유권을 대조한다.
5. 불일치를 근거 부족, 표현 누락, 모델 오류 또는 설계 위험으로 분류한다.
6. 영향, 반증 가능성, 최소 수정·검증 방향을 기록한다.

## 일관성 의무

| 연결 | 확인할 의무 | 실패 신호 |
|---|---|---|
| 시나리오→논리 | 정책·invariant 책임자 존재 | 동일 규칙의 충돌하는 소유자 |
| 논리→런타임 | 수신 계약과 reference 확보 | 연결 기구 없는 호출 |
| 런타임→프로세스 | 실행 주체·수명·상태 소유권 | 별도 process의 메모리를 직접 공유하는 가정 |
| 프로세스→배포 | artifact·host·환경 mapping | 설정과 diagram의 배치 불일치 |
| 데이터→런타임 | key·단위·오류·순서 보존 | 다른 tenant/작업의 결과 적용 |
| 데이터→배포 | 저장·replica·cache·복구 범위 | node 실패 후 durable 상태를 잃는 설계 |
| 보안→각 관점 | 권한 guard와 신뢰 경계의 실체 | UI 제어만으로 server 권한 주장 |
| 품질→결정 | 제약과 측정 가능한 반응 | 근거 없는 성능·복구 보장 |

## 방향과 제약

- source dependency 방향과 call 방향을 별도로 읽는다.
- runtime control이 interface를 통과하면 계약 정의와 binding 위치를 확인한다.
- 허용한 의존 예외는 이유·영향·검증 범위를 적는다.
- 초기화 순서와 import 부수 효과를 숨은 dependency로 검토한다.
- 전역 상태는 process·request·tenant·test scope를 함께 확인한다.
- 객체를 얻었다는 사실은 유효한 수명이나 사용 권한을 보장하지 않는다.

## 흐름과 상태

- 생성 전 또는 종료 후 메시지가 도달하는 경로가 있는가?
- async 시작을 완료와 혼동하거나 reply를 새 request로 해석했는가?
- duplicate, out-of-order, timeout, cancel 이후 효과의 주체가 정해졌는가?
- 병렬 branch가 합류할 때 필요한 완료 조건이 무엇인가?
- 선택되지 않는 branch를 기다리며 진행 불능이 되지 않는가?
- 대안 흐름의 merge를 병렬 흐름의 join으로 오해하지 않는가?
- 한 흐름의 종료와 전체 작업 종료가 구별되는가?
- 화면 이동과 서버의 durable transition은 독립적으로 성립하는가?

## 현재와 제안의 차이

현재 모델은 조사한 경로·revision·환경 안에서만 사실을 주장한다.
제안은 변경 요소, 전제, migration·rollback 방향과 검증할 위험을 명시한다.
기존 구현과 다른 것만으로 결함이라 하지 않고 의도한 계약과 대조한다.
현재 테스트가 고정한 동작이 올바른 요구인지 별도로 확인한다.
아직 없는 연결을 current 모델에 조용히 추가해 모순을 해결하지 않는다.

## 불일치 기록

`ID / 연결 관점 / 충돌한 주장 / 근거 / 위반 가능 계약 / 영향 /
반증 자료 / 최소 해결 / 검증 방법 / 미검증 범위`를 적는다.
단지 그림이 더 정돈돼 보인다는 이유로 구조 변경을 권하지 않는다.
모델의 부족과 실제 시스템 결함은 같은 주장이 아니다.
