# 결정과 검증

## 품질 시나리오

다음 항목을 한 세트로 기록한다.

- ID와 이해관계자, 관련 업무 시나리오
- 자극의 출처와 사건
- 정상·과부하·장애·유지보수 등 실행 환경
- 영향을 받는 대상과 경계
- 기대 반응, 허용되는 저하와 허용하지 않는 결과
- 측정 방법·임계값·관찰 기간
- 비용·규제·호환성·운영 제약
- 우선순위, 근거, 미정 항목

임계값은 요구 계약이나 합의에서 얻는다. 임의의 업계 평균으로 채우지 않는다.
기능 정확성과 품질 목표를 구분하되 품질을 위해 정확성을 훼손하는 대안은 드러낸다.
보안과 규제 제약을 성능·복구 편의의 단순 tradeoff로 제거하지 않는다.

## 요인 ledger

`요인 / 측정 시나리오 / 현재 유연성 / 예상 변화 / 이해관계자·다른 요인 영향 /
중요도 / 구현 난이도·위험 / 평가 담당·방법`을 연결한다.
예상 변화는 확정 요구가 아니다. 발생 가능성과 도입 시점의 근거를 남긴다.
대안에는 구축·구입·범위 조정·보류도 포함한다. 안전·법적 제약은 먼저 확인한다.

## 결정 기록

1. 질문과 상태: proposed/accepted/superseded 및 날짜·담당자
2. 관련 품질 시나리오와 hard constraint
3. 현재 구조와 문제의 근거
4. 유지, 작은 변화, 큰 변화 등 현실적인 대안
5. 선택과 동작 원리, 영향을 받는 관점
6. 장점뿐 아니라 비용·한계·새 실패 모드
7. 미해결 가정과 검증 계획
8. 도입·migration·rollback 방향
9. 재검토 조건과 대체한 이전 결정

패턴 이름은 작동 원리의 설명을 대신하지 않는다.
선택 당시 제약과 현재 제약이 다르면 결정의 유효성을 다시 평가한다.
특정 framework, transport, 언어 또는 deployment style을 보편 기본값으로 만들지 않는다.

## Probe 카드

| 항목 | 기록할 내용 |
|---|---|
| 질문 | 어떤 결정을 위해 무슨 사실이 필요한가 |
| 가설 | 조건과 예측 가능한 반응 |
| 반증 조건 | 무엇이 관찰되면 대안을 기각하는가 |
| 범위 | revision·환경·구성·입력·부하·대상 경계 |
| 방법 | 허용된 명령·절차·관찰 지점 |
| oracle | 요구 계약에서 도출한 기대 결과 |
| 성공 기준 | 임계값과 반복·관찰 조건 |
| 안전 | 권한·비용 상한·중단·정리·복구 조건 |
| 결과 | 실제 관찰과 증거 위치 |
| 한계 | 생략·대역·미실행 범위 |
| 결정 영향 | 유지·변경·추가 확인 |

## 위험에 맞는 실험

- 정책 독립성: UI·DB·network 없는 실행으로 실제 분리 여부를 확인한다.
- binding·mapping: 실제 구성에서 계약과 구현이 연결되는지 확인한다.
- 동시성: 실제로 가능한 순서 역전·중복·재시작 조건을 구성한다.
- 복구: 실패 지점, 남는 상태, 재시도와 중복 효과를 관찰한다.
- 배포: 선언한 artifact·환경 mapping을 검증하되 운영 변경은 별도 승인한다.
- 성능: 대표 데이터·구성·동시성에서 측정하고 병목과 오차를 남긴다.
- 결합 위험: 개별 대안이 성공해도 함께 쓸 때 자원·일관성·복구가 충돌하는지 확인한다.

정적 추적은 실행 증거가 아니고, 작은 prototype은 전체 시스템의 품질 보장이 아니다.
대역이 제거한 위험과 실제 경계에서 확인한 위험을 구별한다.
한 번의 성공을 최대 부하·장기 안정성·전체 환경 coverage로 확대하지 않는다.
명령을 작성한 것과 실행한 것, 실행한 것과 기대 결과를 확인한 것은 다르다.

## 피드백 루프

질문→가장 작은 모델→probe→관찰→결정 갱신을 반복한다.
실패한 가설도 유효한 결과다. 기준을 사후 변경해 성공으로 바꾸지 않는다.
불확실성이 줄지 않으면 더 많은 그림보다 가설·환경·oracle을 먼저 고친다.
