# 객체 설계 검증

만든 모델을 다시 읽어 승인하는 대신, **독립적인 요구·실제 자료·반례**와 대조한다.
문법, 의미, 요구 충족, 구현 일치와 실행 증거를 서로 다른 주장으로 검증한다.
이 절차는 다른 스킬팩에 의존하지 않는다. 관련 표기나 설계를 보완할 때 같은 팩의 전문 절차를 선택한다.

## 범위와 권한

- 리뷰는 기본 읽기 전용이다. 결함 발견이 수정·외부 게시·commit·배포를 허용하지 않는다.
- 실제 실행은 허가된 환경과 데이터에서만 한다. 위험한 시나리오는 모델 위에서 검토하고 미실행을 명시한다.
- 요청된 모델·변경·질문을 고정하고 주변 전체 시스템 검증으로 확대하지 않는다.
- 작성자와 같은 맥락을 공유하는 검토는 완전히 독립적인 효과 실험이 아니다.
- 관찰하지 않은 결과, 요구 ID, 코드 위치, 테스트 성공이나 이해관계자 승인을 만들지 않는다.

## 1. 검증할 주장과 정답 근거를 분리한다

대상 버전과 각 모델의 목적·관점·범위·추상화 수준을 먼저 적는다.
승인된 요구, 현재 구현, 설계 제안, 기존 테스트와 실제 운영은 서로 다른 증거다.
최신 파일이나 현재 구현을 자동으로 정답으로 삼지 않는다.

| 검증 주장 | 필요한 근거 | 단독으로 충분하지 않은 것 |
| --- | --- | --- |
| 그림이 열리거나 표기가 파싱됨 | 해당 도구에서 실제 렌더링·문법 검사 | 모델 의미·요구 충족·실행 결과 |
| 표기가 의도한 의미를 나타냄 | 표기 규칙·버전과 요소·관계의 해석 | 보기 좋은 배치·화살표 존재 |
| 시나리오와 계약을 충족함 | 요구·사건·전후 상태의 추적과 반례 | 작성자가 만든 정상 경로 한 개 |
| 현 코드와 일치함 | 실제 revision·호출·상태·의존 경로 | 이름 유사성·역공학 그림 생성 |
| 구현 결과가 맞음 | 해당 조건에서 실행한 결과와 외부 효과 | 모델 시뮬레이션·테스트 코드만 작성 |
| 사용자·운영자에게 적합함 | 필요한 실제 사람·업무·운영 근거 | 에이전트 평가·구조적 일관성 |

정답이 불명확하면 해당 결론을 보류하고, 독립적으로 확인 가능한 부분은 계속 검토한다.
검사할 모델 자체에서 기대값을 복사하여 같은 모델과 비교하는 순환 검증을 피한다.

## 2. 추적 사슬을 따라간다

현재 범위에서 실제 존재하는 연결만 확인한다. 모든 문서 유형을 새로 만들지 않는다.

1. 대표 사용자 목표와 주 시나리오·중요 확장을 선택한다.
2. 시스템 경계와 외부 사건이 내부 설계와 섞이지 않는지 본다.
3. 이벤트의 전제·결과·실패 보장을 관련 도메인 개념과 연결한다.
4. 보장을 책임지는 객체·모듈과 협력 메시지를 찾는다.
5. 메시지 수신자의 가시성과 공개 연산, 상태 소유권을 확인한다.
6. 필요한 구조·실행·배포 뷰가 같은 경계와 식별자를 나타내는지 본다.
7. 구현을 주장하면 실제 코드와 결과 검사를 연결한다.

끊어진 연결은 누락인지, 의도적인 상세 생략인지, 아직 결정하지 않은 것인지 분류한다.
요구에 없는 설계 요소도 품질 제약·통합·운영 필요를 충족할 수 있다. 연결이 없다는 이유만으로 제거하지 않는다.

## 3. 의미 충돌을 점검한다

표기 상세가 판단을 바꾸면 같은 팩의 `uml-modeling`을 확인한다.
기호가 모호하거나 도구가 일부 표기를 지원하지 않으면 범례·제약·한계를 남긴다.

- 같은 이름이 개념·설계 타입·저장 레코드·배포 인스턴스를 오가며 다른 뜻으로 쓰이는가?
- 개체 식별자, 역할, 단위, 시간 기준과 스냅샷 범위가 모델마다 같은가?
- 다중성과 연관 소유·생명주기 가정이 구체적인 객체 예와 모순되는가?
- 시스템 연산 계약이 결과 상태 대신 구현 알고리즘만 설명하거나 중요한 결과를 빠뜨렸는가?
- 상호작용의 메시지·생성·반환·비동기 순서가 실제로 가능한 협력인가?
- 상태의 사건·가드·효과와 진입·종료 동작이 기대 전이를 나타내는가?
- 활동의 분기·병합·병렬·동기화·종료가 원래 업무 조건을 보존하는가?
- 패키지 의존, 실행 통신, 데이터 흐름과 배포 연결을 같은 종류의 선으로 오인하는가?
- 일반화·인터페이스·패턴 참가자에게 맡긴 계약을 실제 대체·협력에서 지킬 수 있는가?

도메인 연관이나 UML composition을 DB 제약·삭제 정책의 실행 증거로 바꾸지 않는다.
역공학 도구가 생성한 상자·의존은 관찰의 출발점이다. 반사·설정·런타임 구성과 누락 범위를 별도 확인한다.

## 4. 반례로 설계를 압박한다

해당 기능에 의미 있는 것만 고른다. 모든 모델에 모든 장애 시나리오를 강제하지 않는다.

| 조건 | 물을 질문 |
| --- | --- |
| 최소·최대·빈 값·미확인 | 다중성·입력·결과의 경계와 의미가 유지되는가? |
| 정상 경로의 중요한 확장 | 실패 뒤 보장과 다음 행동을 누가 책임지는가? |
| 중단·재진입·취소 | 남은 상태·초안·이미 발생한 효과를 구별하는가? |
| 중복·늦은 응답·결과 미확정 | 같은 작업의 식별과 완료 의미가 흔들리지 않는가? |
| 일부 성공·동시 변경 | 보존할 성공과 불변조건, 충돌·보상 범위가 명확한가? |
| 역할·대상·설정 변화 | 권한·가시성·연관과 메시지 대상이 같은 맥락인가? |
| 예상한 변화 축 | 변경이 보호 경계 안에 머무는가, 추상화만 늘어나는가? |
| 품질 요구의 부하·장애 조건 | 관찰할 지표·환경·판정 조건과 구조 선택이 연결되는가? |

실제 지원하지 않는 재시도·보상·취소를 모델에 추가해 안전한 것처럼 만들지 않는다.
모델의 약점과 해결안은 구분한다. 더 큰 아키텍처나 더 많은 패턴이 자동 해결책은 아니다.
반례가 성립하지 않게 하는 기존 제약·보호 장치도 조사해 발견 사항에 함께 남긴다.

## 5. 코드와 실행 결과를 필요한 만큼 확인한다

구현 검증 요청에서는 실제 타입·호출자·설정·영속화·외부 효과·관련 테스트를 조사한다.
모델의 이름이 같다는 이유만으로 같은 개체·상태·실행 경계를 찾았다고 판단하지 않는다.

- 실제 변경 또는 이벤트가 어떤 상태를 읽고 누가 저장·통신·발행하는지 끝까지 추적한다.
- 테스트의 기대값이 요구나 독립 계약에서 왔는지, 방금 만든 모델을 그대로 복제했는지 본다.
- 중요한 불변조건과 실패 경계를 관찰하는 최소 단위·통합·시스템 검사를 선택한다.
- mock이나 생략이 검증하려는 위험을 제거했다면 그 한계를 표시한다.
- 기존 실패와 새 실패를 구별하고 실패 증거를 재시도 성공으로 지우지 않는다.
- 테스트가 실행되지 않았거나 0개가 실행됐으면 필요한 시나리오를 통과했다고 하지 않는다.
- 정해진 과업을 통과한 결과를 다른 버전·환경·데이터·운영 준비 전체로 확대하지 않는다.

문서 검토만 요청받았으면 실행 계획을 제안하되 이를 실행한 것으로 쓰지 않는다.
구조 변경을 수행했다면 오류·부수 효과·순서·공개 및 저장 형식의 보존 여부를 확인한다.

## 6. 발견을 분류하고 인계한다

**확인된 불일치 / 검증할 위험 / 미결정 계약 / 선택적 개선**을 나눈다.
“패턴을 쓰지 않음”, “UML이 적음”, “응집도가 낮음” 같은 라벨만으로 결함을 만들지 않는다.
각 발견에는 다음 중 판단에 필요한 내용을 포함한다.

> 위치·버전 → 기대 계약과 근거 → 트리거·경로 → 관찰된 모순 → 영향 → 반대 근거 → 최소 조치 → 확인 조건

모델·코드·실행의 증거 상태를 `표기 검사 / 의미 검토 / 코드 추적 / 실제 실행 / 미검증`으로 구분한다.
중요 모델의 비가역 정책·불명확한 사업 의미·고위험 경계는 적절한 결정권자에게 확인한다.
작은 수정마다 외부 검토자나 새 문서를 의무화하지 않는다. 검토 독립성이 부족하면 그 한계를 밝힌다.

## 종료 조건

- 요청한 모델·시나리오·변경과 검증 범위를 빠뜨리지 않았는가?
- 각 중요한 결론을 요구·자료·실행 결과로 역추적할 수 있는가?
- 가정과 현재 사실, 설계 제안과 승인·구현·배포를 분리했는가?
- 해결한 문제, 미검증 범위, 남은 결정과 가장 작은 다음 증거가 명확한가?

발견이 없으면 **검토 범위에서 근거 있는 불일치를 찾지 못했다**고 보고한다.
모델이 완전하거나 제품이 안전하다는 포괄적 보증으로 바꾸지 않는다.
