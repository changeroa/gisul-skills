# Clean Code: Functions

함수를 줄 수로 심사하지 않고, 독자가 호출부에서 목적을 이해하고 필요할 때만 세부 단계로 내려갈 수 있게 만든다. 함수 분리는 정보 숨김과 변경 국소화를 개선해야 한다. 단지 코드를 더 많은 이름으로 나누는 것은 목표가 아니다.

이름·주석·배치는 `clean-code-readability`, 객체와 클래스의 책임 이동은 `clean-code-objects`가 주 책임이다. 판본과 논쟁적 원칙의 적용 한계는 `skill://gisul/gisul/clean-code/references/sources-and-guardrails.md`를 따른다.

## 모드와 권한

리뷰 요청은 읽기 전용이다. 파일 수정은 사용자가 구현·리팩터링을 요청한 범위에서만 수행한다. 테스트·빌드 실행, commit·push·PR·배포와 외부 효과는 호스트와 저장소 정책 및 명시된 권한을 따른다. 사용자의 기존 변경을 덮어쓰거나 무관한 작업을 되돌리지 않는다.

## 1. 동작과 호출 맥락을 먼저 읽는다

1. 함수 정의, 모든 호출자, 사용하는 상태, 테스트와 실패 처리를 찾는다.
2. 입력, 반환, 예외, 상태 변경, I/O, 로그, 이벤트, 자원 사용과 순서를 적는다.
3. 공개·보호 콜백, 리플렉션 대상, 프레임워크 훅인지 확인한다. 사용처가 없다고 바로 삭제하지 않는다.
4. 관련 테스트를 변경 전에 실행하거나, 실행하지 못하면 정적 추적만 했다고 기록한다.
5. 이 함수가 자주 바뀌는 이유와 변경 시 함께 수정되는 코드를 찾는다.

리팩터링이라면 위 동작을 보존한다. 버그 수정이나 기능 변경이면 의도적으로 바꿀 계약을 먼저 분리한다.

## 2. 한눈에 읽히는 서사를 만든다

high-level function에는 정책과 순서를 남기고, 세부 구현은 의미 있는 이름 뒤로 숨긴다.

- 정상 경로의 주요 단계를 위에서 아래로 읽을 수 있게 한다.
- 한 함수 안에서 사업 정책, 데이터 변환, 저장 세부사항 사이의 추상화 수준이 급격히 오르내리는 흐름을 줄인다.
- 중첩된 branch나 loop는 이름이 새로운 의도를 표현할 때 추출한다.
- predicate를 추출하면 복잡한 조건이 어떤 질문인지 드러나는지 본다.
- caller가 답을 얻기 위해 helper 구현을 모두 열어봐야 한다면 interface가 너무 얕거나 이름이 부족한지 검토한다.
- 관련 helper는 호출 흐름이나 언어 관례에 맞춰 가까이 배치한다.

“한 가지 일”은 한 줄이나 한 호출이라는 뜻이 아니다. 더 높은 수준의 의미 있는 이름으로 분리할 수 있고 서로 다른 이유로 바뀌는 단계가 섞였을 때 분리를 고려한다. 한 줄을 다른 말로 반복하는 helper, 공유 상태만 늘리는 추출, 화면을 계속 오가게 하는 잘게 쪼개기는 피한다.

## 3. 함수 크기와 응집도를 함께 본다

큰 함수는 신호이지 자동 결함이 아니다. 다음 중 실제 비용이 있는지 확인한다.

- 함수 이름보다 낮은 여러 관심사가 섞여 있다.
- 한 부분의 변경이 무관한 부분을 깨뜨릴 수 있다.
- 일부 경로만 이해하거나 테스트하기 어렵다.
- 많은 지역 변수와 상태가 긴 거리에서 상호작용한다.
- branch마다 전혀 다른 정책과 의존성이 필요하다.

추출 뒤 다음 비용도 비교한다.

- 인수가 늘고 같은 지역 상태가 여러 helper에 퍼지는가?
- 부수 효과와 실행 순서가 더 숨겨지는가?
- helper 이름이 구현 한 줄을 되풀이할 뿐인가?
- 순차 알고리즘을 이해하려고 여러 파일과 함수를 왕복해야 하는가?
- 분리된 두 함수가 항상 함께 바뀌고 독립적으로 의미가 없는가?

후자의 비용이 더 크면 cohesive한 긴 함수나 다시 합친 깊은 추상화가 낫다. 고정된 최대 줄 수, 중첩 수, 함수 개수로 판정하지 않는다.

## 4. 인수와 반환 계약을 명확히 한다

인수는 호출자와 함수 사이의 결합이다. 적을수록 좋다는 기본값은 쓰되 의미와 언어 관례를 우선한다.

- 인수 순서가 자연스럽고 호출부에서 의미를 알 수 있는지 본다.
- 같은 개념을 이루는 여러 값은 실제 응집성이 있을 때 parameter object나 domain type으로 묶는다.
- 인수가 많아도 keyword/named argument로 명확하고 안정된 API라면 억지 객체를 만들지 않는다.
- boolean flag가 서로 다른 동작을 선택해 호출부가 `true`의 뜻을 추론해야 한다면 명명된 option, enum, 또는 별도 동작을 검토한다.
- 단순 setter나 명확한 enable/disable API처럼 boolean 자체가 계약인 경우는 허용한다.
- output parameter보다 return value나 result object가 흐름을 명확히 하면 바꾼다. 언어·성능·FFI 관례상 output parameter가 적절한 경우는 유지한다.
- 전달되지 않은 global, clock, environment, filesystem, singleton도 숨은 인수다. 테스트와 이해를 방해할 때 경계에서 명시한다.

API를 더 예쁘게 보이게 하려고 기존 소비자를 깨지 않는다. public signature를 바꿀 때는 migration과 호환 계층을 포함한다.

## 5. 명령, 조회와 부수 효과를 드러낸다

- 조회처럼 보이는 함수가 상태를 바꾸거나 I/O를 일으키면 이름과 API가 그 사실을 숨기는지 본다.
- 상태 변경과 질문을 나누면 호출부가 명확해질 때 Command–Query Separation을 적용한다.
- atomic한 `pop`, get-or-create, compare-and-set처럼 분리가 race나 중복 작업을 만드는 경우는 하나의 연산으로 유지한다.
- 내부 mutation이 함수 밖에서 관찰되지 않고 reasoning을 단순화한다면 순수성을 흉내 내려고 복잡하게 만들지 않는다.
- 외부 부수 효과가 여러 곳에 흩어졌다면 정책 계산과 effect 실행을 구별해 테스트 가능한 seam을 만든다.
- init → configure → execute 같은 필수 순서를 문서만으로 강요하지 말고 가능한 경우 API, type, state machine으로 표현한다.

부수 효과의 유무뿐 아니라 발생 순서, 중복 가능성, 실패했을 때 남는 상태를 계약으로 본다.

## 6. 제어 흐름과 오류를 단순화한다

- guard clause가 비정상 조건을 일찍 끝내고 정상 경로를 드러내면 사용한다. 여러 return을 금지하는 규칙은 두지 않는다.
- branch마다 공통 정책이 반복되면 먼저 공통 부분을 분리하되 실행 순서가 변하지 않는지 확인한다.
- switch나 type check가 여러 위치에서 같은 분기를 반복하고 새 타입 추가 때 함께 바뀐다면 한 경계에 모으거나 polymorphism/data table을 검토한다.
- 단순하고 안정된 switch 하나를 class hierarchy로 폭발시키지 않는다.
- 지원되는 언어에서는 exception이 error-code 전달보다 정상 경로를 선명하게 만들 수 있다. 그러나 Go식 명시적 오류, C API, 성능·복구 계약처럼 error value가 관용적이면 따른다.
- `try/catch`가 큰 함수의 중심 흐름을 감싸면 오류 정책을 이름 있는 작은 단위로 분리할 수 있는지 본다.
- 예외를 정상 분기 수단으로 남용하지 않고, 오류를 삼키거나 원인 정보를 잃지 않는다.
- 성공/실패가 부분 상태를 남기는지, cleanup이 모든 경로에서 실행되는지 확인한다.

## 7. 중복은 의미로 판정한다

두 코드가 비슷하다는 이유만으로 합치지 않는다.

- 동일한 사업 규칙이나 공식이 여러 위치에 있어 반드시 함께 바뀌는 **본질적 중복**은 한 권위 있는 구현으로 모은다.
- 현재 우연히 같은 모양이지만 다른 actor와 이유로 변하는 **우연한 유사성**은 분리해 둔다.
- 합친 함수가 flag와 조건으로 서로 다른 사례를 다시 갈라놓는다면 잘못된 추상화인지 의심한다.
- 소량 중복과 잘못된 공통 추상화의 비용을 비교한다. 미래의 세 번째 사례를 상상해 미리 framework를 만들지 않는다.

## 8. 작은 검증 주기로 리팩터링한다

권장 순서는 다음과 같다.

1. 특성 테스트 또는 기존 테스트로 현재 계약을 고정한다.
2. rename, extract variable, guard clause처럼 한 종류의 변환만 적용한다.
3. 가장 가까운 테스트와 정적 검사를 실행한다.
4. 의미 있는 이름으로 extract method를 적용한다.
5. 상태와 인수가 과도해지면 책임 이동이나 객체화를 검토한다.
6. 중복 정책과 오류 처리를 정리한다.
7. 각 단계 후 green 상태를 유지하고, 실패 원인을 모르면 더 쌓지 않는다.
8. 최종 diff에서 기능 변경과 기계적 이동이 섞였는지 확인한다.

TDD, tests-after의 작은 bundle, 다른 규율을 선택할 수 있다. 중요한 것은 짧은 피드백, 실제 설계 검토, 정리 단계와 회귀 증거다.

## 결과

리뷰에서는 함수 길이 자체가 아니라 독자가 알아야 할 숨은 계약, 혼합된 책임, 실제 변경 비용을 위치와 함께 제시한다. 수정했다면 보존한 동작, 적용한 변환 단위, 테스트 결과를 적는다. 더 작게 나누지 않은 경우에도 응집도, 탐색 비용, 성능이나 언어 관례 같은 이유를 설명할 수 있으면 유효한 결정이다.
