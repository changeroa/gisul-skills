# Review Explainer

독자는 시스템 구조를 모를 수 있다. 읽는 순서대로 필요한 맥락을 제공하고, 그림과 실제 소스를 오갈 수 있는 문서형 웹을 만든다. 기본 결과는 항목 목록과 스크롤하는 본문이다. 발표용 슬라이드나 단계별 강제 넘김은 사용자가 따로 선택했을 때만 사용한다.

## 1. 설명할 사실과 범위를 고정한다

- 사용자가 가리킨 리뷰 보고서·발견 사항을 입력으로 사용한다. 특정 리뷰의 지적을 설명하라는 요청을 저장소의 전체 이슈 목록으로 바꾸지 않는다.
- 저장소, 기준 커밋, 발견 사항 ID, 판정과 근거를 기록한다. 과거 커밋의 설명을 현재 main 재감사처럼 보고하지 않는다.
- 확정 결함, 추가 확인 후보, 재검증에서 제외한 후보를 구분한다. 제외 항목의 두 그림은 초기 의심/재검증 결과다. 수정 전/후로 부르지 않는다.
- 관찰한 코드 동작, 제안한 수정, 실제 구현, 실행 검증, 배포를 별개로 표시한다. 이 설명서 제작은 제품 수정·외부 이슈 등록·메시지 전송 권한을 추가하지 않는다.

### 리뷰 근거를 설명으로 넘기는 단계

리뷰 결과를 설명 자료로 전환할 때 Gisul의 `preserve-decisions`를 검색하고 현재 리비전에 고정해 로드한 뒤, **Carry reviewed evidence into explanation or implementation** 절을 적용한다. 원본 리뷰 보고서와 근거 기록을 공통 입력으로 사용하며 정보 보존 규칙을 이 스킬에 복제하지 않는다. 이미 기록이 있으면 그 기록을 읽고 누락·변경된 부분만 보완한다. 원본 이름, 실행·저장 위치, 판단 전제, 반증, 개선안 근거가 설명을 줄이는 과정에서 사라지지 않았는지 대조한다.

해당 스킬을 사용할 수 없으면 그 한계를 밝히고 기존 리뷰 기록으로 가능한 설명을 계속한다. 추측으로 빈칸을 채우거나 인계가 완료됐다고 보고하지 않는다. 단순 문구·스타일 수정에는 이 인계 절차를 다시 실행하지 않는다.

## 2. 해결책을 제시하기 전에 상황에 맞는 베스트 프랙티스를 조사한다

이 단계는 해결책을 새로 제안하거나 기존 개선안을 권장안으로 설명하기 전에 반드시 수행한다. 조사 없이 익숙한 패턴을 “베스트 프랙티스”로 제시하지 않는다.

1. **실제 맥락을 먼저 확인한다.** 배포 설정 → 실행 진입점 → 문제가 되는 코드와 상태의 위치를 연결한다. 관련 런타임·제품 버전, 프로세스/인스턴스 경계, 동시 요청, 상태의 소유자·수명·영속성, 데이터 규모, 지연·비용·운영 제약 중 해결책에 영향을 주는 조건을 확인한다. 설정 파일의 의도, 실제 배포 관측, 미확인 가정을 구분한다. 클라우드 제공자 이름만으로 실행 모델을 추정하지 않는다. 예를 들어 Worker가 앞에 있다는 사실은 뒤의 Container에서 실행되는 상태 객체가 Worker isolate에 있다는 근거가 아니다.
2. **확인한 조건으로 자료를 조사한다.** 해당 런타임·서비스·DB의 공식 문서, 버전별 제약, 공식 권장 패턴과 관련 설계 자료를 찾아 읽는다. 기술적 권고는 일차 자료로 뒷받침하고 출처 URL·적용 버전/확인 시점을 남긴다. 공유 대화나 일반적인 조언은 조사할 가설이며 이 시스템의 구조를 입증하는 근거가 아니다. 같은 조건·버전에 대해 이미 확인한 자료는 재사용할 수 있으나 최신성과 적용 범위를 먼저 확인한다.
3. **이 시스템에 적용되는 이유를 판단한다.** 자료의 전제와 실제 구성을 대조하고, 그 권고가 해당 결함을 막는 이유, 기존 보호 장치, 적합한 대안과 비용·복잡도·일관성의 차이를 설명한다. 규모나 요구가 뒷받침하지 않는 분산 설계를 기본 해법으로 삼지 않는다. 현재 구성에서도 발생하는 문제와 확장·환경 변경 때만 생기는 위험을 구분한다.
4. **근거에서 제안과 검증으로 연결한다.** 개선안에 ‘확인된 환경 조건 → 조사한 권고와 출처 → 적용 이유와 한계 → 제안 → 검증 방법’을 남긴다. 공식 문서가 말한 사실과 작성자의 추론을 구분한다. 자료가 불충분하거나 접근할 수 없으면 조사 한계를 밝히고, 해결안을 검증된 권장안으로 확정하지 말고 조건부 후보와 필요한 확인을 제시한다.

독자에게는 해결책보다 먼저 그 문제에 필요한 실행 구조와 전제를 보여준다. 여러 실행 경계가 결론에 영향을 주면 작은 배치도 또는 컴포넌트 그림을 제공하고 현재 이슈의 위치를 표시한다. 상세 조사 기록은 접힌 근거 영역에 둘 수 있지만 적용 이유와 중요한 조건은 숨기지 않는다.

## 3. 요약 전에 의미 모델을 만든다

각 이슈에서 다음 질문에 답한 뒤 문장을 줄인다.

1. 어떤 사용자가 무엇을 하다가 어떤 결과를 겪는가? 기대 동작은 무엇인가?
2. 관련 대상은 어디에 존재하는가? 브라우저, API 프로세스, 요청 함수의 지역 변수, DB 컬렉션, 외부 저장소 등을 구별한다.
3. 어느 것이 원본이고 어느 것이 사본인가? 누가 읽고 쓰며, 언제 갱신되거나 폐기되는가?
4. 어떤 호출 순서·조건·상태 전이·의존 관계 때문에 문제가 생기는가?
5. 개선안은 무엇을 바꾸며, 그 결과를 성립시키는 정책·환경·측정 조건은 무엇인가?

“캐시의 활성 객체”로 끝내지 않는다. 예: “API 서버의 `MongoStore.state.hospitals` Map에 보관한 병원 사본. DB의 `hospitals` 컬렉션과 별개이며, 요청 함수가 복사한 값은 다른 요청의 저장으로 자동 갱신되지 않는다.” 중요한 위치·소유자·수명·인과를 먼저 남긴다. 구현 세부를 무조건 늘리는 것이 정보 밀도 개선은 아니다.

## 4. 실제 이름과 쉬운 설명의 역할을 나눈다

- UML의 함수, 클래스, 필드, 컬렉션, 이벤트, 파일, 경로, 환경 변수는 대응하는 소스 이름을 그대로 쓴다. 쉬운 별명으로 교체하지 않는다.
- 그림 앞에 **실제 이름 → 존재하는 위치와 역할 → 코드 근거** 대응표를 둔다. 그림 밖 설명에서는 독자의 언어로 풀어 쓴다.
- 속성 이름과 저장소 이름이 다를 수 있다. 예: `packageUploads` 속성이 `contentPackageUploads` 컬렉션에 연결된다면 각각 표시한다. 같은 `refresh`도 어느 파일/클래스의 함수인지 구분한다.
- 소스에 이름이 없는 핸들러는 모듈과 실제 라우트로 식별한다. 익명 반환 객체는 `: Type`처럼 익명임을 드러낸다. 그럴듯한 함수·변수 이름을 만들어 현재 코드처럼 표시하지 않는다.
- 새로 제안한 이름·처리에는 `«proposal»`, 미확인 환경에는 `«unverified»`처럼 상태를 밝힌다. 설명용 값은 예시임을 밝힌다.
- 모든 이름과 연결 관계를 기준 소스에서 확인한다. 검색 문자열이 존재하는 것만으로 소유자·호출·분기 의미가 입증되지는 않는다. 소스 도구는 현재 작업 환경의 검색/LSP 지침을 따른다.

## 5. 이슈의 질문에 맞는 UML을 선택한다

| 독자가 확인할 질문 | 적합한 기본형 |
| --- | --- |
| 어떤 요청이 먼저 읽고 나중에 쓰는가? | 시퀀스 |
| 검사·조건에 따라 어느 경로로 가는가? | 활동 |
| 이벤트를 받으면 상태가 어떻게 바뀌는가? | 상태 |
| 어느 객체의 필드 값이 결과에 사용되는가? | 객체 |
| 구현·계약·소비자가 어떻게 의존하는가? | 컴포넌트 |
| 어떤 프로세스·배포 환경·외부 시스템의 경계인가? | 배치 |

필요하면 다른 UML 종류를 선택한다. 종류의 개수를 채우지 말고 선택 이유와 화살표의 의미를 한 문장으로 적는다. 모든 이슈를 시퀀스로 만들거나 같은 박스에 종류 라벨만 바꾸지 않는다. 대안 저장소 두 개를 연속 호출처럼 그리지 않는다. 문서/타입의 의존 화살표를 시간 순서처럼 설명하지 않는다. 전후에는 공통 이름·방향·비교 축을 유지한다.

그림은 선택한 유형의 문법을 사용한다. 생명선/메시지, 시작·종료/조건 분기, 상태/이벤트, 밑줄 객체/필드, 컴포넌트 의존, 배포 노드/경계를 구별한다. 비교용 SVG와 내려받는 정의의 유형·내용도 일치시킨다.

## 6. 승인된 문서형 읽기 순서를 재현한다

1. **제목 + 짧은 상황 + 판정:** 첫 화면에서 사용자 영향과 확정 여부를 이해한다.
2. **기대하는 동작:** 정상 계약을 먼저 알린다.
3. **먼저 알아둘 대상과 역할:** 보통 핵심 대상 2–4개에 위치·역할을 붙인다. 모든 구현 요소를 나열하지 않는다.
4. **쉬운 전후 비교:** 같은 상황의 이전/개선안을 짧은 인과 단계로 비교한다. 기본 3단계가 유용하나 사실을 왜곡하며 맞추지 않는다. 핵심 원인 한 문장을 붙인다.
5. **접힌 ‘UML과 코드로 자세히 보기’:** 읽는 방향/초점 → 코드 이름 대응표 → UML 선택 이유 → 그림 → 상세 저장 위치·갱신/수명 → 변경점·검증 조건·근거 순서다.

왼쪽 항목 목록에는 제목, ID, 판정별 필터, 검색과 현재 위치가 있다. 본문은 자연스럽게 스크롤한다. 처음부터 코드와 UML을 모두 해독하도록 만들지 않는다.

UML은 **이전 크게**를 기본으로 하고 이후 크게/전후 함께를 제공한다. 두 그림을 항상 반씩 축소하지 않는다. 확대, SVG와 정의 저장, 해시 링크, 항목 이동을 제공한다. 모바일은 문장을 세로 배치하고 넓은 그림은 그림 영역 안에서만 가로로 읽게 하며 같은 내용의 큰 글씨 설명을 함께 둔다.

구현할 때 [references/build-contract.md](references/build-contract.md)를 읽는다. 동봉한 `assets/explainer.html`과 `scripts/build_explainer.py`가 이 구성을 재현한다. 자산과 실행 스크립트는 작업용 출력 디렉터리에 내려받아 사용한다. 워크플로 스킬 본문을 로컬 스킬 폴더에 설치하거나 복제하지 않는다. 기존 사용자 산출물을 바꿀 때는 승인된 버전과 회복 경로를 먼저 보존한다.

## 7. 독자의 읽기 흐름으로 검수한다

[references/quality-gates.md](references/quality-gates.md)를 읽고 결과를 기록한다. 해결책마다 위 2절의 맥락 확인·일차 자료 조사·적용 판단이 있는지 확인한다. 출처가 있어도 전제가 이 시스템과 다르거나 실제 실행 경계가 연결되지 않으면 수정 필요로 판정한다. 정적 생성 성공, 실제 브라우저 동작, 시각 검수, 사람의 이해도 검증은 서로 다르다.

브라우저 자동화는 현재 `aside-browser` 지침을 읽고 수행한다. 직접 화면과 DOM을 살펴야 하므로 직접 검사 경로를 사용한다. 각 항목의 설명과 모든 전후 그림을 확인하고, 각 UML 종류·가장 긴 이름·가장 복잡한 항목·불확실/제외 판정을 화면으로 검사한다. 데스크톱과 좁은 폭을 확인하고 의미 또는 읽기 흐름 문제를 고친 뒤 관련 범위를 다시 확인한다.

최종 응답은 바로 열리는 URL, 핵심 변경, 실제 검증과 남은 한계를 짧게 전달한다. 미리보기 서버는 독자가 검토할 수 있게 유지하고 경로·PID·종료 방법을 기록한다. 사람의 이해도 테스트 없이 “독자가 이해함”을 측정한 것처럼 보고하지 않는다.
