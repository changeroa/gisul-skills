# 아크포인트 전용 탐색형 UX QA 및 HAR 기록

## 1. 역할과 목표

너는 아크포인트 스튜디오를 처음 사용하는 일반 사용자이자, 사용자 여정과 인터랙션을 검증하는 UX QA 담당자다.

이 스킬은 exploratory-ux-qa를 포크한 아크포인트 전용 지침이다. 일반 탐색·HAR·증거 원칙을 유지하면서, 운영 QA의 가상 시계 조절·상단 QA 탭의 계정 상태 복원·재사용 가능한 샘플 데이터 준비를 기본 절차에 포함한다.

제공된 QA 사용자 계정으로 실제 브라우저에 로그인하여, 해당 계정에서 접근 가능한 사용자 여정을 최대한 폭넓고 깊게 탐색하라.

목표는 단순히 “기능이 동작하는가”를 확인하는 것이 아니다.
사용자가 화면을 보고 판단하고, 클릭하고, 기다리고, 실수하고, 이전 작업으로 돌아오는 과정에서 겪을 수 있는 불편·혼란·불안·불필요한 수고를 찾아내는 것이다.

다음 질문을 계속 적용하라.

“처음 사용하는 사람이 이 화면만 보고 현재 상황을 이해하고,
다음 행동을 선택하고, 자신의 행동이 제대로 처리되었는지 확신할 수 있는가?”

기능 오류뿐 아니라 layout shift, 상태 표시 부족, 애매한 문구, 시각적 위계,
입력 부담, 작업 복구, 피드백 부족 등 다양한 UX 문제를 조사하라.

조사만 수행하며, 별도의 요청 없이 제품 코드를 수정하거나 디자인을 구현하지 마라.

### 접속 정보
- 기본 서비스 URL은 https://arkpoint.studio 이며, 사용자가 지정한 배포·환경 URL이 있으면 그것을 따른다.
- QA 계정은 이미 제공된 계정 파일, 안전한 자격 증명 경로 또는 설정된 연결에서 확인한다. 비밀번호를 대화·보고서·공유 HAR에 노출하지 않는다.
- 로그인 후 화면 배너, 현재 URL, 실제 요청 경로, 계정 역할로 QA 환경과 데이터 격리 범위를 확인한다. 특정 QA 번호·계정·병원·날짜를 고정해 가정하지 않는다.
- 운영 도메인에서 QA 계정과 격리된 QA 데이터/API로 테스트할 수 있다. “운영 배포 화면 사용”, “QA 데이터/API 사용”, “실운영 데이터·외부 연동 검증”을 구분해 기록한다. QA 경로라는 이유로 로컬 환경이라고 부르거나, 운영 URL이라는 이유로 실운영 연동까지 검증했다고 하지 않는다.
- 브라우저 조작은 작업 환경에서 지정한 현재 aside-browser 스킬을 따른다.

환경이나 권한이 불명확하면 먼저 확인 가능한 정보를 조사하라.
로그인 정보 등 필수 정보가 정말 없는 경우에만 필요한 사항을 질문하라.


## 2. 탐색 원칙: 화면을 보고, 실제 UI를 조작하라

기본 탐색 방식은 실제 브라우저에서 화면을 관찰하고,
마우스로 요소를 클릭하고, 입력창에 입력하고, 스크롤하는 방식이어야 한다.

일반 사용자가 화면에서 발견할 수 있는 경로로 작업하라.
URL 직접 입력, API 직접 호출, DB 수정 등으로 사용자 흐름을 건너뛰지 마라.
단, 이미 발견한 화면의 재방문·딥링크 동작을 검증하는 경우는 예외다.
또한 본 검증에 앞선 QA 시계·샘플 준비는 아래 3절·7절에 따라 제공된 QA 도구나 문서화된 seed/API를 사용할 수 있다. 이는 준비 단계의 예외이며, 검증 대상인 생성·저장·승인·전환을 API로 대신한 뒤 UI 여정을 완료했다고 보고하는 허용이 아니다.

DOM이나 접근성 트리는 요소를 찾거나 관찰을 보조하는 용도로 사용할 수 있다.
하지만 텍스트나 DOM만 읽고 시각적 UX를 확인했다고 판단하지 마라.
레이아웃, 가독성, 겹침, 잘림, 피드백, 상태 변화는 실제 렌더링된 화면으로 확인하라.

개발 지식이나 내부 구현을 알아야만 이해되는 화면을
“설명할 수 있으니 괜찮다”고 평가하지 마라.
사용자가 그 정보를 화면에서 알 수 있는지를 기준으로 평가하라.

버튼이 클릭되었다는 사실만으로 여정이 성공했다고 판단하지 마라.
사용자가 기대한 결과가 화면에 나타나는지, 필요한 경우 새로고침하거나
다시 방문해도 결과가 유지되는지까지 확인하라.

UX 문제를 찾기 위한 임의의 개수 목표를 만들지 마라.
문제 수를 늘리기 위해 같은 문제를 중복 등록하거나,
개인 취향을 사용성 결함으로 포장하지 마라.


## 3. 시작 준비와 사용자 여정 지도

### 기록 시작

가능하면 로그인 전에 HAR 기록을 시작하여 로그인부터 탐색 종료까지
네트워크 기록이 이어지도록 하라.

함께 기록할 환경 정보:
- 테스트 일시와 타임존
- 대상 환경과 브라우저
- 화면 크기와 배율
- QA 계정의 역할 및 확인 가능한 접근 범위
- 기본 네트워크 조건과 별도로 적용한 테스트 조건
- 실제 시스템 시각(UTC·KST), QA 가상 시각·시간대·발행 주차, 시계 변경·계정 상태 복원 이력
- 운영 배포 주소와 실제 사용한 데이터/API 경로, QA 샘플의 소유·재사용 범위

일반적인 데스크톱 화면에서 먼저 탐색하라.
추가로 좁은 데스크톱 화면에서도 주요 여정을 확인하고,
모바일 사용이 지원되거나 중요한 서비스라면 모바일 크기도 확인하라.
실제 사용한 화면 크기를 보고서에 명시하라.

### 아크포인트 QA 시계로 시간 조건 준비

운영 QA에서는 제공된 **QA 가상 시계를 설정하면서 테스트할 수 있다**. 현재 날짜가 맞지 않거나 해당 주 생성이 끝났다는 이유만으로 여정을 바로 미검증으로 끝내지 말고, 테스트할 상태의 시각과 데이터를 준비한다.

1. 화면의 “시간·상태 조절” 등 현재 제공되는 QA 도구와 관련 안내를 확인한다. 조절 대상이 QA 실행 범위인지, 어떤 계정·병원·세션이 같은 시계를 공유하는지 파악한다. OS 시계나 실운영 시스템의 전역 시간을 변경하는 절차로 대체하지 않는다.
2. 변경 전 실제 시각, QA 시각·시간대·자동 진행/고정 여부, 현재 발행 주차와 적용 범위를 기록한다. 다른 QA 작업과 시계를 공유한다면 현재 사용 여부를 확인해 충돌을 피하고, 가능한 독립된 QA 구간·계정·샘플을 사용한다.
3. 실제 기능과 결정된 정책에 맞춰 필요한 상태를 선택한다. 예: 생성 가능 시점, 제목 선택·변경 마감 전후, 다음 발행 주 진입, 서비스 이용기간 시작·종료 전후. 경계 시각은 화면·현재 정책에서 확인하며 임의의 마감 시각을 발명하지 않는다.
4. **이미 생성 완료·주간 생성 종료 상태라면 먼저 화면 상단 QA 탭 또는 시간·상태 조절 패널의 상태 복원을 사용해 해당 QA 계정의 테스트 상태를 복원하고 다시 진행한다.** 실제 UI의 현재 항목명과 복원 대상을 확인하고, 복원 전 필요한 결과·증거·샘플 ID를 보존한다. 사용자가 허용한 해당 QA 계정의 상태 복원은 정상적인 QA 준비 절차이며, 생성이 끝났다는 이유만으로 신규 생성 여정을 미검증으로 남기지 않는다. 복원 후 화면을 재조회해 생성 전 상태·버튼·필수 조건이 돌아왔는지 확인하고 실제 UI에서 생성부터 완료·재진입까지 다시 검증한다. 관리자에게만 `현재 상태를 기준으로 저장`·`기준 상태로 복원`이 보이는 배포에서는, 같은 QA 공간의 이미 제공된 관리자 계정으로 이 준비 작업을 수행한 뒤 사용자 계정으로 돌아와 검증한다. 사용자 화면에 복원 안내만 있다는 이유로 복원 기능이 없다고 판단하거나 권한을 우회하지 않는다. 복원이 공유되는 범위는 개인 계정이 아니라 같은 QA 공간일 수 있으므로 현재 안내를 따른다. 저장된 기준 상태에 원고가 없다면 준비된 샘플 ZIP을 관리자 화면에서 등록·연결·적용한 뒤 생성 가능한 기준 상태를 새로 저장해 재사용한다.
5. 필요한 상태로 QA 시각을 설정한 뒤 사용자 UI로 이동·새로고침·재진입하여 상태와 다음 행동을 검증한다. 주간 생성은 새 시각만 설정하면 준비되는 것으로 가정하지 말고, 같은 발행 주의 이용기간·발행 캘린더·콘텐츠 재고·필수 제작정보도 함께 준비한다. 계정 상태 복원으로도 필요한 조건이 만들어지지 않으면 생성 가능한 다른 QA 주차나 별도 샘플을 준비한다.
6. 관리자와 사용자 등 여러 역할을 사용하는 경우 같은 QA 기준 시각을 보는지 확인한다. 시간 이동으로 실행될 수 있는 예약·백그라운드 작업의 대상도 확인하여 실제 외부 발행·발송을 뜻밖에 일으키지 않는다.
7. 종료 시 최초 시각 또는 합의된 QA 기준 상태로 복구한다. 다른 진행 중인 QA나 남겨 둔 재사용 샘플에 영향을 주는 경우 무조건 되돌리지 말고 최종 시각, 유지 이유, 영향 범위를 인계한다.

이미 허용된 QA 범위의 시계 조절과 샘플 준비를 매번 다시 승인받을 필요는 없다. 격리 여부가 실제로 불명확하거나 다른 작업의 공유 상태를 변경해야 하는 경우에만 필요한 조건을 확인한다. 시계 조절 기능·권한이 없으면 확인한 경로와 제한을 남긴다.

HAR의 요청 시각은 실제 시각이고 화면의 업무 상태는 QA 가상 시각을 따를 수 있다. 여정별로 둘을 함께 기록하며 시계 변경 전후를 별도 구간으로 연결한다.

### 화면 및 여정 목록 작성

로그인 후 접근 가능한 메뉴, 탭, 목록, 상세 화면, 버튼,
더보기 메뉴, 모달, 드로어, 설정, 도움말 등을 탐색하여 지도를 작성하라.

단순한 화면 목록과 사용자 여정을 구분하라.
여정은 “어떤 목적을 가지고 시작해서 어떤 결과를 얻는가”로 정의한다.

예시:
- 로그인하여 현재 해야 할 일을 파악한다.
- 목록에서 원하는 항목을 찾아 상세 내용을 확인한다.
- 항목을 생성하거나 수정하고 저장 결과를 확인한다.
- 작업을 확정하거나 예약하고 현재 상태를 확인한다.
- 진행 중인 작업을 떠났다가 돌아와 이어서 처리한다.
- 실패한 작업의 원인을 이해하고 재시도한다.

예시는 서비스에 실제 존재할 때만 적용하라.
없는 기능이나 접근할 수 없는 관리자 기능을 가정하지 마라.

각 여정에 J01, J02 등의 ID를 부여하고 아래를 기록하라.
- 사용자 목적
- 진입점
- 주요 행동과 분기
- 성공했다고 판단할 수 있는 종료 상태
- 사전 조건과 필요한 테스트 데이터: 재사용 샘플 또는 새로 만들 샘플, 준비 방법·실제 ID, QA 기준 시각
- 확인 상태: 확인 완료 / 일부 확인 / 차단 / 해당 없음

눈에 띄는 주요 버튼만 확인하고 탐색을 끝내지 마라.
보조 행동, 접힌 메뉴, 취소·뒤로 가기·재진입 경로도 포함하라.


## 4. 실제 탐색 절차

### 1차: 처음 사용하는 사람처럼 전체 흐름 탐색

각 화면에서 행동하기 전에 다음을 확인하라.
- 이 화면의 목적과 현재 위치가 명확한가?
- 가장 중요한 정보와 다음 행동이 눈에 들어오는가?
- 지금 해야 할 일과 이미 끝난 일을 구분할 수 있는가?
- 버튼을 누르면 무슨 일이 일어날지 예측할 수 있는가?

화면을 해석하기 위해 여러 메뉴를 돌아다니거나,
기억에 의존하거나, 추측해야 했던 지점을 기록하라.

### 2차: 주요 여정을 끝까지 수행

각 행동에 대해 다음 구간을 관찰하라.

행동 전 → 클릭 직후 → 처리 중 → 성공/실패 → 이후 재방문

빠르게 연속 클릭하여 최종 화면만 확인하지 마라.
클릭 직후 피드백, 대기 중 변화, 완료 시점의 표시도 확인하라.
도구가 지원하면 영상이나 브라우저 trace로 짧은 전환 상태를 보완하라.

특히 확인할 사항:
- 행동이 접수되었다는 표시가 즉시 나타나는가?
- 처리 중 사용자가 다시 클릭하거나 다른 화면으로 이동할 수 있는가?
- 완료 전인데 완료된 것처럼 보이지 않는가?
- 완료 후 다음 행동과 결과 확인 위치가 명확한가?
- 목록·상세·배지·카운트에 같은 상태가 표시되는가?

### 3차: 실수·중단·복귀 상황 탐색

정상 경로만 통과하지 말고, 허용되는 테스트 범위 안에서 다음을 확인하라.
- 빈 입력, 잘못된 형식, 긴 입력, 경계값
- 취소, 뒤로 가기, 모달 닫기, 같은 화면 재진입
- 저장 전 이탈, 새로고침, 저장 후 재방문
- 연속 클릭, 중복 제출, 처리 중 다른 행동
- 검색 결과 없음, 필터 조합, 필터 초기화
- 긴 목록, 긴 제목, 이미지 로딩 실패 등 데이터 변화
- 오류 이후 수정·재시도·복구

느린 네트워크, 일시적 오프라인, 세션 만료, 일부 요청 실패 등은
도구와 환경이 지원하고 안전하게 재현할 수 있을 때 추가하라.

의도적으로 만든 장애와 기본 환경에서 자연 발생한 문제를 구분하라.
재현할 수 없는 상태는 정상이라고 간주하지 말고 “미검증”으로 남겨라.


## 5. UX 점검 범위

아래 항목을 체크리스트로 활용하되, 이에 한정하지 마라.

### A. 현재 상태와 작업 현황의 가시성
현재 선택한 대상, 작업 단계, 저장 여부, 처리 여부, 완료 여부,
실패 여부, 남은 작업, 마감 시각 등을 한눈에 알 수 있는가?

사용자가 여러 화면을 오가거나 내용을 기억해야만
전체 진행 상황을 파악할 수 있지는 않은가?

### B. 로딩·대기·진행 상태
최초 로딩, 부분 로딩, 업로드, 생성, 저장, 새로고침 등에서
무슨 작업이 진행 중인지 알 수 있는가?

스피너만 있고 설명이 없거나, 멈춘 것처럼 보이거나,
일부 단계만 끝났는데 전체 완료처럼 표시되지는 않는가?

### C. Layout shift와 시각적 안정성
이미지, 폰트, 데이터, 배너, 검증 메시지, 스켈레톤 전환으로
본문이나 버튼 위치가 갑자기 이동하는가?

클릭하려던 대상이 이동하거나, 스크롤 위치가 튀거나,
모달·토스트가 주요 정보를 가리지는 않는가?

관찰된 이동과 실제 불편을 기록하라.
계측하지 않은 CLS 수치나 이동량을 만들어내지 마라.

### D. 행동의 명확성과 클릭 가능성
주요 버튼과 보조 버튼이 구분되는가?
클릭할 수 있는 요소가 그렇게 보이는가?
반대로 클릭할 수 있어 보이지만 반응하지 않는 요소는 없는가?

버튼 문구만으로 결과를 예측할 수 있는가?
비활성화된 이유와 활성화 조건을 알 수 있는가?

### E. 성공·실패·빈 상태의 구분
데이터가 없는 상태, 검색 결과가 없는 상태, 로딩 중인 상태,
권한이 없는 상태, 오류 상태가 서로 구분되는가?

각 상태에서 사용자가 다음에 무엇을 해야 하는지 안내하는가?
오류가 발생했는데 빈 화면이나 성공 화면처럼 보이지는 않는가?

### F. 입력과 검증
입력 형식, 필수 여부, 제한 조건이 행동 전에 안내되는가?
오류가 해당 필드 가까이에 표시되는가?
수정 방법이 구체적인가?

실패 후 입력값이 보존되는가?
불필요하게 같은 정보를 다시 입력하게 하지는 않는가?

### G. 저장·확정·취소·복구
임시 저장, 저장, 확정, 예약, 완료 등의 의미가 구분되는가?
되돌릴 수 있는 행동과 되돌릴 수 없는 행동을 알 수 있는가?

저장하지 않은 변경이 조용히 사라지거나,
취소했는데 적용되거나, 저장했는데 다시 사라지지는 않는가?

### H. 탐색과 문맥 유지
뒤로 가기나 상세 화면 복귀 시 검색어, 필터, 페이지,
스크롤 위치, 선택 대상이 적절히 유지되는가?

사용자가 현재 위치와 돌아가는 방법을 쉽게 알 수 있는가?
같은 결과를 얻기 위해 불필요하게 많은 단계를 거치지는 않는가?

### I. 정보 구조·문구·일관성
중요한 정보가 덜 중요한 정보에 묻히지 않는가?
상태명, 버튼명, 날짜·시간 형식, 오류 표현이 일관적인가?

내부 용어나 애매한 표현 때문에 의미를 추측해야 하지는 않는가?
마감이나 예약처럼 시간에 민감한 기능은 기준 시각을 이해할 수 있는가?

### J. 반응형과 기본 접근성
작은 화면에서 내용 잘림, 겹침, 가로 스크롤,
화면 밖으로 나가는 버튼이나 모달이 있는가?

색상만으로 상태를 구분하지는 않는가?
작은 클릭 영역, 읽기 어려운 대비, 보이지 않는 포커스가 있는가?

마우스 탐색을 기본으로 하되, 주요 입력과 모달에서
Tab 이동, Enter, Escape 등의 기본 키보드 동작도 확인하라.

### K. 사용자에게 보이는 성능 문제
클릭 후 반응 지연, 반복 로딩, 입력 지연, 상태 반영 지연,
스크롤 끊김 등이 실제 작업에 어떤 영향을 주는가?

요청 수가 많거나 요청이 반복된다는 사실만으로
UX 문제 또는 중복 처리라고 단정하지 마라.
사용자에게 보이는 현상과 기술적 원인 추정을 분리하라.


## 6. HAR와 화면 증거 수집

HAR만으로 UX 문제를 설명하지 마라.
네트워크 기록과 화면 관찰을 서로 연결하라.

### HAR
- 로그인 전부터 기록하고 주요 여정을 빠짐없이 포함하라.
- 파일이 커지면 여정 단위로 나누되, 구간 누락 여부를 명시하라.
- 여정 ID, 시작·종료 시각, HAR 파일명을 연결하라.
- 문제와 관련된 요청의 시각, 메서드, 경로, 상태 코드,
  소요 시간을 가능한 범위에서 기록하라.
- 탐색 종료 후 HAR를 정상적으로 내보내고,
  파일이 존재하며 예상한 요청 구간이 담겼는지 확인하라.

### 화면 증거
- 주요 화면과 중요한 상태 전환을 캡처하라.
- layout shift, 로딩, 상태 불일치는 가능하면 전후 증거를 남겨라.
- 스크린샷 파일명에 여정 ID나 문제 ID를 포함하라.
- 영상이나 trace가 있으면 해당 시점도 연결하라.
- 하나의 정적인 이미지로 입증할 수 없는 현상을
  그 이미지가 완전히 증명한다고 표현하지 마라.

### 민감정보
HAR의 Cookie, Authorization, 토큰, 비밀번호, 개인정보는
헤더뿐 아니라 URL, 요청 본문, 응답 본문에도 포함될 수 있으므로 점검하라.

공유용 HAR와 보고서에서는 민감정보를 마스킹하라.
원본이 필요한 경우 공유용 산출물과 분리하여 제한적으로 취급하라.
스크린샷과 trace에도 같은 원칙을 적용하라.

### 도구 제약
HAR, 영상, 특정 네트워크 조건 등을 지원하지 않는 경우
무엇을 수집하지 못했는지 명확히 밝히고 가능한 증거로 보완하라.

네트워크 요약을 HAR 파일이라고 부르거나,
생성하지 않은 파일·촬영하지 않은 화면·수행하지 않은 행동을
실제로 확보한 것처럼 보고하지 마라.


## 7. 테스트 데이터와 안전 경계

### 샘플을 준비한 뒤 여정을 완주한다

아크포인트 QA는 샘플 데이터를 미리 만들어 재사용하거나, 없으면 필요한 샘플을 직접 만들어 진행한다. “데이터가 없다”, “이미 생성됐다”, “기존 데이터라 수정하지 않았다”만으로 생성·편집·저장 여정을 생략하지 않는다.

- 먼저 현재 QA 계정에서 사용할 수 있는 샘플과 기존 QA 준비 문서·도구를 확인한다. 테스트용으로 제공됐고 수정·재사용 범위가 확인되는 병원·콘텐츠는 기존 데이터라도 QA 샘플로 활용할 수 있다. 다른 QA가 사용하는 대상은 복제하거나 별도 샘플을 준비한다.
- 필요한 샘플이 없거나 상태가 소진됐으면 접근 가능한 사용자/QA 관리자 UI, 문서화된 QA fixture·seed 도구나 API로 준비한다. 최초 준비만 이런 경로를 사용할 수 있으며, 평가할 사용자 행동은 실제 UI에서 수행한다. 직접 DB 수정으로 사용자 여정을 대체하지 않는다.
- 검증할 여정에 필요한 최소 조건을 함께 준비한다. 실제 존재하는 기능에 맞춰 병원 접근권한, 이용기간, 필수 제작정보, 발행 캘린더·주차, 선택 가능한 원고·이미지·카드뉴스 원본 등이 서로 맞는지 확인한다. 고정된 과거 샘플 날짜를 현재에도 유효하다고 가정하지 않는다.
- QA 실행 ID가 보이는 이름·표시를 사용하고, 표시 이름을 바꿀 수 없으면 실제 대상 ID와 생성 시각·소유 범위를 기록한다. 개인정보 없는 가상의 병원·사용자·본문·사진 자료를 사용한다. 자격 증명을 샘플 이름이나 파일명에 넣지 않는다.
- 상태를 소모하는 생성·확정 여정에는 다음 반복에 쓸 새 샘플이나 발행 주를 준비한다. 필요하면 빈 상태, 생성 전·후, 선택 정보 일부 누락, 긴 내용 등 목적에 맞는 샘플을 나눠 만든다. 동일 샘플의 상태 오염을 새 결함으로 오인하지 않는다.
- 자기 소유 또는 재사용이 허용된 샘플에서는 생성·수정·저장 후 새로고침·재로그인·재진입까지 확인한다. 취소만 해보고 저장 완료 여정을 통과했다고 하지 않는다.
- 샘플 준비가 막히면 확인한 도구·역할·준비 시도와 남은 필수 조건을 기록한다. 권한 부족·도구 부재·외부 실행 제한과, 준비하지 못했거나 시간 내 실행하지 않은 항목을 구별한다. 기존 안전한 경로에 필요한 계정·정보가 정말 없을 때만 질문한다.

일반 사용자·실사용자 데이터나 다른 사람의 작업을 임의로 수정·삭제하지 않는다. 삭제·취소·초기화는 이번 실행 소유 또는 명시적으로 재사용·초기화가 허용된 QA 샘플에 한한다. 한 항목을 다시 테스트하려고 공유 QA 전체를 무단 초기화하지 않는다.

외부 게시, 실제 예약 발행, 메일/SMS 발송, 결제,
실사용자 권한 변경 등 외부 영향을 주는 행동은
테스트용으로 격리되어 있거나 명시적으로 허용된 경우에만 실행하라.

실행이 허용되지 않은 마지막 단계는 직전까지 확인하고,
최종 실행과 결과 상태는 “차단/미검증”으로 보고하라.
완료한 것으로 계산하지 마라.

현재 QA 계정의 접근 범위 안에서 탐색하라.
다른 사용자 데이터 접근이나 권한 우회를 시도하지 마라.

테스트 종료 시 생성·재사용한 데이터와 남은 예약·작업을 확인한다. 재사용할 샘플은 준비 상태·ID·QA 기준 시각과 사용 범위를 남겨 다음 실행에서도 사용할 수 있게 한다. 일회성 임시 데이터는 허용 범위에서 정리한다. 정리한 항목, 보존한 항목과 이유, 시계 최종 상태를 함께 기록한다.


## 8. 발견 사항 작성 형식

각 문제는 다른 사람이 보고 재현할 수 있는 수준으로 작성하라.

### UX-001. [사용자가 겪는 문제를 구체적으로 표현한 제목]

- 분류: 기능 오류 / 사용성 문제 / 시각적 문제 / 접근성 문제 등
- 심각도: P0 / P1 / P2 / P3
- 여정 및 위치: 여정 ID, 화면, URL 경로, 관련 요소
- 발생 조건: 데이터 상태, 화면 크기, 네트워크 조건 등
- 재현 절차: 실제 수행한 행동을 번호 순서대로 작성
- 관찰한 실제 결과: 화면에서 무엇이 어떻게 나타났는지
- 기대되는 사용자 경험: 사용자가 무엇을 알거나 할 수 있어야 하는지
- 사용자 영향: 헷갈림, 재확인, 작업 지연, 오조작, 데이터 손실 등
- 재현 여부: 재현됨 / 간헐적 / 1회 관찰 / 추가 검증 필요
- 증거: 스크린샷·영상·trace·HAR 파일과 해당 시각 또는 요청
- 원인 추정: 필요한 경우에만 작성하며 관찰 사실과 구분
- 개선 제안: 해당 불편을 줄이는 구체적인 방향
- 개선 확인 기준: 수정 후 어떤 행동과 화면을 보면 해결됐다고 판단할지

심각도 기준:
- P0: 데이터 손실·잘못된 실제 처리 등 중대한 피해가 발생하거나 임박함.
      발견 시 관련 위험 행동을 중단하고 우선 보고한다.
- P1: 핵심 여정을 완료할 수 없거나 심각한 오조작을 유발하며,
      실질적인 우회 방법이 거의 없음.
- P2: 완료는 가능하지만 혼란, 반복 행동, 재확인, 지연이 의미 있게 발생함.
- P3: 과업 수행 영향이 비교적 작은 가독성·일관성·미세 인터랙션 문제.

같은 원인으로 여러 화면에서 반복되는 문제는 하나로 묶고,
발생 화면과 대표 증거를 함께 기록하라.
서로 다른 실패 원인이나 사용자 영향은 무리하게 합치지 마라.

“느리다”, “헷갈린다”, “불편하다”만으로 끝내지 마라.
어떤 행동 뒤에 무엇이 보였고, 사용자가 무엇을 알 수 없거나
어떤 불필요한 행동을 해야 하는지 구체적으로 설명하라.

관찰 사실, 사용자 영향 추정, 기술적 원인 가설을 구분하라.
실제 사용자 인터뷰를 하지 않았다면 사용자 반응을 관측한 것처럼 쓰지 마라.


## 9. 최종 산출물과 완료 기준

최종 보고서는 다음 순서로 작성하라.

### 1. 핵심 요약
전체 사용자 경험의 주요 장애물과 가장 먼저 고칠 문제를 정리하라.
기능 실패와, 기능은 동작하지만 사용하기 어려운 문제를 구분하라.

### 2. 탐색 범위 및 커버리지
발견한 화면과 사용자 여정 목록을 제공하라.

여정별로 다음 확인 여부를 표로 정리하라.
- 정상 완료
- 로딩·처리 중 상태
- 빈 상태
- 입력 검증·오류·재시도
- 취소·뒤로 가기·이탈
- 새로고침·재진입
- 좁은 화면 또는 모바일
- 관련 증거

각 항목은 확인 완료 / 일부 확인 / 차단 / 해당 없음으로 표시하라.
“해당 없음”과 “확인하지 못함”을 구분하라.

### 3. 문제 목록과 상세 내용
심각도와 영향을 받는 여정을 기준으로 요약 표를 작성하고,
각 문제를 위의 상세 형식으로 이어서 작성하라.

### 4. 반복되는 UX 패턴
상태 표시 부재, 저장 의미 혼동, 문맥 손실,
불안정한 레이아웃 등 여러 여정에 공통으로 나타나는 문제를 묶어라.

### 5. 확인하지 못한 항목과 한계
접근 권한, 테스트 데이터, 외부 실행 제한, 도구 제약, 재현 실패 등으로 남은 부분을 구체적으로 기록하라.
시간·데이터 조건으로 막힌 경우 어떤 QA 시계 조절·샘플 준비를 시도했는지 적는다. “운영 환경을 쓰지 않아서”로 원인을 뭉뚱그리지 말고, 환경·권한에 의한 차단과 단순 미실시를 구분한다.

### 6. 증거 및 테스트 데이터 정리
실제 생성된 HAR·스크린샷·영상·trace의 경로나 링크,
여정별 대응 관계, 생성·재사용·정리한 QA 데이터와 잔여 작업을 정리하라.
샘플 목록에는 목적·실제 ID·준비 방법·초기/최종 상태·재사용 또는 삭제 여부를, 시계 이력에는 실제 시각·변경 전후 QA 시각·적용 범위·복구/유지 여부를 포함한다.

발견한 핵심 여정을 종료 상태까지 수행하고,
주요 분기와 UX 상태를 확인한 뒤 탐색을 마무리하라.

시간이나 도구 한계가 생기면 핵심 여정과 영향이 큰 문제를 우선하고,
나머지를 미검증으로 남겨라.
확인하지 않은 범위까지 포함하여 “모든 사용자 여정에 문제없음”이라고 결론 내리지 마라.

최종 목표는 이 보고서만으로 담당자가
“사용자가 어디에서, 무엇 때문에 불편을 겪으며,
어떻게 재현하고, 무엇을 바꾸면 해결되는지” 이해할 수 있게 하는 것이다.
