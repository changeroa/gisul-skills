# Object Design Workflow

설계를 먼저 완성하려 하지 말고, 중요한 미결정을 작은 실행과 관찰로 해소한다.
반복의 산출물은 패턴이나 다이어그램 개수가 아니라 동작 증거와 더 나은 다음 결정이다.
이 문서는 외부 팩 없이 실행 가능한 독립 절차다.

## 1. 권한과 현재 상태를 고정한다

- 리뷰·학습 요청은 읽기 전용이며 구현·실험 권한을 자동으로 포함하지 않는다.
- 파일 변경, 테스트 실행, 설치, 외부 호출과 배포는 허용된 범위에서만 한다.
- 사용자 변경을 덮어쓰거나 문서 작성을 이유로 제품 코드를 수정하지 않는다.
- 결제·발송·운영 데이터 변경을 실제 서비스에서 재현하지 않는다.
- 현재 코드 revision, 대상 경로, 실행 환경과 관찰 날짜를 기록한다.
- 현재 요구, 구현 사실, 제안 설계와 검증되지 않은 가정을 분리한다.
- 확인하지 않은 코드·모델·테스트를 읽었거나 실행했다고 표현하지 않는다.

## 2. 미결정과 실패 비용부터 찾는다

1. 사용자 목표와 이번에 보호할 관찰 가능한 계약을 한 문장으로 적는다.
2. 현재 성공·실패 시나리오에서 상태 변화와 외부 효과를 추적한다.
3. 설계 선택을 바꿀 수 있는 미결정과 고위험 가정을 나열한다.
4. 틀렸을 때의 안전·데이터·비용·일정·변경 영향을 적는다.
5. 이미 알려진 사실과 추가 조사 없이는 알 수 없는 항목을 구분한다.
6. 이번 반복이 끝나면 어떤 결정을 내릴 수 있어야 하는지 정한다.

'좋은 구조', '확장성 확보', '패턴 적용'만으로는 학습 목표가 되지 않는다.
요구와 무관한 코드 청소를 위험 해소로 포장하지 않는다.

## 3. 품질 요구를 검증 가능한 시나리오로 바꾼다

각 quality scenario에 다음을 적는다.

- **자극:** 사용자 행동, 부하, 변경 요청 또는 의존성 실패.
- **환경:** 데이터 규모, 실행 환경, 부하와 실패 범위.
- **응답:** 사용자나 운영자가 관찰할 결과와 허용되는 저하.
- **기준:** 시간·오류·손실·수정 범위 등의 수용 한계.
- **검증:** 방법, 담당, 필요한 자원과 결과를 확인할 위치.

'빠르게', '대부분', '복구 가능'은 측정 조건이 정해지기 전까지 미결정이다.
기준 수치는 현재 계약·관찰·제약에서 정하고 관행의 숫자를 복사하지 않는다.
검증할 계획도 없는 정밀한 요구 목록보다 중요한 시나리오 하나를 실제로 확인한다.
법률·안전상 허용되지 않는 fallback은 편의성 목표보다 먼저 제외한다.

## 4. 현재 변형과 예상 변화를 구분한다

- **Variation point:** 지금 요구되거나 실제 운영되는 인터페이스·규칙의 차이.
- **Evolution point:** 앞으로 생길 수 있으나 아직 요구되지 않은 변화.
- 현재 변형에는 실제 예와 의미 차이를 적는다.
- 예상 변화에는 근거, 가능 시점과 잘못 예측할 비용을 적는다.
- 나중 변경 비용과 지금 추상화·테스트·운영 비용을 비교한다.
- 뒤늦게 바꾸기 비싼 선택은 작은 경계나 실험으로 선택권을 보존한다.
- 안정된 의존성까지 모두 감싸거나 모든 객체에 factory를 만들지 않는다.
- 공통 인터페이스로 묶어도 실패·일관성·보안 의미가 같은지 따로 확인한다.

## 5. 작은 실행 반복을 선택한다

1. 사업상 중요도, 실패 비용과 불확실성이 높은 후보를 우선한다.
2. 선택한 가정을 반증할 수 있는 가장 작은 실행 경로를 고른다.
3. 큰 사용자 목표는 독립적으로 관찰 가능한 end-to-end 시나리오로 줄인다.
4. 성공뿐 아니라 결정에 중요한 실패·복구 경로를 포함한다.
5. 시간·자원 예산, 수용 기준과 중단 기준을 시작 전에 정한다.
6. 실제 가용 인원, 통합 비용과 검증 시간을 포함해 범위를 맞춘다.

UI만, 저장소만 끝내고 사용자 행동의 검증을 다음 반복으로 미루지 않는다.
격리된 spike가 더 싸면 사용하되 전체 통합을 검증한 것으로 확대하지 않는다.
spike의 폐기·제품화 여부와 남은 통합 위험을 명시한다.
고정 주수나 정해진 반복 횟수를 강제하지 않고 피드백 지연과 위험에 맞춘다.
시간 상자를 사용한다면 기한이 닥쳤을 때 품질 증거 대신 범위 축소를 검토한다.

## 6. 필요한 만큼 분석하고 설계한다

- 무엇을 제공할지와 어떻게 구현할지를 구분하되 둘을 번갈아 수정한다.
- 이번 시나리오의 용어, 책임, 상태, 경계와 협력을 이해할 만큼만 모델링한다.
- 정적 의존성만으로 불충분하면 중요한 경계 통과 순서를 함께 살핀다.
- 논리적 모듈과 process·node·배포 단위를 같은 것으로 취급하지 않는다.
- 현 구조 유지, 작은 변경, 기존 기능 활용과 새 구현의 비용을 비교한다.
- 구매·재사용·요구 축소·보류·중단도 대안에 포함한다.
- 패턴은 현재 문제와 tradeoff를 설명할 때만 선택한다.
- 계층 수, 인터페이스 수와 문서 형식을 완료 기준으로 삼지 않는다.
- 자체 ORM·범용 framework보다 검증된 도구의 지원 범위와 최소 구성을 먼저 조사한다.

분석 완료 뒤 설계 완료 뒤 코딩이라는 단계별 통과 절차로 만들지 않는다.
아키텍처 영향은 일찍 조사하지만 실제 실행 전에 모두 알 수 있다고 가정하지 않는다.

## 7. 코드와 테스트에서 피드백을 얻는다

1. 허용된 환경에서 선택한 시나리오를 실행 가능하게 만든다.
2. 실제 결정 경계가 드러나는 가장 낮은 비용의 검증을 선택한다.
3. 구성·영속화·외부 계약이 위험이면 그 경계를 제거한 대역만으로 결론내리지 않는다.
4. 정상 결과, 실패 시 남은 상태와 복구 완료 조건을 관찰한다.
5. 계획했던 응답과 실제 응답을 비교하고 가정이 깨진 지점을 적는다.
6. 결과가 대안을 지지하는지, 선택을 바꾸어야 하는지 판단한다.

테스트 통과를 요구 완전성이나 운영 준비의 증명으로 확대하지 않는다.
실행 실패가 환경 문제인지 제품 결함인지 미확인이라면 그대로 남긴다.
반복 실험이 새 정보를 주지 않으면 같은 접근을 계속하지 않는다.

## 8. 모델·코드·날짜의 drift를 정리한다

- 모델에 목적, 범위, 대응 코드 revision과 마지막 검증 날짜를 연결한다.
- 생성·캡처 날짜와 실제 코드 일치 여부를 확인한 날짜를 구분한다.
- 계획 모델, 구현 모델과 폐기한 대안을 표시해 서로 섞이지 않게 한다.
- 책임·상태·협력이 바뀌면 다음 판단에 필요한 모델만 갱신한다.
- 모델과 코드가 다르면 어느 쪽이 계약에 맞는지 실행 근거로 판단한다.
- 오래된 모델은 갱신·축소·폐기하고 날짜만 바꿔 최신으로 보이게 하지 않는다.
- 모든 구현 세부를 수동 복제하지 말고 중요한 결정과 경계를 유지한다.
- 미검증 영역은 최신 코드라는 이유만으로 검증 완료로 올리지 않는다.

## 9. 중단하고 다음 반복을 정한다

- **수용:** 시나리오 기준과 결정에 필요한 증거를 확보했다.
- **전환:** 가정이 깨졌거나 더 작은 대안이 유리해 접근을 바꾼다.
- **차단:** 권한·자료·환경·외부 사건이 없어 판단할 수 없다.
- **예산 종료:** 학습 예산이 끝났고 남은 불확실성을 공개한다.
- 안전·법률 위반 가능성이나 되돌릴 수 없는 효과가 나타나면 즉시 멈춘다.
- 차단 상태에는 필요한 입력과 가장 작은 다음 행동을 적는다.
- 다음 반복은 쉬운 미완료 작업 순서가 아니라 새 위험과 근거로 다시 고른다.
- 장기 목표는 유지하되 먼 미래의 상세 실행 계획을 확정 사실로 만들지 않는다.
- 추정과 약속을 구분하고 새 통합 경험이 나오면 범위와 신뢰도를 갱신한다.

## 10. 결과와 완료 증거

보고에는 목표, 미결정, 선택 시나리오, 대안, 실제 변경과 관찰 결과를 남긴다.
`확인된 사실 / 실행 결과 / 제안 / 미검증 / 차단`을 구별한다.
테스트에는 revision·환경·실행 날짜·명령·관찰 범위를 연결한다.
모델 갱신 또는 폐기, 남은 위험, 중단 이유와 다음 결정도 함께 적는다.
완료 여부는 코드·문서 양이 아니라 이번 수용 기준으로 판단한다.
필요한 기록 양식과 점검 예시는 [결정과 증거 기록](references/decision-evidence.md)을 사용한다.
