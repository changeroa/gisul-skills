# 동작 흐름 테스트

## 목적

개별 동작의 성공뿐 아니라, 동작이 이어지거나 중단·재시도될 때도 시스템이 기대한 결과와 일관성을 유지하는지 검증한다.

테스트 범위는 요청받은 기능과 직접 영향을 받는 흐름으로 한정한다. 모든 상태 조합을 나열하기보다 실제 위험이 있는 경계를 선택한다.

## 1. 기대 동작과 검증 범위를 정한다

요구사항, 기존 결정, 구현, 테스트에서 다음을 파악한다.

- 사용자가 달성하려는 결과.
- 주요 행동과 그 행동으로 달라지는 상태.
- 상태를 소유하는 주체와 유지되는 기간.
- 외부 시스템, 비동기 처리, 영속화가 개입하는 경계.
- 실패·중단·재시도 시 기대하는 동작.

현재 구현을 그대로 정답으로 삼지 않는다. 명시된 요구사항, 구현에서 관찰한 동작, 추정을 구분한다.

불명확한 사항 중 테스트의 합격 기준을 바꾸는 중요한 결정은 확인한다. 그 외에는 가정을 기록하고 독립적으로 검증할 수 있는 부분을 진행한다.

## 2. 개별 동작을 연속된 시나리오로 확장한다

먼저 대표적인 정상 흐름을 정한다. 그 흐름에서 오류가 발생하기 쉬운 경계를 찾아 관련 변형을 선택한다.

| 관점 | 검토할 변화 |
|---|---|
| 순서 | 이전 작업이 늦게 완료됨, 처리 순서가 뒤바뀜 |
| 반복 | 중복 실행, 재시도, 같은 대상 재방문 |
| 중단 | 취소, 이탈, 종료, 연결 끊김 |
| 복구 | 재접속, 재시작, 저장 상태로 복원 |
| 동시성 | 여러 작업·사용자·클라이언트가 같은 상태를 변경 |
| 대상 변경 | 작업 도중 계정·항목·조건·컨텍스트 변경 |
| 부분 실패 | 일부 단계만 성공, 성공 응답 유실, 후속 처리 실패 |
| 경계 데이터 | 비어 있음, 한도 도달, 삭제됨, 권한 변경 |

각 변형은 해당 기능과 관련이 있을 때만 적용한다. 데이터 유실, 잘못된 대상 처리, 중복 부작용, 복구 불가 위험을 우선한다.

## 3. 시나리오별 판정 기준을 먼저 적는다

테스트 코드를 작성하거나 도구를 조작하기 전에 다음을 정한다.

- 초기 조건.
- 행동 및 외부 사건의 순서.
- 지연·실패·동시 실행 등 필요한 조건의 재현 방법.
- 처리 중 관찰되어야 하는 동작.
- 최종 결과와 허용되지 않는 부작용.
- 실행 결과를 판정할 증거.

관련된 불변 조건을 명시한다. 예:

- 결과는 해당 요청·대상·버전에만 적용된다.
- 오래된 결과가 최신 상태를 덮어쓰지 않는다.
- 재시도해도 허용되지 않은 중복 부작용이 발생하지 않는다.
- 미확인·실패·빈 결과를 서로 혼동하지 않는다.
- 사용자 입력과 이미 확정된 데이터가 정해진 규칙에 따라 보존된다.
- 완료 보고와 실제 저장·처리 결과가 일치한다.
- 중단된 작업을 다시 시작하거나 복구할 수 있다.

기능에 없는 보존·복구·중복 방지 요구사항을 임의로 추가하지 않는다.

## 4. 결함을 잡을 수 있는 테스트 층을 선택한다

주장하려는 동작에 맞춰 검증 수단을 선택한다.

- 로직 테스트: 전환 규칙, 계산, 검증, 충돌 해결.
- 통합 테스트: 구성 요소 사이의 호출, 영속화, 외부 시스템 계약.
- 상호작용·종단 간 테스트: 실제 진입점에서 시작하는 연속된 작업.

빠르고 안정적인 하위 층에서 세부 조건을 검증하고, 주요 흐름은 실제 구성 요소가 연결된 상태에서 확인한다.

정적 출력 검사로 실행 중 변화를 검증했다고 주장하지 않는다. 모킹한 의존성의 실제 동작까지 검증했다고 주장하지 않는다. 기존 테스트와 중복하기보다 누락된 경계와 연결을 보완한다.

도구 선택과 실행은 프로젝트의 기존 지침을 따른다. 테스트 도구를 사용했다는 사실 자체를 검증 근거로 삼지 않는다.

## 5. 조건을 통제하고 과정과 결과를 관찰한다

가능하면 시간·응답 순서·실패 지점을 명시적으로 통제한다. 임의의 대기보다 관찰 가능한 사건이나 상태를 기다린다.

예: 오래된 결과의 영향 검증

1. 작업 A를 시작하고 완료를 보류한다.
2. 조건을 변경해 작업 B를 시작한다.
3. B를 완료하고 결과를 확인한다.
4. A를 뒤늦게 완료한다.
5. 정해진 최신성 규칙과 부작용 조건이 유지되는지 확인한다.

최종 결과만으로 놓칠 수 있는 문제는 처리 중에도 관찰한다. 필요에 따라 출력, 이벤트, 요청, 저장 결과를 연결해 확인한다. 관련 오류가 없는지도 확인하되, 오류가 없다는 사실만으로 통과시키지 않는다.

재현에 필요한 조건을 만들지 못하면 미검증으로 남긴다. 테스트의 관찰 범위보다 강한 보장을 주장하지 않는다.

## 6. 실패를 재현 가능한 회귀 테스트로 남긴다

실패하면 초기 조건, 사건 순서, 기대값, 실제 결과를 보존한다. 우연한 성공이나 단순 재실행으로 실패를 덮지 않는다.

수정 작업이 범위에 포함된 경우:

- 원인을 드러내는 최소 재현 테스트를 만든다.
- 가능하면 수정 전 실패와 수정 후 통과를 확인한다.
- 영향을 받는 연결 흐름을 검증한다.

테스트 편의를 위해 제품의 기대 동작이나 합격 기준을 바꾸지 않는다. 테스트 데이터와 생성 자원은 필요한 증거를 보존한 후 정리한다.

## 7. 증거에 맞춰 결과를 보고한다

시나리오별 결과를 구분한다.

- 통과: 조건을 재현하고 기대 동작을 확인함.
- 실패: 기대 동작과 다른 결과를 확인함.
- 미검증: 필요한 조건이나 관찰을 확보하지 못함.
- 해당 없음: 적용되지 않는 이유가 있음.

보고에는 다음을 포함한다.

- 검증 대상과 환경·버전.
- 실행한 주요 시나리오와 결과.
- 재현 테스트나 실행 증거의 위치.
- 모킹·관찰 범위와 중요한 미검증 항목.
- 발견한 문제와 남은 결정 사항.

검증한 범위 안에서만 완료를 선언한다.
