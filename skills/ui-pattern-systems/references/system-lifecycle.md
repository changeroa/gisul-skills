# 시스템 inventory와 수명주기 운영

공유 자산으로 승격하거나 실제 소비 제품의 변경·폐기를 관리할 때 읽는다.
작은 팀의 단일 선택에는 기존 명세를 보강한다. 아래 모든 양식과 역할을 별도 문서로 만들지 않는다.

## 1. Inventory를 실행 계약에 연결

목적은 목록 수집이 아니라 무엇이 같고 무엇이 달라야 하는지를 판단하는 것이다.
현재 제품 화면, 디자인 자산, 구현 코드, 문서가 가리키는 버전을 구별한다.

항목마다 다음 중 판단에 필요한 정보만 기록한다.

```text
항목 식별자 / 이름·별칭:
사용자 문제 / 적용·제외 맥락:
실제 소비 제품·역할·진입 흐름:
패턴과 component·variant·token·콘텐츠의 연결:
상태·행동·접근성 계약:
디자인·구현·문서 버전과 확인한 차이:
소유자 / 기여·검토 경로:
검증된 조건 / 미확인 조건:
분류와 다음 조치:
```

`재사용 가능 / 보수 필요 / 의미 있는 예외 / 중복 / 유해·폐기 후보`를 근거로 분류한다.
같은 색 값이 우연히 일치해도 의미와 변경 이유가 다르면 하나의 semantic token으로 합치지 않는다.
다른 이름의 token이 같은 역할을 중복 소유하면 소비자와 theme·mode 영향을 확인한 뒤 통합을 제안한다.
동작이 다른 변형은 별도 계약이 필요한지, 같은 동작의 외형 차이는 정당한 맥락이 있는지 확인한다.

## 2. 패턴 문서의 최소 완결성

문서 이용자가 다음을 결정할 수 있어야 한다.

- 이 패턴이 내 과업에 맞는가? 어떤 조건에서는 다른 해법을 택하는가?
- 어떤 variant와 state가 지원되며, 제품 정책은 어디서 정하는가?
- 어떤 component·token·콘텐츠 예제를 어느 버전에서 사용하는가?
- 접근성 동작을 component가 제공하는가, 소비자가 연결해야 하는가?
- 다른 패턴과 조합할 때 바뀌거나 보존되는 상태는 무엇인가?
- 알려진 한계와 대안, 변경 요청 담당자는 누구인가?

프리뷰는 상태의 대표 예제를 선택하고 확인된 범위를 표시한다.
정적 이미지는 모습, live markup은 렌더링, 상호작용 데모는 구현한 전환만 보여준다.
실제 저장·권한·외부 효과를 연결하지 않은 데모로 제품 수준의 성공을 보증하지 않는다.
상태 예제는 default뿐 아니라 실제 적용 가능한 대기·빈 값·오류·완료·제한 조건을 포함한다.
지원하지 않는 상태를 mock으로 감추지 말고 소비자 책임 또는 미지원으로 명시한다.

접근성 계약은 의미·이름, 입력 방식, focus 이동/복원, 동적 상태 안내, 대비·확대·motion 등 관련 요구를 포함한다.
각 요구에 제공 주체, 소비자 설정, 검증 범위와 알려진 한계를 연결한다.
속성 몇 개나 자동 검사 통과를 전체 접근성 준수로 보고하지 않는다.
현재 지원 환경과 적용 표준은 별도로 확인하고 고정된 과거 예제를 그대로 복사하지 않는다.

## 3. 제안에서 안정적 채택으로

별도 위원회를 강제하지 말고 누가 판단하고 누가 갱신하는지만 명확히 한다.

1. 제안자는 실제 과업·반복 문제·기존 해법의 한계와 소비자를 제시한다.
2. 소유자는 재사용, 국소 보수, 예외, 새 패턴 중 적절한 범위를 검토한다.
3. 구현·디자인·콘텐츠 담당자는 행동 계약과 소비 환경의 차이를 확인한다.
4. 관련 상태·접근성·조합 검증이 가능한 최소 예제로 위험을 확인한다.
5. 제한된 실제 소비에서 사용하고 미지원 조건과 피드백을 수집한다.
6. 안정적 계약과 지원 책임이 확보되면 채택 경로·버전·문서를 함께 제공한다.

비개발자도 문제·카피·행동 사례를 제안할 수 있게 한다. 코드 변경 가능 여부로 기여를 제한하지 않는다.
기여 승인과 제품 출시 승인은 다르다. 게시·배포는 기존 권한과 절차를 따른다.

## 4. 버전과 예외 관리

- 안정된 식별자와 버전으로 디자인 자산·component API·token·문서를 연결한다.
- 시각 변경, 행동 변경, API 변경, 의미 변경을 구별하고 실제 소비자 영향을 기록한다.
- 함수 signature가 같아도 focus·scope·default·공개 동작이 바뀌면 호환성 변경일 수 있다.
- token 변경은 theme·상태·대비·브랜드 소비자에 주는 영향을 확인한다.
- 변경 설명에는 이익뿐 아니라 migration, 미지원 조건, 되돌릴 방법을 남긴다.
- 예외는 대상·이유·책임자·재검토 사건을 기록한다. 모든 예외에 임의 만료일을 강제하지 않는다.
- 문서와 구현의 차이를 발견하면 어느 계약이 유효한지 확인한다. 최신 파일을 자동 정답으로 삼지 않는다.

채택은 패키지 설치나 import 수만으로 판단하지 않는다.
정한 패턴 계약을 실제 제품이 사용하는지, 왜 우회·복제·예외가 생기는지 확인한다.
분모가 확인된 범위만 채택률을 말하고 샘플 조사를 전체 현황으로 확대하지 않는다.
표준화가 사용자 결과를 악화시키면 강제 적용보다 계약 수정 또는 예외를 검토한다.

## 5. Deprecation과 retire의 완료 조건

수명주기 명칭은 기존 시스템을 따르되 다음 의미는 섞지 않는다.

- **제안/실험:** 적용 조건과 동작을 확인 중이며 안정적 지원을 약속하지 않음.
- **지원:** 명시한 조건에서 사용할 수 있고 유지 책임이 있음.
- **Deprecated:** 새 사용을 제한하고 기존 소비자 이동을 관리 중임.
- **Retired:** 정한 지원 범위에서 사용 중단·제거 조건을 충족함.

폐기 기록에는 이유, 소비자·버전 목록, 대체/예외, 이동 책임, 일정 또는 제거 조건을 둔다.
저장값·링크·사용자 설정·학습된 행동이 남는다면 코드 제거 외의 전환도 설계한다.
되돌리기 어려운 데이터 이동은 별도 승인과 복구 정책 없이 실행하지 않는다.

완료 전에 확인한다.
1. 확인 범위의 소비 제품이 이동했거나 명시적인 제한 지원으로 분리되었는가?
2. 오래된 디자인 자산·문서·샘플 코드가 새 채택을 유도하지 않는가?
3. migration으로 과업·공개 범위·동의·저장 수명이 의도치 않게 바뀌지 않았는가?
4. 제거된 항목의 이유와 대체 경로를 기존 링크나 기록에서 찾을 수 있는가?
5. 검증하지 못한 소비자와 잔여 지원을 완료로 숨기지 않았는가?

패턴 등록, 구현 배포, 실제 채택, migration 완료, retire는 각각 다른 상태로 보고한다.
