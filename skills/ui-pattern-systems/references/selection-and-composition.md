# 선택과 조합의 판단 사례

후보의 적용 조건이 모호하거나 여러 패턴이 같은 상태를 공유할 때 해당 절만 읽는다.
예시는 선택을 돕는 질문이다. 모든 제품에 같은 패턴이나 기능을 추가하는 체크리스트가 아니다.

## 후보 비교의 최소 기록

기존 결정 기록에 다음을 붙인다. 후보 개수나 점수를 채우기 위한 형식으로 사용하지 않는다.

| 후보 | 해결하는 과업·맞는 조건 | 제외 조건·비용 | 근거 수준 | 결정을 바꿀 미확인 사실 |
|---|---|---|---|---|
| 현재 흐름 유지/보수 | 기존 방식에서 충족되는 결과 | 남는 마찰 | 관찰·연구 등 | 확인할 조건 |
| 대체 해법 | 달라지는 사용자 행동과 이익 | 새 학습·상태·운영 비용 | 관찰·연구 등 | 확인할 조건 |

관찰된 사실과 기대 효과를 분리한다. 숫자는 실제 자료와 측정 조건이 있을 때만 쓴다.
서로 다른 사용자 집단의 합산 수치가 문제를 가릴 수 있으므로 관련 집단·기기·진입 경로를 나눠 본다.
실험에서 전환이 늘어도 원치 않은 실행, 취소, 지원 요청이 함께 늘었는지 확인한다.
이탈만으로 UI 패턴이 원인이라고 단정하지 말고 가격·자격·데이터·성능 등 다른 설명을 검토한다.

## 온보딩: 설명보다 첫 가치 도달

- **Walkthrough:** 낯선 개념이나 순서를 이해해야 할 때 비교한다. 일상 화면의 모호함을 긴 설명으로 덮지 않는다.
- **Playthrough:** 실행하며 익히는 편이 유리할 때 비교한다. 실제 설정과 안전한 sandbox를 구분한다.
- **Progressive disclosure:** 선택적 상세 정보를 필요할 때 연다. 중요한 비용·제약·동의를 감추는 데 쓰지 않는다.
- **Staged disclosure:** 앞 단계 결과가 다음 행동의 조건인 순차 흐름에 사용한다. 단순히 화면을 짧게 만들려고 쪼개지 않는다.
- **Progressive reduction:** 익숙해진 사용자에게 도움을 줄일 수 있다. 학습 상태의 근거와 복원·재학습 경로를 둔다.

판단 질문:
- 처음 온 사람, 기존 계정의 새 기기, 중단 후 복귀가 다른 안내를 필요로 하는가?
- 샘플을 삭제하거나 건너뛰어도 본 작업이 유지되는가? 실습이 비용·quota·외부 전송을 발생시키는가?
- 권한·계정·선택 입력을 지금 요구할 사용자 이익이 있는가? 거절하면 무엇을 할 수 있는가?
- 도움을 완료한 것이 아니라 목표 작업을 완료한 것으로 성공을 정의했는가?

## 정보 탐색: 발견과 재탐색을 분리

| 선택 | 유리할 수 있는 조건 | 반드시 비교할 비용 |
|---|---|---|
| Autocomplete | 입력하려는 값을 이미 알고 일부를 입력함 | 늦은 제안·잘못된 자동 확정 |
| Autosuggest | 관련 후보를 보며 의도를 좁힘 | 관련성·범위 오해·대표 이미지의 왜곡 |
| Live filter | 결과 갱신이 빠르고 조건을 하나씩 탐색함 | 중간 갱신·focus 이동·요청 비용 |
| Batch filter | 여러 조건을 함께 완성하거나 조회 비용이 큼 | 적용 전/후 혼동·오래된 결과 |
| Pagination | 위치 기억·특정 대상·재방문이 중요함 | 페이지 경계와 추가 이동 |
| Load more | 이어 보되 사용자가 확장을 결정함 | 확장 뒤 위치와 복귀 상태 |
| Continuous loading | 다음 항목을 이어 발견하는 것이 핵심임 | footer 도달·재탐색·메모리·동적 안내 |

작은 집합이나 의미 없는 분류에는 필터가 없어도 된다. taxonomy가 실제 데이터와 사용자 언어에 맞는지 확인한다.
다중 선택의 AND/OR, 조건별 결과 수의 의미, 0건일 때 풀 수 있는 제약을 명시한다.
기능이 풍부하다는 이유로 지연되는 제안을 유지하지 않는다. 실제 지원 환경에서 도움을 주는 시점을 확인한다.

## 사회적 행동: 아이콘보다 약속

저장, 추천, 평가, 구독, 상호 관계를 같은 행동으로 취급하지 않는다.
각 행동에 `수집/재방문 → 공개 범위 → 상대 알림 → 관계·권한 변화 → 취소 효과`를 적는다.

- 개인 저장함과 공개 추천이 같은 아이콘을 쓰면 실행 전 차이를 설명할 수 있는가?
- 비대칭 follow와 상호 동의 관계가 메시지·콘텐츠 수신 정책과 어떻게 연결되는가?
- 자신의 저장 항목을 다시 찾는 과업과 다른 사람의 목록을 구경하는 과업에 같은 목록 방식이 맞는가?
- feed는 actor·action·time과 필요한 맥락을 보여주는가? 묶음·정렬이 사건의 의미를 바꾸는가?

공개성이나 관계 해제 효과를 외부 서비스 관례에서 추정하지 않는다. 해당 제품의 정책을 확인한다.

## 구매 후보와 등록: 보존 가치가 생기는 시점

임시 wish list는 구매·재고 예약·영구 보존과 다르다. 사용자에게 무엇을 약속하는지 먼저 정한다.
계정 없이 후보를 모으고 영구 보존 시 등록하게 할 수 있지만, 수명과 이동 정책이 필요하다.
로그인 전 목록과 기존 계정 목록을 어떻게 합칠지, 중복·실패·다른 계정을 어떻게 다룰지 명시한다.
추가 저장을 동의로 오인하거나, 가입·홍보 수신을 하나의 선택으로 묶지 않는다.
구매나 결제의 다른 과업을 일반적인 등록 흐름에 억지로 맞추지 않는다.

## 조합 계약: 검색+category+filter 예

같은 화면에서 각각 잘 작동해도 다음 충돌을 먼저 해결한다.

| 사건 | 가능한 충돌 | 결정할 계약 | 관찰할 결과 |
|---|---|---|---|
| 새 query 입력 | 사용자는 전체 검색 기대, 기존 category는 범위 제한 | 범위 보존/초기화와 표시 정책 | 활성 범위와 결과가 같은 뜻을 가짐 |
| category 변경 | 이전 category 전용 facet이 남음 | 공통 facet 보존, 무효 조건 제거·안내 | 숨은 제약 때문에 0건이 되지 않음 |
| batch 조건 편집 | 선택 표시가 바뀌지만 결과는 이전 조건 | 적용 전 draft와 적용된 조건 구분 | 사용자가 현재 결과의 조건을 알 수 있음 |
| 상세에서 복귀 | 위치·query·filter가 각각 다른 시점으로 복원 | 복귀 단위와 복원 근거 | 같은 탐색 문맥으로 돌아옴 |
| 로그인/대상 전환 | 다른 계정의 저장 조건이나 결과가 섞임 | 소유자·공유 허용 범위와 초기화 경계 | 다른 대상의 정보가 현재 결과처럼 보이지 않음 |

보존 또는 초기화 중 하나를 보편 규칙으로 삼지 않는다. 진입 과업과 숨은 조건의 위험을 비교한다.
상태별 세부 렌더링·요청 검증은 기존 상태 검토와 실행 검증에 넘긴다.

## 조합을 단순화하는 순서

1. 같은 개념·변경 이유가 확인된 공유 요소를 재사용한다.
2. 의미 없는 반복을 제거하되 범위와 관계를 설명하는 표시는 남긴다.
3. 후보 미리보기 등으로 시행착오를 줄여 다른 기능의 필요를 낮출 수 있는지 본다.
4. 서로 다른 의미를 고르는 중간 단계는 모호함을 실제로 줄일 때만 둔다.
5. 배치와 포함 관계를 실제 검색·선택 범위와 맞춘다.
6. 이전 상태를 보존/초기화하는 이유와 사용자에게 드러나는 단서를 함께 정한다.
7. 직접 이어지면 별도 결합 위젯 없이 연결한다.
8. 결합 후 남은 학습·성능·접근성·복구 비용을 다시 비교한다.

## 냄새에서 복구로

문제 기록은 `증상 → 매력적으로 보인 이유 → 빠진 맥락 → 반례 → 최소 복구`로 작성한다.
예를 들어 숨은 메뉴의 문제는 공간 절약 자체가 아니라 주요 과업 발견에 실패하는 조건이다.
모달의 문제는 mode 변경 자체가 아니라 불필요한 중단·중첩·focus 탈취·탈출 실패일 수 있다.
더 큰 재설계 전에 노출 우선순위, 라벨, 범위, inline 표시, 현재 동작 보수를 비교한다.
기만이 확인되면 더 효과적인 기만을 실험하지 말고 명확한 결과 설명과 자유로운 선택으로 대체한다.
