# UI Pattern Systems

패턴을 모양이 아니라 **사용자 문제를 특정 맥락에서 해결하는 반복 가능한 행동 모델**로 다룬다.
발견 → 평가 → 선택 → 조합 → 문서화 → 거버넌스 → 폐기를 하나의 생애주기로 연결한다.
요청에 해당하는 단계만 수행하고, 이미 유효한 결정과 검증은 재사용한다.

## 작업 범위와 책임

- 설계·리뷰 요청은 분석과 제안이다. 구현·공유 자산 변경은 요청된 범위에서만 수행한다.
- 작은 선택에는 기존 이슈의 짧은 기록이면 충분하다. 카탈로그나 포털부터 만들지 않는다.
- 알려진 제품 정책을 우선한다. UI 선택으로 권한·보존·공개·결제 정책을 조용히 바꾸지 않는다.
- 필요한 정보가 없으면 확인된 사실과 가정을 나누고, 그 정보가 바꾸는 선택만 보류한다.
- 외부 사례를 검색할 때 현재 환경과 재사용 조건을 확인한다. 공개 접근을 라이선스 허가로 보지 않는다.
- 실행 도구, 배포, 외부 공개와 사용자 모집 권한은 이 스킬이 부여하지 않는다.

## 판단 단위를 구분한다

| 단위 | 책임 | 오판 방지 |
|---|---|---|
| Pattern | 문제·맥락·행동·결과와 적용 조건 | 같은 외형이 같은 패턴임을 뜻하지 않는다 |
| Component | 구체적인 UI 구현, API와 실행 상태 | 하나의 패턴이 여러 컴포넌트를 사용할 수 있다 |
| Token | 색·간격·서체 등 이름 붙은 설계 값과 의미 | 값의 일치가 행동·사용성의 일치를 보장하지 않는다 |
| Variant | 같은 계약 안에서 허용하는 표현·구성의 차이 | 다른 사용자 목적을 옵션 플래그로 숨기지 않는다 |
| State | 조건·사건에 따른 현재 상황과 가능한 행동 | 시간에 따른 상태를 새 패턴으로 늘리지 않는다 |
| Design system | 위 자산과 결정·기여·배포·유지 과정 | 컴포넌트 패키지만으로 완성되지 않는다 |

패턴과 컴포넌트는 다대다로 연결될 수 있다. 이름 수를 코드 단위 수로 강제하지 않는다.
같은 문제·동작·변경 이유는 묶되, 외형 유사성만으로 공통화하지 않는다.

## 1. 발견: 문제와 맥락에서 후보를 찾는다

1. 누가 무엇을 끝내려는지, 어떤 결과를 보면 완료를 아는지 한 문장으로 적는다.
2. 여정 진입점, 과업, 사용자 집단, 환경·제약, 콘텐츠·데이터를 확인한다.
3. 정확한 대상 재탐색인지 새로운 대상 발견인지, 일회성인지 반복 업무인지 구분한다.
4. 기존 제품의 성공 사례·지원 이슈·디자인 시스템·구현 자산을 먼저 조사한다.
5. 부족한 부분만 패턴 모음, 플랫폼 관례, 실행 예제, 유사한 다른 도메인으로 넓힌다.
6. 대표 이름과 별칭을 기록하되 이름 분류 자체를 사용자 문제보다 앞세우지 않는다.

근거마다 관찰 대상·조건·확인 시점과 한계를 남긴다.
사용자 연구, 제품 관찰, 외부 사례, 원칙 기반 추정, 시각적 영감을 구별한다.
갤러리 이미지는 외형을, 동작 예제는 가능한 구현을 보여줄 뿐 우리 과업의 적합성을 증명하지 않는다.
유명 서비스의 채택이나 경쟁사의 전환율을 우리 제품의 인과 증거로 옮기지 않는다.

## 2. 평가: 맥락 적합성과 비용을 비교한다

후보마다 해결하는 문제, 맞는 조건, 사용하지 않을 조건을 먼저 적는다.
현재 구현 보수, 더 단순한 흐름, 아무 패턴도 추가하지 않기를 대안에서 제외하지 않는다.

- **과업 적합성:** 진입 이유, 데이터 규모·분포, 반복 사용, 완료 조건과 맞는가?
- **행동 이해:** trigger → action → feedback이 연결되며 결과와 범위를 예상할 수 있는가?
- **수행 비용:** 학습·입력·탐색·지연·중단·복구 부담이 어디로 이동하는가?
- **접근 가능성:** 입력 방식, 포커스·동적 안내, 좁은 화면, 확대에서 필요한 계약은 무엇인가?
- **정책 적합성:** 공개 범위, 동의, 계정 요구, 저장 수명과 권한을 보존하는가?
- **유지 비용:** 새 상태·변형·의존성·문서·운영 부담을 감당할 수 있는가?

클릭 수, 후보 개수, 개선율 같은 임의의 고정 숫자로 승자를 정하지 않는다.
특정 장치·사이트의 관례를 모든 제품의 법칙으로 만들지 않는다.
과업별 선택 함정이나 결합 예제가 필요하면 [선택과 조합](references/selection-and-composition.md)을 읽는다.

### 기만과 사용자 통제를 선택 단계에서 거른다

- **Smell:** 조사 신호다. 모달·숨은 탐색이 있다는 사실만으로 결함을 확정하지 않는다.
- **구현/맥락 결함:** 동작이 깨졌거나 특정 사용자 조건에 해법이 맞지 않는 경우다.
- **Anti-pattern:** 매력적으로 보이는 반복 해법이 빠뜨린 조건 때문에 더 큰 비용을 만든다.
- **Dark pattern:** 숨겨진 결과, 기만적 표현, 부당한 방해로 원치 않는 행동을 유도한다.

관찰된 메커니즘과 피해를 먼저 쓰고 제작자의 의도나 법적 위반은 근거 없이 단정하지 않는다.
정확한 가치 설명과 발견 가능한 선택은 설득일 수 있지만, 거절 은폐·수치심·허위 긴급성은 정당화하지 않는다.
동의가 필요한 행동은 목적·범위·효과를 선택 전에 설명하고, 선택·거절·철회 경로를 구별한다.
선택적 동의를 핵심 기능 조건에 불필요하게 묶거나 default·침묵·계속 진행을 동의로 치환하지 않는다.
거절 후 반복 압박, 가입보다 과도하게 어려운 취소, 철회 후 효과가 남는 범위를 확인한다.
보안상 필요한 확인은 목적과 비례성을 설명한다. 모든 추가 단계를 조작이라고 판단하지 않는다.
전환율 향상만으로 통제 침해를 승인하지 않는다. 법적 요건은 적용 관할·정책으로 별도 확인한다.

## 3. 선택: 결정을 검증 가능한 가설로 남긴다

1. 같은 역할·과업·데이터·환경에서 후보를 비교한다.
2. 불확실성이 선택을 바꾸면 해당 행동만 보여주는 최소 프로토타입이나 관찰을 준비한다.
3. 선택한 해법, 제외한 대안, 기대 이익, 잔여 비용, 미확인 가정을 기록한다.
4. 기존 관례에서 벗어나면 학습비용을 감수할 이유와 되돌릴 조건을 명시한다.
5. 실제 사용자 성과가 필요한 주장은 휴리스틱 판단·내부 데모와 분리한다.

단품 프리뷰가 보여준 상태만 근거로 삼는다. 모의 저장이나 정적 이미지를 제품 통합 성공으로 보고하지 않는다.
확인된 해로운 동작은 숨기지 않고 대안을 제안한다. 영향이 불확실하면 검증할 조건을 좁힌다.

## 4. 조합: 패턴 사이의 계약 충돌을 푼다

검색+필터, 목록+저장, 온보딩+가입처럼 함께 쓰는 패턴의 연결 지점을 먼저 찾는다.
각 패턴을 개별 평가한 결과만 합쳐 전체 성공으로 판정하지 않는다.

- **공유 의미:** query, category, selection 같은 이름이 같은 대상·단위·범위를 가리키는가?
- **소유권:** 공유 상태의 권위 있는 값과 변경 주체는 누구인가? 중복 소유로 충돌하지 않는가?
- **포함 관계:** 전체 검색과 현재 목록 검색, category와 facet의 관계가 화면 구조와 맞는가?
- **전환:** 새 검색·탭 이동·로그인·뒤로 가기·대상 변경 때 무엇을 보존/초기화하는가?
- **연결:** 앞 단계 결과가 다음 단계 선행조건을 충족하며 중단·거절 후 대안이 있는가?
- **피드백:** 결과 없음·범위 제한·처리 중을 어느 패턴이 설명하며 안내가 모순되지 않는가?
- **통제:** 공개 범위·저장 수명·동의가 조합으로 달라지는 순간을 사용자가 아는가?

충돌은 `조건 → 각 패턴의 약속 → 모순 → 선택한 정책 → 관찰할 결과`로 남긴다.
같은 뜻의 반복은 줄이되 범위·관계를 설명하는 필요한 반복은 보존한다.
중간 선택 단계는 모호함을 줄일 때만 추가한다. 조합마다 새 상위 컴포넌트를 만들지 않는다.
개별 패턴의 단점을 조합이 줄였는지, 다른 단계로 비용을 옮겼는지 다시 평가한다.

## 5. 문서화: 해법과 실제 구현을 연결한다

기존 명세나 패턴 항목에 필요한 내용만 보강한다. 화면과 코드만 저장하지 않는다.

- 이름·별칭, 사용자 문제, 적용/제외 맥락, 선택 이유와 대안.
- 행동 계약, variant/state 경계, 조합 관계와 정책 예외.
- component·token·콘텐츠 자산, 사용 제품·버전, 확인한 근거와 미검증 조건.
- 상태별 동작, 키보드·포커스·안내 등 접근성 요구, 구현 소유자와 변경 경로.

프리뷰를 정적·live markup·상호작용·실제 연결로 구분하고 mock 범위를 표시한다.
실제 소비 환경에 맞는 예제와 필요한 초기화·데이터 조건을 제공한다.
데모용 샘플 데이터나 장식이 제품의 필수 요구처럼 전파되지 않게 한다.
상세 기록 양식과 수명주기 운영은 [시스템 운영](references/system-lifecycle.md)을 읽는다.

## 6. 거버넌스: inventory에서 채택까지 관리한다

시스템 이용자가 누구인지, 재사용·일관성·협업 중 무엇을 개선할지 먼저 정한다.
팀의 규모와 실제 마찰에 맞는 최소 운영을 택하고 포털 구축을 선행조건으로 삼지 않는다.

1. 실제 화면·디자인 파일·코드·문서의 inventory를 만들어 같은 패턴의 변형과 소비자를 찾는다.
2. 재사용 가능, 보수 필요, 의미 있는 예외, 중복, 유해·폐기 후보를 구분한다.
3. 핵심 흐름에서 반복되는 문제부터 공유 자산으로 승격한다. 사용 횟수만으로 승격하지 않는다.
4. 제안·검토·승인·구현·문서 갱신의 책임자와 비개발자 기여 경로를 정한다.
5. 상태·접근성 계약, 구현·디자인 자산 버전, 호환성·migration 책임을 함께 관리한다.
6. 실제 소비 제품의 적용과 이탈 이유를 확인하고 지원·버그·변형 요청을 다음 결정에 반영한다.

동작은 다른데 외형을 강제하거나, 동작은 같은데 불필요한 차이를 방치하지 않는다.
예외에는 적용 범위·이유·소유자·재검토 조건을 둔다. 최신 구현을 자동으로 표준으로 삼지 않는다.
채택률만 목표로 삼지 않는다. 사용자 과업 결과와 팀의 변경·지원 부담을 함께 본다.

## 7. Retire: 사용 중단과 제거를 구별한다

- 유해한 행동, 더 나은 대안, 유지 불가, 실제 미사용 등 폐기 이유를 명시한다.
- 소비 제품과 버전을 조사하고 대체 패턴·데이터/행동 migration·지원 범위를 정한다.
- deprecated 상태는 새 채택을 제한하는 상태다. 기존 소비자가 사라졌다는 뜻이 아니다.
- 제거 전에 남은 참조와 사용자를 확인하고 필요한 전환·복구 경로를 준비한다.
- 승인된 범위에서 이동·제거한 뒤 소비자 동작과 문서 연결을 확인한다.
- 대체가 불가능한 소비자가 남으면 제한 지원 또는 예외를 기록하고 완료로 숨기지 않는다.

## 기존 스킬과 선택적으로 연결한다

필요한 책임만 연결하며 이 스킬 때문에 모든 QA를 추가 실행하지 않는다.

| 필요한 후속 판단 | 연결할 스킬 |
|---|---|
| 상태별 설명·다음 행동·요청의 정합성 | `ux-state-review` |
| 화면에서 발견·이해·선택 가능한지 | `dont-make-me-think` |
| 실제 전환·저장·복구와 시안 일치 검증 | `browser-e2e-review` |
| 미지의 여정을 폭넓게 탐색 | `exploratory-ux-qa` |
| 비동기·이벤트·저장 등 구현 메커니즘 | `review-client-runtime` |
| 선택된 기준과 변경 합의의 지속적 보존 | `preserve-decisions` |

세부 상태표·브라우저 증거 수집·합의 보존 절차를 복제하지 않는다.
결정한 계약과 확인 조건을 전달하고 해당 스킬의 결과를 원래 항목에 연결한다.

## 결과

처리한 생애주기 범위, 선택·조합·운영 결정, 근거와 미확인 조건을 짧게 전달한다.
제안, 승인된 결정, 구현, 검증, 실제 채택, 폐기 완료를 구분한다.
새 파일 수나 패턴 수가 아니라 요청한 문제의 결정과 인계가 해결됐는지 확인한다.
