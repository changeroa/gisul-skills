# Responsibility Design

시나리오에서 필요한 결과를 협력 객체의 책임으로 분배한다.
목표는 패턴 수나 클래스 수가 아니라 설명 가능한 소유권과 검증 가능한 동작이다.
명사마다 클래스를 만들거나 동사마다 서비스 클래스를 만드는 방식으로 시작하지 않는다.
언어의 함수, 모듈, closure, protocol도 적합한 책임 경계가 될 수 있다.

## 작업 범위

- 리뷰는 읽기 전용으로 시작한다. 수정은 명시적으로 요청된 범위에서만 한다.
- 현재 코드, 호출자, 요구사항과 테스트를 읽고 추정과 확인 사실을 구분한다.
- 실제로 읽지 않은 경로와 실행하지 않은 검사는 미확인으로 표시한다.
- 객체 설계를 이유로 public API, 저장 형식이나 외부 effect를 임의로 바꾸지 않는다.
- 이미 선택된 함수형·데이터 지향 설계에 클래스 계층을 강요하지 않는다.

## 1. 한 시나리오를 고정한다

1. actor가 달성하려는 결과와 시스템 경계를 한 문장으로 적는다.
2. 정상 흐름 하나와 중요한 거절·실패 흐름 하나를 고른다.
3. 외부 입력, 사전 상태, 필요한 상태 변화, 출력과 외부 effect를 적는다.
4. 시스템 연산과 UI 제스처를 구별한다. 클릭은 의미 있는 업무 요청으로 변환한다.
5. SSD가 있다면 외부 시스템 연산을 상세 협력의 진입 메시지로 사용한다.
6. SSD가 없다면 관찰 가능한 입력 사건을 정하되 가상의 문서를 만들지 않는다.
7. 후조건은 인스턴스 생성, 값 변경, 연결 형성·해제 등 확인할 결과로 나눈다.
8. 분석 모델은 설계 입력이지 구현 명령이 아니다. 잘못된 가정은 수정한다.

## 2. knowing / doing 책임 장부를 만든다

각 책임을 구체적인 질문으로 표현한다.
- **Knowing:** 누가 원본 상태, 관련 객체, 계산 가능한 사실을 아는가?
- **Doing:** 누가 생성, 계산, 상태 변경, 다른 협력의 시작·조정을 수행하는가?
- 책임은 의무의 추상화다. 반드시 메서드 하나 또는 클래스 하나와 대응하지 않는다.
- 큰 책임은 하위 책임으로 나누되 실제 결과와 연결되지 않는 분해는 피한다.
- 필요한 정보, 현재 소유자, 불변식과 실패 조건을 각 책임에 붙인다.
- 같은 사실을 여러 객체에 복사한다면 어느 표현이 권위 있는지 지정한다.
- 화면에 표시할 책임과 표시할 값을 알고 제공할 책임을 분리한다.
- 상태의 소유권과 일시적인 참조 접근권을 혼동하지 않는다.

장부 항목은 `책임 / 필요한 정보 / 후보 소유자 / 협력 / 후조건 / 검증`으로 적는다.
새 객체를 만들기 전에 기존 소프트웨어 타입과 그 계약을 먼저 확인한다.
도메인 용어는 이해를 돕지만 사람의 업무를 그대로 소프트웨어 객체에 몰아주지 않는다.

## 3. 결정 종류에 맞는 출발점을 고른다

- 외부 업무 요청의 첫 수신자를 정하면 Controller를 검토한다.
- 인스턴스 생성 책임이면 Creator를 검토한다.
- 그 외의 계산·지식·변경 책임은 Information Expert에서 시작한다.
- 출발점은 정답이 아니다. 모든 후보를 coupling과 cohesion으로 다시 평가한다.
- 원칙 이름만으로 결론을 내리지 말고 필요한 정보와 실제 변경 경로를 설명한다.

## 4. Information Expert로 정보와 행위를 연결한다

1. 책임을 완수하는 데 필요한 정보를 목록화한다.
2. 각 정보의 현재 소유자와 접근 가능한 협력자를 찾는다.
3. 대부분의 정보를 가진 dominant expert가 있는지 확인한다.
4. 여러 partial experts라면 각자 자신의 부분을 계산하고 의미 있는 결과로 협력한다.
5. 필드를 한곳에 모으는 대신 기존 소유자에게 행위를 요청할 수 있는지 본다.
6. 후보가 비슷하면 새 참조, 불안정 의존성과 무관한 책임 증가를 비교한다.
7. 현재 요구로 드러난 다음 변화는 동률 판단에 쓰되 상상한 미래를 증거로 쓰지 않는다.

**반례:** 기록 객체가 모든 저장 데이터를 안다고 해서 SQL·재시도·화면 출력을 소유하지는 않는다.
그 배치는 기술 의존, 중복과 관심사 혼합을 늘릴 수 있다.
그 경우 좁고 응집된 별도 협력자가 낫다.
반대로 모든 계산을 외부 서비스로 옮기고 원본 데이터를 계속 추출하면 결합이 커질 수 있다.
데이터 운반용 DTO·record에 억지로 업무 행위를 넣지 않는다.

## 5. Creator로 생성과 연결을 설계한다

후보는 다음 관계를 이미 가진 객체에서 찾는다.
- 생성 대상의 소유·포함·합성 관계를 관리한다.
- 생성 대상을 기록하거나 밀접하게 사용한다.
- 유효한 생성에 필요한 초기화 데이터를 안다.
- 수명과 불변식을 유지할 책임을 이미 가진다.

여러 후보가 가능하면 기존 포함 관계와 추가 의존 비용을 함께 비교한다.
생성, 초기화, 소유 컬렉션 등록과 후속 연결이 모두 수행되는지 확인한다.
반쯤 초기화된 객체가 외부로 노출되는 중간 상태를 피한다.
복잡한 타입 선택, pooling, 재사용, 자원 수명은 별도 생성 협력자를 정당화할 수 있다.
단순 생성 한 번을 위해 범용 factory chain을 추가하지 않는다.
소유자가 직접 생성하는 것과 composition boundary에서 의존성을 주입하는 것을 비교한다.
업무 규칙에 필요한 생성 결정과 기술 객체 조립을 구별한다.

## 6. Controller로 진입과 조정을 정한다

Controller는 UI 기술 밖에서 업무 요청을 처음 받는 역할이다.
web route나 framework의 MVC controller와 동일하다고 가정하지 않는다.
- 연산이 적고 관련성이 높으면 시스템·하위시스템 facade receiver가 충분할 수 있다.
- 서로 다른 시나리오가 많거나 세션 상태가 필요하면 use-case coordinator를 검토한다.
- 같은 대화의 연산들이 공유하는 상태와 순서 계약의 소유자를 분명히 한다.
- 화면 객체는 입력 변환과 표현을 담당하고 업무 판단은 위임한다.
- coordinator는 전문가들을 연결하되 그들의 상태나 계산을 복제하지 않는다.
- 여러 사용자·요청의 진행 상태가 하나의 가변 필드에 섞이지 않게 한다.

비대 징후는 무관한 연산 축적, 직접 계산 증가, 도메인 데이터 중복과 과도한 참조다.
먼저 실제 전문가에게 위임하고, 필요하면 시나리오별 coordinator로 나눈다.
모든 query를 coordinator에 전달하면 API가 비대해질 수 있다.
안정된 조회 계약에 직접 접근하는 대안도 비교하되 변경 명령이 불변식을 우회하면 안 된다.

## 7. 협력 메시지와 visibility를 검증한다

각 메시지에 다음을 지정한다.
1. 송신자와 수신자, 업무 의미가 드러나는 연산 이름.
2. 입력, 결과, 소유권·mutation 권한과 오류 계약.
3. 호출 전 필요한 상태와 성공 후 보장되는 변화.
4. 수신자 참조를 얻는 실제 경로와 참조가 유효한 시점.
5. parameter·local 참조인지 장기간 보관할 attribute인지.
6. 호출 실패 시 남는 상태와 이미 발생한 외부 effect.

참조가 필요하다는 이유만으로 전역 lookup을 도입하지 않는다.
반복 협력이 필요하면 생성 시 연결하고 일시적 사용이면 좁은 입력으로 전달한다.
전체 객체 전달은 내부 협력을 단순화할 수 있지만 불필요한 권한과 결합도 늘릴 수 있다.
경계 밖에는 필요한 데이터 계약을 사용하고 내부 그래프를 그대로 노출하지 않는다.
상호작용은 전체 흐름과 어려운 하위 흐름으로 나눠도 되며 메시지 정체성을 유지한다.

## 8. Low Coupling과 High Cohesion으로 대안을 비교한다

- 새 의존과 기존 의존을 구분하고 무엇이 불안정한지 적는다.
- 타입 선언, 생성, 인자, 반환, 상속과 호출도 의존이다.
- 안정된 라이브러리 직접 사용을 raw edge 수만으로 문제 삼지 않는다.
- 결합을 없애려다 한 객체가 모든 일을 하는 설계를 피한다.
- 관련된 목적·불변식·변경 이유와 업무량으로 응집도를 본다.
- 메서드 수·줄 수만으로 분리하지 않는다. 작은 전달 객체도 비용이다.
- 네트워크 경계를 넘는 세밀한 협력은 지연 비용이 크므로 원격 계약을 따로 평가한다.
- 현재 유지, 작은 책임 이동, 새 협력자 도입의 비용을 비교한다.

## 9. 초기화와 실행 증거로 마무리한다

유용한 업무 협력을 먼저 설계한 뒤 필요한 생성·연결 작업을 startup 목록으로 모은다.
코딩 시 최소 startup을 먼저 구현해도 되며 설계 순서와 실행 순서를 혼동하지 않는다.
정적 모델의 참조·연산이 동적 메시지의 수신자·입력과 일치하는지 확인한다.
query는 예기치 않은 영속 상태 변경을 하지 않아야 한다.
명령이 결과를 반환할지는 언어·원자성·API 계약으로 결정하고 무조건 void를 강요하지 않는다.
정상·거절·실패 시나리오를 UI 없이 실행할 수 있는 가장 작은 검증 경계를 고른다.
생성 수, 연결, 상태 전이, 외부 effect 순서와 재호출 결과를 검사한다.
실행하지 못했다면 테스트 제안과 실제 실행 증거를 구분한다.

## 결과와 QA

결과에는 시나리오, 책임 장부, 선택한 소유자, 협력 경로와 선택 이유를 적는다.
가장 단순한 대안, 거절한 후보와 남은 위험도 함께 적는다.
- 각 후조건을 어느 메시지와 소유자가 보장하는가?
- 어느 객체도 소유하지 않는 상태나 두 곳이 서로 믿는 검증은 없는가?
- controller가 전문가의 일을 빼앗거나 helper가 데이터를 과도하게 추출하지 않는가?
- 생성·조회·변경이 모두 실제 visibility와 수명 안에서 가능한가?
- 무효 순서, 부분 실패와 독립 세션에서 불변식이 유지되는가?
- 새 추상화가 현재 변경 비용을 줄이는가, 이름과 탐색만 늘리는가?
