# API 지연·데이터 요청 경로

## 지표와 요청 분류

브라우저 총시간·TTFB, 서버/함수 wall time·CPU time, 실행 환경 처리 시간, 응답 후 백그라운드 작업 시간을 분리한다. 낮은 CPU만으로 DB·스토리지·컨테이너 병목을 확정하지 않는다.

엔드포인트별 요청 수, p50/p95/p99, 4xx/5xx/timeout/취소, 요청·응답 크기, cold/warm, 동시성·대기열, 사용자 여정 영향을 확인한다. 평소 느린 요청과 드물게 매우 느린 요청을 나누고, 정상적인 긴 다운로드·스트리밍을 일반 JSON API와 섞지 않는다.

## 실제 경로 분해

실제 존재하는 홉만 그린다. 예: 브라우저 → CDN/프록시 → 함수/서버 → 인증 → DB/객체 저장소/외부 API → 직렬화 → 응답. 정적 페이지에 API 경로를 만들어 넣지 않는다.

확인 가능한 구간을 연결한다.

- DNS·연결·TLS·리다이렉트, CORS preflight·중복 왕복.
- 인스턴스 시작·애플리케이션 준비 대기, 스케일링·대기열.
- 연결 풀 획득·연결 재생성, 실제 DB 쿼리 수·시간.
- 객체 GET/HEAD/PUT/LIST 등의 횟수·시간과 외부 API 지연.
- 이미지 변환·압축/아카이브 생성·직렬화, 재시도·직렬 실행·불필요한 대기.
- 응답 이후의 처리와 사용자가 기다려야 하는 완료 조건.

가능하면 같은 request ID/trace ID로 연결한다. 현재 자료로 원인을 구분하지 못하면 `계측 필요`를 독립 항목으로 남기고 최소 구간 로그·trace·Server-Timing을 제안한다. 외부 응답과 로그에 민감한 내부 정보가 새지 않게 한다.

## 중복·직렬 처리·DB 효율

동일 요청의 반복 조회, N+1, 원본/미리보기의 메타데이터 중복 조회, 저장 직후 불필요한 전체 재조회, 독립 I/O 직렬 실행, 완료 단계 재실행, 불필요한 필드·이미지·본문, polling, 페이지네이션·쿼리·인덱스를 조사한다. 코드 모양만으로 결함이라고 단정하지 말고 실제 빈도·비용·정합성 의도를 확인한다.

DB는 실제 쿼리·실행 계획 등으로 판단한다. 실행 계획 분석 명령이 쿼리를 실제 실행하는지 확인하고, 운영의 무거운 스캔이나 비용 큰 분석은 허용 범위를 지킨다. 병렬화는 제한된 동시성으로 검토하고 메모리·연결 수·하위 서비스 부하·오류율·처리 순서를 함께 검증한다. 성능 개선을 위해 권한·정합성·중복 방지·필요한 저장 확인을 제거하지 않는다.
