# 실행 환경·스케줄러·작업 안정성

## 서버·함수·컨테이너와 배포

존재하는 실행 환경에 맞춰 사양·인스턴스 수, 평상시/피크 CPU·메모리, 무거운 작업·동시 요청 부하, 재시작·OOM·비정상 종료, 시작/준비 완료 시간, 휴면·스케일링 조건, 연결·캐시·임시 파일 초기화, 종료 시 진행 중 처리, 대기열·장시간 작업 경합을 확인한다. 특정 공급자의 `sleepAfter` 같은 필드는 실제 사용하는 경우에만 조사한다.

빈 브라우저 캐시와 서버 cold start를 구분한다. 운영 인스턴스를 임의로 중단하지 말고 기존 시작 로그와 자연 발생한 첫 요청을 우선 활용한다. 재시작 실험은 격리 환경 또는 명시적으로 허용된 범위에서 수행한다.

휴면 변경은 “유휴 종료 임계값을 짧게 함” 또는 “실행 상태를 더 오래 유지함”처럼 방향을 명시하고 비용·첫 요청 지연을 함께 비교한다. 사양 축소는 평균 메모리만으로 판단하지 말고 무거운 작업의 피크와 여유 용량을 확인한다.

재시작/배포 후 미완료 작업을 찾아 재개할 수 있는지, 필수 데이터가 임시 디스크에만 있지 않은지, 이전/새 작업자가 중복 완료하지 않는지 확인한다. 라우팅·애플리케이션·실행 이미지·스키마 등 실제 배포 구성의 호환성을 확인한다. 배포 성공 메시지와 실제 서비스 버전은 구분한다.

## Cron·스케줄러·큐·내부 타이머

설정 파일과 실제 등록 상태를 대조한다. 여러 스케줄러·내부 타이머·수동 실행 경로가 같은 작업을 호출하는지도 본다. 트리거별 식/주기, 환경, 공급자 시간대와 선택한 표시 시간대, 핸들러·매개변수, 실제 실행·처리 결과, 유지 목적·보존 정책, 중복 방지 장치를 기록한다. 시간대 전환이 있는 환경은 일광 절약 시간 경계도 고려한다. 한국 시각을 보편적 기본값으로 고정하지 않는다.

같은 시각이라고 같은 작업, 다른 이름이라고 다른 작업으로 판단하지 않는다. 공급자의 현재 스케줄 문법으로 대표 기간의 예정 실행 시각을 펼쳐 비교한다. 트리거 발생, 핸들러 호출, 실제 업무 처리 횟수를 구분한다. 감소 횟수는 어떤 실행을 제거하는지 계산 근거를 남긴다. 일일/주간 작업 통합이 보존 기간·마감·정리 대상·누락 보충에 미치는 영향을 확인한다.

다음을 격리 테스트와 기존 기록으로 검증한다. 운영 maintenance를 시험 삼아 실행하지 않는다.

- 실행 겹침·중복 전달·재시도에도 결과가 중복되지 않는가?
- 실패·중단 후 필요한 작업을 다시 찾을 수 있는가?
- 멈춘 작업의 소유권/잠금이 영구히 남지 않고 안전하게 회수되는가?
- 일부 성공을 전체 성공과 구분하고 성공·실패·재시도·미처리 수를 확인할 수 있는가?
- 시간 경계와 이전/새 작업자 경쟁에서 누락·중복이 없는가?

문제 규모에 비해 과도한 큐·스케줄러 도입을 기본 해법으로 삼지 않는다.

## 오류·관측·재시도

런타임 예외, HTTP 4xx/5xx, 정상 검증 실패·권한 거절, 사용자 취소·연결 종료, timeout·재시도, 내부 서비스/작업 실패, 일부 처리 후 성공처럼 보이는 결과를 구분한다. 예외 0건은 서비스 오류 0건이 아니다. HTTP 200 또는 202 접수만으로 업무 완료를 확정하지 않는다.

실패한 사용자 여정·요청/작업·단계, 안전한 재시도 여부, 자동 복구/관리자 개입, 발견 가능한 로그·경고를 확인한다. 최대 재시도 횟수·대기 간격·중복 방지·최종 실패 처리를 조사한다. 관측 추가 시 개인정보·로그 비용·샘플링·보존 기간을 고려한다. 기존 도구로 해결 가능하면 새 관측 플랫폼을 기본으로 추가하지 않는다.
