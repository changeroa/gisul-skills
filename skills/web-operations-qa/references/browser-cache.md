# 브라우저·CDN·애플리케이션 캐시

## 계층과 측정 조건

브라우저 메모리/디스크, 존재하는 Service Worker, CDN, 프록시·서버·애플리케이션, 존재하는 DB 결과 캐시를 분리한다. CDN HIT는 브라우저 무요청을 뜻하지 않는다. 브라우저 재사용, 304 재검증, 본문 전체 재전송을 구분한다. 304 자체는 캐시 실패가 아니다.

요청 범위와 실행 권한 안에서 다음을 구분하여 측정한다.

- 빈 브라우저 캐시의 첫 방문.
- 캐시가 활성화된 상태에서 같은 화면 재방문.
- 일반 새로고침.
- 강력 새로고침/캐시 비활성화 상태의 진단 측정.
- 배포 후 기존 탭·기존 캐시가 남은 사용자의 재방문. 운영 배포 권한이 없으면 격리 환경의 검증과 실제 운영 미검증을 구분한다.

DevTools의 Disable cache, 자동화 설정, 요청 가로채기가 캐시 동작을 바꾸는지 확인한다. 비활성화 상태를 일반 재방문 경험으로 보고하지 않는다. 각 측정의 브라우저·지역·네트워크·기기·캐시 조건을 기록한다. 존재하는 실제 사용자 성능 지표와 실험실 측정은 구분한다.

## 자산별 정책과 실제 응답

HTML, 내용 해시 JS/CSS, 폰트·이미지, manifest, Service Worker 파일을 구분한다. 실제 GET에서 Cache-Control, ETag/Last-Modified, Age, Vary, Content-Encoding, 상태 코드·전송량, 공급자가 제공하는 캐시 상태 헤더를 확인한다. Cloudflare의 CF-Cache-Status 등 공급자 헤더는 해당 환경에서만 사용한다. HEAD가 GET과 같다고 가정하지 않는다.

내용 변경 시 URL도 반드시 바뀌는 자산만 장기 캐시와 `immutable` 후보로 삼는다. 예를 들어 공개된 내용 해시 자산에는 `Cache-Control: public, max-age=31536000, immutable`을 검토할 수 있지만, 경로가 `/assets/`라는 이유만으로 보장된다고 판단하지 않는다.

HTML은 새 배포를 발견할 갱신 정책을 확인한다. HTML·동적·인증 응답까지 장기 캐시를 일괄 적용하지 않는다. URL 외에 응답을 바꾸는 계정·쿠키·쿼리·언어·인코딩 등이 캐시 키와 실제 계층 동작에 반영되는지 확인한다. Vary가 모든 CDN에서 같은 방식으로 처리된다고 가정하지 않는다.

헤더 설정이 실제 응답 생성 계층에 적용되는지 확인한다. 빌드 산출물 포함 여부, 경로 매칭, 규칙 우선순위, 애플리케이션/호스팅/CDN 간 덮어쓰기를 검사한다. 예를 들어 Cloudflare Static Assets의 `_headers`를 쓸 때 정적 자산 응답과 Worker가 직접 생성한 응답을 구분하고 현재 공식 적용 범위를 확인한다. 설정 파일만 보지 말고 실제 GET과 브라우저 재방문으로 검증한다.

## 캐시 정확성·권한·배포 경계

- 수정 사항이 필요한 시점에 반영되고, 저장 후 잘못된 이전 결과가 남지 않는가?
- 로그인·로그아웃·계정/테넌트 전환에서 다른 사용자의 데이터가 노출되지 않는가?
- 권한 제거 후 보호 자료 접근이 정책대로 차단되는가? 이미 내려받은 로컬 사본과 이후 서버 접근을 구분한다.
- 조건부 요청·304 경로에서도 필요한 인증·권한 검증이 유지되는가?
- 보호 이미지·문서·다운로드에 공개 캐시 정책을 일괄 적용하지 않았는가?
- 새 HTML과 구버전 JS/CSS가 섞이거나 기존 탭의 지연 로딩 청크가 사라지는가?
- 누락된 JS 요청에 SPA의 HTML이 반환되는가?
- Service Worker가 있다면 업데이트·활성화·기존 탭 제어와 복구 경로는 적절한가?

권한과 ETag/304가 이미 구현되어 있으면 실제 동작을 확인하고 없는 기능처럼 중복 제안하지 않는다. 장기 캐시의 효과와 새 버전 전환·구버전 복구를 함께 검증한다. 복구를 위한 광범위한 캐시 삭제를 무조건 실행하지 않는다.
