# 객체 저장소·보존·정리·정합성

R2·S3 등 실제 연결된 저장소와 허용된 버킷/컨테이너/prefix 범위만 조사한다. 공급자별 Lifecycle·버전 관리·복구·일관성 보장을 동일하다고 가정하지 않는다.

## 현황과 참조

객체 수·저장량·증가 추세, 원본/파생/아카이브/임시 파일 구성, 객체 키와 DB/메타데이터 참조, Lifecycle 조건·적용 대상, 미완료 multipart upload 정리 설정, GET/HEAD/PUT/LIST 작업량을 확인한다. 일부 목록이나 prefix 표본을 전체 현황으로 보고하지 않는다. 대량 LIST 자체의 부하·비용도 고려한다.

다음을 구분한다.

- 저장소에 있지만 유효한 참조가 없는 후보.
- DB/메타데이터에서 참조하지만 저장소에는 없는 객체.
- 업로드·처리 중이라 최종 참조가 아직 없는 객체.
- 보존 정책상 의도적으로 남긴 객체.

화면에 보이지 않는다고 고아 객체로 확정하지 않는다. 실제 서비스의 활성/활성화 예정 데이터, 진행 중 작업, 예약·확정·발행, 이전 버전·복구, 공유 참조·관리자 보존 관계를 조사한다. 객체 나이만으로 삭제 가능 여부를 판단하지 않는다. Lifecycle이 애플리케이션의 DB 참조를 판별한다고 가정하지 않는다.

## 삭제 정책을 제안할 때

1. 후보를 읽기 전용으로 산출한다.
2. dry-run으로 대상·개수·용량·근거를 확인한다.
3. 업로드·재시도·예약·보존·복구 기간에서 유예기간을 도출한다. 임의 숫자를 확정 정책으로 만들지 않는다.
4. 삭제 직전 참조와 객체 상태를 재확인한다.
5. 재참조·업로드·활성화와 삭제의 경쟁을 보호한다. 재확인만으로 경쟁이 사라졌다고 보지 않는다.
6. 제한된 배치 크기·중단 조건으로 실행한다.
7. 결과와 실패 항목을 감사 가능한 형태로 남긴다.

실제 삭제는 해당 행동까지 허용된 경우에만 수행한다. 코드 롤백과 삭제 객체 복구를 구분하고, 복구 수단이 없으면 명시한다. dry-run 검증에는 참조 중·처리 중·공유·복구용 객체가 제외되는지 포함한다.
