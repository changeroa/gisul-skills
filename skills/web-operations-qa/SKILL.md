# 웹 운영 성능·캐시·효율·안정성 QA

실제 사용자 여정, 네트워크 요청, 코드·배포 설정, 운영 지표·로그를 연결하여 불필요한 대기·반복 처리·잘못된 캐시·장애 시 누락과 중복·비용 낭비·관측 공백을 찾는다. 일반적인 권장 사항보다 **확인한 문제, 판단 근거, 최소 변경, 검증 결과**를 남긴다.

특정 도메인·공급자·프레임워크·API·DB·객체 저장소가 있다고 가정하지 않는다. 정적 페이지부터 서버 기반 웹앱까지 실제 구성과 요청 범위에 맞춰 적용한다. QA만 요청되면 조사와 개선안까지, 개선 구현도 요청되면 허용된 코드 수정과 검증까지 진행한다. 이 스킬을 읽는 것 자체는 운영 변경 허가가 아니다.

## 1. 대상과 실행 범위 확정

대화·저장소·기존 연결 설정에서 다음을 파악한다. 이미 제공된 정보나 승인을 다시 묻지 않는다. 대상 또는 권한을 정할 수 없어 의존 작업이 막힐 때만 필요한 정보를 질문하고, 독립적으로 가능한 조사는 계속한다.

- 대상 URL과 환경: 운영·스테이징·프리뷰를 구분한다. API·자산 도메인은 실제 요청과 설정에서 찾는다.
- 저장소·작업 경로·배포 방식·관측 도구·공급자 연결과 이용 가능한 권한.
- 조사할 사용자 여정, 기존 요구사항·성능 목표, 사용 지역·표시 시간대, 요청한 결과가 진단인지 구현인지 운영 적용인지.
- QA 계정·데이터와 부하 허용 범위. 없으면 공개·읽기 경로부터 확인하고 제한을 기록한다.

리소스마다 이름/식별자, 역할, 환경, 도메인·라우팅·바인딩·호출 관계, 코드/설정 근거를 연결한다. 전용 리소스와 공유 리소스를 구분하고, 개발·과거 프로젝트 사용량을 운영 수치에 합산하지 않는다. 계정 전체 수치만 보이면 운영 전용 수치와 구분한다.

정적 사이트는 브라우저·호스팅·CDN부터 조사한다. 서버 실행 환경, DB, 스케줄러, 객체 저장소는 존재하고 범위에 포함될 때만 조사한다. 접근할 수 없는 구성 요소는 `미확인`, 확인 결과 없는 구성 요소는 `해당 없음`으로 남긴다.

## 2. 실행 권한과 운영 안전

- 운영의 기본 작업은 읽기 조사와 저부하 검증이다. 구현이 요청되고 코드 변경 권한이 있으면 프로젝트 규칙에 맞는 브랜치/격리 작업 공간에서 최소 변경과 필요한 테스트를 진행한다.
- 운영 배포·설정 변경은 현재 대화에서 허용한 범위에 한한다. 허용되지 않았다면 조사·로컬 구현·테스트를 끝내고 적용 대상·변경점·위험·중단 기준·복구 절차를 구체화한 뒤 필요한 승인만 요청한다.
- 운영 데이터/객체 삭제, 스케줄러 실행·삭제·주기 변경, 인스턴스 강제 재시작, 광범위한 캐시 삭제, 사양·휴면·스케일링 변경, WAF·권한·인증·공개 범위 변경, 실제 게시·메일·결제, 고부하/대량 요청은 그 행동까지 허용된 경우에만 실행한다. 일반적인 QA·개선 요청이 이를 모두 허가하지는 않는다.
- 쓰기 검증에는 식별 가능한 QA 계정·데이터를 사용한다. 로컬/스테이징 명령의 실제 연결 대상이 운영 DB·저장소가 아닌지 먼저 확인한다. 공개 URL 접근만 가능한 경우 외부 관측 범위에서 진행한다.

## 3. 기준선과 증거

기존 보고서의 수치·원인·우선순위를 검증 대상으로 취급한다. 기존 주장은 `일치 / 일부 일치 / 불일치 / 미확인`으로 구분한다. 예를 들어 낮은 CPU, 특정 캐시 헤더, 예외 0건만으로 병목·전체 캐시 동작·전체 서비스 정상 여부를 확정하지 않는다.

운영 이력이 있으면 최근 24시간·7일을 우선 확인하고, 필요할 때만 기간을 늘린다. 모든 수치에 조회 시각, 대상 기간·시간대, 리소스·환경·엔드포인트, 정확한 지표명·정의·단위, 요청/표본 수, 출처·조회 조건, 샘플링·보존·집계 지연 한계를 붙인다. 아직 이력이 없으면 가능한 측정과 누락된 기준선을 명시한다.

평균뿐 아니라 가능한 p50·p95·p99·실패율을 함께 본다. 적은 표본의 높은 백분위수를 안정적 특성으로 해석하지 않는다. 기간·엔드포인트·성공/실패·cold/warm 상태를 섞지 않는다. 구간별 p95를 합산하거나 전체 p95에서 CPU p95를 빼서 구간 지연을 계산하지 않는다.

실제 존재하는 주요 여정을 재현하고 요청이 화면과 행동에 주는 영향을 연결한다. 기존 여정/QA ID가 있으면 재사용한다. 브라우저 도구의 현재 사용 지침을 따르고, HAR를 지원하면 수집한다. 지원하지 않으면 가능한 네트워크 기록·헤더·화면 증거로 대체하고 누락 범위를 남긴다. HAR만으로 서버 내부 원인을 단정하지 않는다.

증거에는 `PERF-001` 같은 문제 ID를 연결한다. HAR·trace·로그·캡처를 공유/저장하기 전에 Cookie, Authorization, 세션·토큰·비밀번호, 서명 URL 자격 증명, 개인정보·민감한 본문을 제거한다. 실제 생성되어 내용이 유효한 파일과 조회 근거만 보고한다. 접근 권한 부족, 로그 부재, 보존 만료, 도구 제약을 구분하고 “관측하지 못함”을 “없음/정상”으로 바꾸지 않는다.

## 5. 개선 선택과 검증

사용자·데이터 영향, 빈도·범위, 원인 확신, 효과, 구현 난이도, 회귀 위험·복구 가능성, 현재 규모를 함께 판단한다. `지금 수정할 근거가 충분함 / 계측 우선 / 규모 증가 후 검토 / 현재 적절하여 유지`를 구분한다.

가능하면 한 변경에서 하나의 주요 가설을 검증한다. 무관한 리팩터링·명명 변경·의존성 교체를 섞지 않는다. 권한·정합성 검증, 중복 방지, 필요한 저장 확인을 성능을 위해 제거하지 않는다. 설정도 추적 가능한 변경으로 남긴다. 계측 추가는 병목 해결과 별도로 보고한다.

변경 전에 성공 기준과 회귀 방지 조건을 정한다. 기존 요구사항이 없으면 검증용 제안을 서비스의 확정 목표처럼 쓰지 않는다. 동일 여정·데이터 규모·브라우저·지역·캐시 조건·서버 상태에서 전후를 비교하고, 표본·변동·오류율·메모리 영향도 확인한다. 한 번 빠른 응답이나 로컬 결과를 운영 개선으로 보고하지 않는다.

변경 위험에 맞춰 단위·통합·브라우저 검증을 조합한다. 캐시·권한·저장·예약·업로드 등 실제 영향받는 기능을 확인한다. 운영 부하를 제한하고, 재시작·중복 작업·시간 경계·삭제 경쟁은 격리 환경에서 검증한다.

운영 적용이 허용되면 영향 범위를 최소화하여 적용하고 실제 응답·헤더·서비스 버전/이미지·등록된 작업·지표로 확인한다. 배포 명령 성공과 서비스 적용, 효과 검증은 별개다. 관측 기간이 부족하면 `적용 완료·효과 관측 필요`, 운영 적용 전이면 `구현 완료·운영 미적용`으로 남긴다.

## 6. 결과 작성

[증거와 보고서 형식](references/report.md)에 따라 요청 규모에 맞는 보고서를 작성한다. 담당자가 무엇을 왜 바꾸는지, 실제 적용·개선 여부를 어떻게 확인하는지, 문제가 생기면 어떻게 중단·복구하는지 판단할 수 있어야 한다. 요청 범위 밖의 조사나 구현·배포를 완료한 것처럼 표현하지 않는다.
